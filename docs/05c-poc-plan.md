## 1. 過去の優先順位の確認

`01b` 7.4節 と `01` 11章で確定済みの順位は変わっていない。

| 優先 | PoC | 対応リスク | 失敗時の影響 |
| --- | --- | --- | --- |
| **1** | **PoC-01**（計装経路） | R-02 | 最大。失敗するとサーバー以降が全て L2 になり、価値提案の再定義が要る |
| 2 | PoC-03（要素→コード、特に Turbopack） | R-03 | 大。要素選択と編集の成否を決める |
| 3 | PoC-02（RSC計装） | R-02 | 中。対象プロジェクトの範囲を決める |
| 4 | PoC-04（対応付け精度） | R-01 | 中。粒度と確度表示の設計を決める |

**今回やるのは PoC-01 である。** 今回の依頼（HTTP通信とSQL実行を観測し UI へ渡す）は PoC-01 の範囲とほぼ一致する。
未検証リスク UR-02（バンドル後のコードに ORM 計装がフックできるか）・UR-03（dev server のワーカーへ `NODE_OPTIONS` が伝播するか）・UR-04（性能影響）も PoC-01 が担当する。

## 3. 検証アプリ（隔離された架空アプリ）

実案件のコードにも DB にも接続しない。本番環境を変更しない。

| 項目 | 内容 |
| --- | --- |
| 置き場所 | 本リポジトリの外、または `poc/fixture-app/`（本体のビルドに含めない） |
| 構成 | Next.js 15 (App Router) + TypeScript + PostgreSQL + Prisma |
| 規模 | ページ3枚 / API ルート3本 / SQL発行箇所5か所（`01b` Q-01.3 の題材そのまま） |
| DB | **ローカルの使い捨て PostgreSQL**（コンテナ）。専用スキーマ。実案件のDBへ接続しない |
| データ | 架空の地名・連番のみ。氏名・住所・連絡先・決済情報を一切含めない |
| バンドラ | Turbopack / webpack の両方で実行する（UR-01 / C-5） |

### 収集してよいもの / いけないもの

| 収集する | 収集しない |
| --- | --- |
| スパンの名前・開始時刻・終了時刻・親子関係 | **SQL のパラメータ値**（NFR-20。構造だけを取る） |
| 実行された SQL 文（プレースホルダのまま） | **Cookie / Authorization ヘッダ / 接続文字列 / 環境変数** |
| HTTP のメソッド・パス・ステータス・所要時間 | リクエストボディ・レスポンスボディの中身 |
| 情報スキーマから読んだテーブル・カラムの定義 | 行データ（実データ値） |

収集物は**ローカルのファイルに書き出すだけ**とし、外部へ送信しない。

## 5. UI データモデルへの変換

### 5.1 対応表

| 観測したもの | 変換先（`02a`） | 実装上の型 | 鍵になる属性 |
| --- | --- | --- | --- |
| ブラウザのネットワーク記録 1件 | `HttpExchange` | `TraceNode{kind:'http'}` | メソッド・パス・ステータス・`metrics.durationMs` |
| ルートハンドラのスパン | `Span` | `TraceNode{kind:'server'}` | スパン名・`metrics.durationMs` |
| ORM計装のスパン（`db.statement`） | `SqlStatement` | `TraceNode{kind:'sql'}` | SQL文・`metrics.durationMs` / `metrics.rows` |
| SQL の FROM 句 + 情報スキーマ | `DbTable` | `TraceNode{kind:'table'}` | スキーマ名 + テーブル名 |
| SQL の SELECT 句 + 情報スキーマ | `DbColumn` | `TraceNode{kind:'column'}` | カラム名 + 型 |
| トレースIDの一致 | `handles` | `TraceHop` | — |
| スパンの親子関係 | `executes` | `TraceHop` | `parentSpanId` |
| SQL の構文解析 | `reads` / `projects` | `TraceHop` | ⑤ を始点とする（**⑥→⑦ を作らない**） |

### 5.2 変換で守ること

| # | 規約 | 根拠 |
| --- | --- | --- |
| 1 | **`projects` の始点は `SqlStatement`。`DbTable` から `DbColumn` への辺を作らない** | `02a` 3.5節 / `02d` 2.3節 |
| 2 | **観測できなかった区間を省略しない。** 切断として表現する | OBS-05 |
| 3 | **ステップバッジを変換結果に持たせない。** バッジはスコープ内の表示順から再計算する揮発値である | `02` 5.3節 / `02a` 5章 |
| 4 | **件数・経路全体の観測性・最弱環を変換結果に持たせない。** 経路から算出する | `02d` 2.3節 |
| 5 | **スパンの開始時刻を保持する**（第7章） | `03c` 5.2節 |
| 6 | 座標・レイアウトは変換の対象外。UI 側の責務 | — |

### 5.3 変換アダプタの置き場所

現在の `src/lib/trace.ts` は**合成データと図の座標が同居している**。変換を入れる前に、次の3層に分ける。

```
観測結果（PoC が出力する JSON）
  ↓  adapter（PoC-01 の成果物。純粋な変換。UI を知らない）
オブジェクトモデル（02a: LineagePath / TraceNode / TraceHop / Observability）
  ↓  layout（座標を与える。現在 trace.ts が持っている部分）
描画（FlowScene）
```

**この分離は PoC-01 の成否にかかわらず必要である。** 今回の計画では adapter の出力＝オブジェクトモデルの JSON を成果物とし、
UI への接続は「合成データを同じ形の JSON に置き換えられること」を確認するところまでとする。

## 6. 実測と推定の分離

変換時に、要素ごとに `observability` と `source` を**取得した時点で**決める。後から埋めない。

| source | レベル | この PoC で出る箇所 |
| --- | --- | --- |
| `browser-network` | L0 | ③ の所要時間・ステータス |
| `trace-span` | L1 | ④、⑤ |
| `trace-context` | L1 | `handles` |
| `orm-instrumentation` | L1 | ⑤ の SQL文 |
| `sql-ast-parse` | **L1相当** | `reads` / `projects` / ⑥ / ⑦ |
| `db-introspection` | L0 | ⑥ / ⑦ の定義 |
| `orm-schema-map` | **L2** | `maps`（取れた場合） |
| `time-window` | **L2** | 親子関係が取れず時間窓で紐付けた場合（＝判定「条件付き成功」） |
| `none` | — | ①②、`renders`、`derives`（本PoCの範囲外） |

> **UI 上は `実測` / `推定` の2語のみを出す。** L0〜L3 の記号は出さない（UXR-12 / `02d` 3.2節）。
> ただし**モデルは `source` を保持する**。較正（PoC-04）に後から必要になり、後付けできないためである（`02d` 7章）。

## 7. 採番に必要な最小のデータ追加（Phase 5C からの持ち越し）

`03c` 5.2節のページスコープの採番（スパン開始時刻順）は、**現在の合成データでは実装できない**（第9章）。
PoC-01 で実測を得る際、次を記録すれば実装可能になる。

```ts
/** ページ読み込み開始を 0 とした相対ミリ秒。スパンに対応する要素だけが持つ */
span?: { startMs: number; endMs: number }
```

| 対象 | 持つか |
| --- | --- |
| ③ 通信 / ④ サーバー処理 / ⑤ 実行SQL | **持つ**（スパンである） |
| ⑥ テーブル / ⑦ カラム / ② コンポーネント | **持たない**（定義であってスパンではない） |
| ① 表示された値 | DOM を読んだ時刻。スパンではない |

> **残る論点**: ページスコープの採番対象は「スパンだけ」なのか、「俯瞰に描かれる全ノード」なのか。
> `03c` 5.2 は前者を書いているが、俯瞰には定義ノードも描かれる。**開始時刻を得ても、この判断は別に必要である。**
> 本PoCでは時刻を**記録するだけ**とし、採番規約の確定は UI 側の判断に委ねる。

## 8. 判定基準

`01b` Q-01.4 をそのまま用い、変換の基準を追加する。

| 基準 | 成功 | 条件付き成功 | 失敗 |
| --- | --- | --- | --- |
| SQL取得率 | 95%以上 | 80〜95% | 80%未満 |
| HTTP取得率 | 99%以上 | 95〜99% | 95%未満 |
| 親子関係 | SQLスパンが HTTPスパンの子として紐付く（**L1 成立**） | 時間窓推定のみ（**L2 へ降格**） | 紐付けできない |
| 非追加(b) | 方式2が機能する | 方式1のみ | いずれも不可 |
| バンドラ | Turbopack / webpack 双方 | 片方のみ | 双方で不安定 |
| 性能 | 起動 +20%以内 / 遅延 +10ms以内 | 起動 +50%以内 / 遅延 +30ms以内 | それ以上 |
| **変換（追加）** | **③〜⑦ と h3〜h6 が機械的に構成でき、探索画面が合成データと同じ構造で描ける** | 一部を手で補う必要がある | 構成できない |
| **分離（追加）** | **全要素に `source` が付き、推定が実測に混ざらない** | 一部が `none` に落ちる | 区別できない |

失敗時の縮退は `01b` Q-01.5 の代替1〜4 をそのまま使う。**代替4（サーバー以降が全て L2）でもプロダクトは成立する**（NFR-12）。
