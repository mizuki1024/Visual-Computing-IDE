## 1. 製品での再現条件と原因

### 1.1 レビューの主張の確かめ方

レビューの RV07 は `resolveSelection` を直接呼んだ単体の再現で、「HMR 後の DOM で同じ識別子が新しい要素に付くことは注入の規則からの帰結で、画面の操作では確かめていない」（06h レビュー 第5節）。本作業では、**修正前の製品のコードのまま**、実ブラウザ・実際の HMR で探索モードの選択を操作して確かめた（`tests/select-revision-e2e.spec.mjs`。記録 `docs/07c-f01-results/e2e-baseline.txt`）。

区別した3つの経路と、修正前の結果:

| 経路 | 作り方 | 修正前の結果 |
| --- | --- | --- |
| **(a) 古い DOM・古い通信結果による誤対応** | ソースを変え、開発サーバーに直接ページを要求して変換（対応表の書き直し）を起こす。プレビューへの HMR は試験の転送役で止め、DOM は前の版のまま。古い DOM の `span.code` をクリックする | **誤対応**。`src/app/cards-rsc/page.tsx:22:13` に「特定済み」、右ドックの JSX は**新しい要素**の `<span className="kind">新着</span>`（選んだのは `<span className="code">{s.code}</span>`） |
| 　同上（要求の途中） | クリックの要求を転送役で止めている間に、同じ行・列へ別の `<span>` を足す | **誤対応**。同じく新しい要素に特定 |
| 　同上（兄弟の入れ替え） | `RegionBadge` の `badge-dot` と `badge-text`（同じ `<span>`・同じコンポーネント）を入れ替え、HMR の前の DOM で `badge-text` を選ぶ | **誤対応**。`badge-dot` の位置に特定 |
| **(b) ソース変更後の識別子の再利用による誤対応（既存の選択）** | 選択した後に、そのファイルを変える | **前の要素の情報を現在の情報として出し続ける**。選択の行・右ドック（位置・JSX の行）・キャンバスのコンポーネントが残る。Server Component・Client Component のどちらでも |
| **(c) 現在の DOM を新しくクリック** | HMR の後の DOM をクリックする | **正しい**。いまのソースの要素（移った後の位置を含む）に特定する |

つまり F-01 は**探索の経路で成立する**（PoC だけの問題ではない）。書き込みは無いが、利用者が選んでいない要素の位置とソース行を「特定済み・実測」として出す。

### 1.2 原因

- 要素識別子は `sha1(ファイル:行:列)` だけから決まる（`poc/anchor/transform.cjs` の `anchorId`）。**どの版のソースから描いたかを DOM が持っていない。**
- 照合（`resolveSelection` の6段）は「いまの対応表」と「いまのソース」だけを見る。古い DOM の識別子は、同じ位置に来た新しい要素の識別子と同じ値なので、6段すべてを通る。
- 対応表とソースの版を比べるだけでは足りない。HMR の再コンパイルで対応表とソースは新しい版で揃い、**古い DOM だけが前の版**という状態（経路 (a)）がふつうに起きる。
- 画面は、選択を解決した後にソースが変わっても確かめ直さない（経路 (b)）。

## 3. 選択とソースの版を照合する仕組み

### 3.1 照合する4つの版

| 版 | どこにあるか | 何の版か |
| --- | --- | --- |
| **DOM の版** | クリックした要素の `data-vcide-rev`（祖先はそれぞれの `data-vcide-rev`） | その要素を描いたモジュールを**変換したときのファイルの内容** |
| **変換結果の版** | 変換が差し込んだ `data-vcide-rev` そのもの | 同上（変換結果と DOM の版は同じ値。DOM の版は「その変換結果から描かれた」ことの記録） |
| **対応表の版** | 対応表のファイルごとの `rev`（ローダが同じ変換で書く） | 対応表の行・列・タグ・コンポーネントが、どの内容について書かれたか |
| **ファイルの版** | IDE が照合のたびにファイルを読み直して計算 | いまディスクにある内容。第7段（ソースの読み直し）は**この同じ内容**を構文解析する |

版はすべて同じ規則: ファイルの内容（UTF-8）の sha1 の先頭16桁（`transform.cjs` の `sourceRevision` と `anchors.ts` の `sourceRevision`。単体テストで同じ値になることを確かめている）。内容のハッシュなので、DOM からソースは復元できない。

### 3.2 照合の段（6段 → 7段）

`resolveSelection` は、要素自身の識別子について次をすべて満たしたときだけ位置を出す。

1. この要素自身に識別子が付いていた
2. いま実行中の開発サーバーの対応表にその識別子がある
3. 対応表のファイルが注入範囲（`src/`）の中にある
4. 識別子を (ファイル:行:列) から計算し直すと一致する
5. **（新）DOM の版 = いまのファイルの版、かつ 対応表の版 = いまのファイルの版**。DOM の版が無い・対応表の版が無いときは照合できないので止める
6. DOM のタグと対応表のタグが一致する
7. ソースを読み直し（**5 で版を計算したのと同じ内容**）、その位置に同じタグの JSX があり、囲むコンポーネントが一致する

祖先（包含関係の文脈）も同じ照合を通ったものだけを使う。版の古い祖先は文脈に入れない。

「ファイルのハッシュを足しただけ」で終わらせなかった点:

- **対応表とファイルの版の一致だけでは、経路 (a) を防げない。** HMR の再コンパイル後は対応表もファイルも新しい版で揃うので、古い DOM の識別子がそのまま新しい要素に照合される。DOM が自分の版を持ち、IDE がそれを照合することが要る。
- 版の計算と構文解析が別々にファイルを読むと、その間の書き換えで取り違える。1回だけ読み、その内容で版と索引を作る。索引のキャッシュも、更新時刻・大きさではなく内容の版で引く（同じ大きさ・同じ時刻の書き換えを取り違えないことを単体テストで確かめた）。

### 3.3 通信

- 選択の知らせに `anchorRev`（要素自身の版、無ければ null）と `ancestorRevs`（祖先ごとの版、`ancestorAnchors` と同じ長さ）を足し、**通信の版を 2 → 3** にした。版 2 の知らせ・版のキーを持たない選択は受けない（既存の検査を弱めていない。知らないキーを捨てる・nonce・送り主の origin・起動の鍵の検査はそのまま）。
- 送るのは内容のハッシュだけで、ソース・ページの本文・属性の値は送らない（`select-e2e` の「知らせのキーは決めたものだけ」に2つのキーを足して確かめている）。

### 3.4 選択の後の確かめ（画面）

- 選択を解決したとき、**照合に使ったファイルと版**（選んだ要素のファイルと、照合に通った祖先のファイル）を覚える。
- 解決済みの選択がある間、1.5 秒ごとに `POST /api/runtime/source-revisions`（いまの起動の鍵とファイルの一覧）で、いまの版を取り直す。違えば・読めなければ無効にする。API は注入範囲の `.tsx`/`.jsx` だけを受け、ハッシュだけを返す。変更操作と同じ入口の検査（POST・JSON・独自ヘッダ・同一オリジン）と、いまの起動でなければ 409 を返す検査を `anchor` の API と同じに持つ。
- 由来の評価（`/api/runtime/lineage`）はサーバーが要素をもう一度照合するので、その照合が**同じ要素・同じ版**でなければ、評価を使わず無効にする。
- 無効にするとき: 選択の通し番号を進め（待っている解決・由来の評価・版の確かめの応答を捨てる）、右ドック・キャンバスの前の要素の情報、文書の同定と由来の評価、プレビューの中の選択枠を消す。

### 3.5 古い応答が後から届く場合

既存の「選択の通し番号」と「起動の鍵」の照合（7B-2・7B-3B-2）をそのまま使い、新しい版の確かめにも同じ照合を入れた。遅れて届いた古い解決・古い由来の評価・前の選択の「変わった」という確かめは、新しい選択・解除後・停止後・再起動後の状態を上書きしない（第5節 e2e の 5・6・9）。

## 4. 無効化する範囲と、その理由

| 単位 | 採用 | 理由 |
| --- | --- | --- |
| 選んだ要素の JSX があるファイル | **無効にする**（コメントだけの変更でも） | 識別子は位置だけから決まる。内容が変わった後に「同じ位置の同じ要素だ」と言う根拠は位置しか無く、位置で同一性を補わない（推測しない）。内容が完全に同じに戻れば版も同じなので、また特定できる |
| 照合に通った祖先のファイル | **無効にする** | 右ドックの包含関係（`A ← B`）は祖先の照合から作っている。祖先のファイルが変われば、その文脈は確かめていない情報になる |
| それ以外のファイル | **無効にしない** | 選択の位置・コンポーネント・包含関係の根拠に使っていない。無関係な変更のたびに選び直させると、試用で「勝手に選択が消える」になる。実ブラウザで、無関係なファイルの変更後も選択が保たれることを確かめた |
| 開発サーバーの停止・再起動 | 従来どおり解除する | 7B-2 のまま |

ファイル単位を選んだので、同じファイルの中の無関係な変更（コメント・別のコンポーネント）でも選び直しになる。これは保守的な側に倒した結果で、要素単位の同一性（位置に依らない照合）は大きな設計変更になるため今回は入れていない。

**値の由来（`supplies`）が依存するファイル**（データ取得の呼び出し・SQL を書いたファイルなど）はこの単位に入れていない。由来の評価は 7B-3B-2 の仕組み（評価の時点で静的解析と実測を照合し、実行の後に書き換わったものは使わない）に任せており、F-01（要素の同一性）とは別の問題である（第6.2節）。

## 6. 防げるケースと残る限界

### 6.1 防げるもの

- 古い DOM（HMR の前・HMR の失敗・読み込み直していないプレビュー）から来た選択を、同じ位置の新しい要素として特定すること
- 解決の要求の途中でソースが変わったときの誤対応
- 対応表がソースより古い・新しいときに、対応表の位置を使うこと
- 選択の後にコードが変わったとき、前の要素の位置・ソース行・コンポーネント・包含関係・由来の評価を、現在の情報として出し続けること
- 遅れて届いた古い解決・由来の評価・版の確かめが、新しい選択や解除・停止・再起動の後の状態を上書きすること

### 6.2 残る限界

| 限界 | 内容 |
| --- | --- |
| 確かめの間隔 | 選択の後のファイルの変更は、最長で約 1.5 秒（＋要求の時間）のあいだ前の情報のまま出る。その間に新しくクリックした場合は、クリックの照合（第3.2節）で止まる |
| 無効化の粒度 | ファイル単位。同じファイルの無関係な変更（コメント・別のコンポーネント）でも選び直しになる |
| 由来が依存するファイル | 値の由来（`supplies`）の評価が使う別のファイル（データ取得の呼び出し・SQL）の変更では選択を無効にしない（7B-3B-2 の仕組みに任せている）。由来の結び付け（`linked`）の状態での新しい照合は、このコンテナで `lineage-e2e` が修正前から通らないため、実ブラウザでは確かめていない（切れた状態での照合は確かめた） |
| 識別子が消えた場合の理由 | 古い DOM の識別子がもう対応表に無い（その位置に JSX が無くなった）ときは `anchor-not-in-manifest` になる。どのファイルの識別子か分からないため `source-changed` とは言えない。説明文に「コードが変更される前の表示から来た識別子」も含めた |
| ローダの前の変換 | 版は「ローダに渡された内容 = ディスクの内容」を前提にする。対象の設定で注入のローダより前に別のローダが内容を変えると、版がつねに合わず、すべて `source-changed` になる（誤対応ではなく、特定できない側に倒れる）。確かめたのは Turbopack（Next 16.4.3）の題材だけで、webpack では今回回していない |
| 以前の変換のキャッシュ | 本修正の前に作られた Turbopack のキャッシュから描かれた要素には版が無く、`revision-missing` になる（ファイルを保存し直せばそのファイルの要素には付く）。この状態は実際には再現していない（未検証） |
| 版の衝突 | sha1 の先頭 64 ビット。内容の違う2つの版が同じ値になる確率は無視できるが、0 ではない |
| アプリによる偽装 | ページのスクリプトは `data-vcide`・`data-vcide-rev` を書き換えられる（7B-2 からの信頼の前提と同じ）。いまの版を古い要素に付け替えるアプリの悪意には対処しない |
| DOM の大きさ | 識別子を付ける要素ごとに約 35 バイトの属性が増える |
| 実際の環境 | 実物の Codespaces・利用者の実在プロジェクトでは確かめていない（7B-2 と同じ） |

1. **`lineage-e2e` がこのコンテナで修正前から通らない**（由来が「この文書の通信で SQL を観測していません」で切れる）。7C-3 の記録では通っていたので、環境（計装・タイミング）か題材の依存のどちらが原因かを、本修正とは別に確かめる。それまでは、由来を結んだ状態での F-01 の照合（第3.4節の由来の評価の照合）は実ブラウザで確かめていない。

4. 06h レビューの 7 節「探索側へ持ち帰ること」のうち、F-01 は本書で対処した。06h レビューの記録・判定は書き換えていない（本書から参照するだけ）。
