## 1. 実装した機能

### 1.1 体験

```
① 開発サーバーを起動（7A のまま）→ プレビューに実ページ（7B-1 のまま）
② プレビューのバーの［選択］を押す（選択モード。プレビューの中のクリックはページを操作しない）
③ 実ページの要素をクリック
④ パネルの1行:  選択: <span> → RegionBadge  src/components/RegionBadge.tsx:8:7
   右ドック   :  ① 表示された値 ─renders→ ② コンポーネント（実測）
                 位置（行・列）／JSX の1行／包含関係／'use client' の有無／特定方法／照合の根拠／主張の範囲
   キャンバス :  同じ ①② と「ここから先は観測していません（props の由来）」の切断
⑤ 特定できない要素（ライブラリ由来・JSX を経ない DOM・body など）:
   パネル  :  選択: <h3> — 特定できません（この要素自身に要素識別子がありません）

⑥［解除］か開発サーバーの停止で、ページを開いたときのデータセット（合成・記録）に戻る
```

### 1.2 構成

```
ブラウザ（IDE の画面, origin A）                         プレビューの iframe（中継, origin B）
  LivePreview                                            agent.js（中継が <head> の先頭に差し込む）
    ├─ window 'message' ← hello（中身なし）──────────────  P.postMessage(hello, ancestorOrigins[0] | '*')
    ├─ win.postMessage(connect+nonce, B, [port2]) ───────→ 最初に登録したリスナーが受け取り、
    │                                                      stopImmediatePropagation（アプリに渡さない）
    ├─ port1 ←───────────── connected / 場所 / 選択 ─────  port2（以後はこれだけ）
    └─ POST /api/runtime/anchor { run, selection }         選択 = 識別子・タグ・何番目か・文字数と文字種・パス
         └─ anchors.ts: 対応表 → 6段の照合 → 位置 or 理由
    └─ adapter.fromLiveSelection → layout → ExploreStore.showLive → 既存のキャンバスと右ドック
```

**位置は iframe から受け取らない。** iframe が送るのは識別子だけで、位置は IDE が自分の対応表とソースの読み直しで決める。

### 1.3 識別子の注入を実ページに届ける

- 起動時に対象の `next.config.*` が `POC03_ANCHOR` を読む設定かを調べ（`anchorSupport`）、そうなら
  `POC03_ANCHOR=1` と `POC03_ANCHOR_OUT=<IDE>/.ide-runtime/anchors/<プロジェクトの sha1>` を起動先に足す。
  **7B-1 の許可リストは変えていない**（IDE が作る値を足すだけで、IDE のプロセスの環境変数を通すわけではない）
- **対象の next.config は書き換えない**（7A の方針）。設定が無いプロジェクトは `anchors.state = unavailable` とし、
  選択すると「このプロジェクトでは要素識別子を注入していません」と理由を出す
- 対応表の置き場所は**起動をまたいで同じ**にした。Turbopack は変換結果を対象の `.next` にキャッシュするので、
  起動ごとに置き場所を変えると、キャッシュに当たったファイルではローダが走らず対応表が空になる。
  識別子は位置から決まるので、ソースが同じなら対応表も同じである。古い記述が残っても、第3節の照合で現在のソースと合わないものは出さない

## 5. 誤特定を防ぐ仕組み

位置として出すのは、次の **6段をすべて通ったとき**だけである（`anchors.ts`）。1つでも欠ければ「特定できません」と理由を返す。

| 段 | 照合 | 落ちたときの理由 |
| --- | --- | --- |
| 1 | **この要素自身**に識別子が付いている（祖先へは遡らない） | `anchor-missing` |
| 2 | 識別子が、いまの起動のビルドが書いた対応表にある | `anchor-not-in-manifest` |
| 3 | 対応表のファイルが注入範囲（`src/`）の中にある（`..`・絶対パス・`node_modules`・**シンボリックリンクで外へ出るもの**を拒否） | `outside-scope` |
| 4 | 識別子を「ファイル:行:列」から計算し直すと一致する | `id-mismatch` |
| 5 | DOM のタグと対応表のタグが一致する | `tag-mismatch` |
| 6 | **ソースを読み直し**、その位置に同じタグの JSX があり、囲むコンポーネントが一致する | `source-mismatch` |

加えて:

- **選択の解決の前に起動を照合する。** 要求は「どの起動のページで選んだか」（instance・PID・開始時刻）を持ち、いまの起動と違えば 409（`stale-run`）
- **知らせの形を検査し、知らないキーは捨てる。** 位置（`file` / `line`）を選択に書いて送っても 400 で拒否する
- **包含関係は照合を通った祖先だけで作る**
- 照合器（typescript）を読み込めないときは**照合しないまま出さない**（`verifier-unavailable`）
- 単体（第7.1節）で、ソースを1行ずらす・タグを変える・コンポーネント名を変える・対応表を書き換える・リンクで外を指す、の各場合に止まることを確かめた

## 6. 通信の安全性

| 指示 | 実装 | 検証 |
| --- | --- | --- |
| 送信先の origin を明示し、無条件の `*` を避ける | IDE → iframe の `connect` は**中継の origin を宛先に明示**。iframe → IDE は最初の `hello` だけが window 経由で、宛先は `location.ancestorOrigins[0]`（Chrome / Safari）。それが使えないブラウザ（Firefox）だけ `'*'` だが、**`hello` は中身を持たない**。以後の知らせはすべて MessagePort（宛先が1つに決まっている）。許可していない親の下に埋め込まれていると分かれば `hello` も送らない | 単体（`postMessage(` は2か所だけで、`'*'` になりうるのは中身の無い `hello`） |
| 受信側で `event.origin` と `event.source` を検証 | IDE: `hello` は `e.origin === 中継の origin` かつ `e.source === この iframe の window` のときだけ。スクリプト: `connect` は `e.source === parent` かつ origin が IDE の画面として許した範囲（`frame-ancestors` と同じ表）のときだけ | E2E 第5節 |
| 型・版・内容の検証 | `previewProtocol.ts`。版 2・種別の許可リスト・nonce の一致・**知らないキーがあれば捨てる**・識別子は16進10桁・パスは `/` 始まりで `//` を拒否・数の範囲・フォームの部品に値の形があれば矛盾として捨てる。サーバーの API も同じ検査をもう一度行う | 単体 第1節（23件）/ E2E 第5節 |
| 古いページ・終了したプロセスからの選択を無視 | (1) 接続は iframe の文書ごとに作り直し、**いまの接続の port の知らせだけ**を受ける (2) 接続ごとに起動の鍵（instance:PID:ポート）を持ち、違えば捨てる (3) 停止・再起動で接続を閉じ、選択を解除し、待っている解決の返事も捨てる (4) API は起動を照合して 409 | E2E 第7節 |
| iframe 内のアプリ自身が偽装できる可能性 | 下の表 | E2E 第5節 |
| 受信したソース位置を無条件に信用しない | **位置は受け取らない。** 識別子だけを受け取り、IDE の対応表とソースの読み直しで決める（第5節） | E2E 第5節 (e) |
| 停止したら選択も実態と矛盾させない | 停止・異常終了・再起動で選択を解除し「選択を解除しました」と書く。キャンバスと右ドックは元のデータセットに戻る。停止中の解決は 409 | E2E 第7節 |

### 6.1 iframe の中のアプリが偽る場合

アプリのスクリプトは中継のスクリプトと同じ文書・同じ JavaScript の世界で動く。完全には隔離できない前提で、次のように狭めた。

| アプリができること | 結果 |
| --- | --- |
| `parent.postMessage` で選択や場所の知らせを偽る | **受けない。** window 経由で受けるのは `hello` だけ。偽った知らせは数えて捨てる（E2E (a)） |
| `hello` を偽って、IDE が返す port を横取りする | **できない。** 中継のスクリプトは `<head>` の最初で動き、最初に登録したリスナーで `connect` を受けて `stopImmediatePropagation` する。アプリのリスナーには届かない（E2E (b)）。IDE は新しい接続を、相手が答えるまで今の接続と入れ替えないので、偽った `hello` で今の接続が切れることもない |
| `element.click()` や `dispatchEvent` で選択を起こす | **選ばない。** 利用者の本物のクリック（`isTrusted`）だけ（E2E (c)） |
| 後から `Element.prototype.getAttribute` などを書き換える | スクリプトは主な関数（`getAttribute` / `querySelectorAll` / `getBoundingClientRect` / `addEventListener`）を先に取っておく。`location` や `history` など、それ以外への書き換えまでは防いでいない |
| DOM の `data-vcide` を書き換える（別の要素の識別子を付ける） | タグが違えば第5段で止まる（E2E (d)）。存在しない識別子は第2段で止まる。**同じタグの別の JSX の識別子に付け替えた場合は、その JSX の位置を指してしまう**（残る制約1） |
| IDE の解決の API を直接呼ぶ | 別 origin なので入口の検査で止まる（E2E (e)） |

## 9. データ保護・セキュリティ上の制約

| 対象 | 扱い |
| --- | --- |
| DOM の本文・属性 | 読まない。スクリプトが読むのは選んだ要素の `data-vcide`・タグ名・祖先の `data-vcide`・直下のテキストノードの**長さと文字種**だけ（`innerHTML` / `textContent` / `innerText` / 属性一覧を使わない — 単体で検査） |
| フォームの入力値 | 読まない。`input` / `textarea` / `select` / `option` / `button` / 編集可能な要素は値の形も取らない |
| Cookie / localStorage / トークン | 触れない（E2E で印を入れて、送られないことを確認） |
| ソースコード | 照合した JSX の1行だけを右ドックに出す（PoC-03 と同じ）。全文は持たない |
| 絶対パス | 画面・状態 API に出さない（対応表の置き場所も出さない — E2E で確認）。位置はプロジェクトルートからの相対パス |

**残る制約**

1. **アプリが DOM の `data-vcide` を、同じタグの別の JSX の識別子に書き換えた場合**、その JSX の位置を指す。識別子はアプリの DOM の一部なので、アプリ自身が書き換えることは防げない。
   照合により「存在する JSX の位置」以外は指さない（任意の位置・プロジェクト外は指せない）
2. 選択モードの間、スクリプトは捕捉段階でポインタ・クリックのイベントを止める。アプリが `window` に捕捉段階のリスナーを先に置くことはできないが（スクリプトが `<head>` の最初で動く）、
   `document` やより内側の要素での処理の順序には依存しない設計にしている
3. 選んだ要素の枠（オーバーレイの `div`）は `<html>` の直下に足す。選択モードを切ると取り除く。アプリの DOM を数える処理があれば影響しうる
4. 対象のアプリの CSP が `'self'` のスクリプトを許さない場合、スクリプトは動かず選択できない（7B-1 と同じ）
5. 対応表は対象プロジェクトのビルド（＝利用者のコード）が書く。形を検査し、6段の照合を通ったものだけを使うが、「存在する JSX の位置」の範囲で誤った対応を書かれる可能性はある（第4段で識別子と位置の対応は崩せない）
6. 注入は開発ビルド限定・`next.config` にローダの設定が要る（PoC-03 の条件と同じ）。IDE は設定を書き換えない
