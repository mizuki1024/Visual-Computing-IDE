### 3.4 適用前プレビュー（EP-12） — **方式 A: 条件付き成功**、**方式 B: 条件付きで成立（比較実験のみ）**

| 方式 | 中身 | 結果 | 限界 |
| --- | --- | --- | --- |
| **A. 予測の重ね合わせ（今回使った方式）** | 題材の Tailwind で**変更後の className の token をすべて**コンパイルし、utilities の規則だけを「予測の印が付いた要素」に限って layer の外に足す。対象要素の `p-4` を `p-5` に差し替える。`md:p-6` も同じ順序で出すので、上書きの順序は Tailwind のまま | 下書きの間ソースは不変（E12）。予測の計算済み padding は Mobile 20px・Desktop 24px（E13）。見出しは斜線地＋「▨ 適用前プレビュー（予測）· 下書き 1件を反映」、Desktop は「この幅は変化なし（予測）」（E13、画面 02）。計測値にも `predicted: true` が付く | React のコードを実行した結果ではない（DOM と CSS の予測）。JS で決まる描画・要素の増減・条件で変わるクラスは予測できない。React が持つ DOM を書き換えるので、予測中に再描画が起きると予測が外れうる（「ページを操作」に入ると予測を外す — 04e 4.2）。ページで未使用の token は CSS が無いので、IDE 側でコンパイルが要る（今回はした） |

## 7. 製品実装へ進む前の残条件

1. **探索トラックの着手条件**: M2 の達成（`07c0` P2-9 の #8・#9）と、A群の完成後のユーザーテスト（`01c` 1.4節・2.2節）。編集の実装はその結果を受けて B群の順序を決めてから（`02e` 1.7 ED-09、`02f` CP-02）。
2. **方式の決定（EP-12）**: 方式 A（軽い・予測）と方式 B（実描画・起動 7 秒・メモリ約 2 倍・ハードリンクの写しが要る）のどちらを、どの条件で使うか。B を採るなら、写しの作り方（Turbopack が root の外のシンボリックリンクを解決しない）・下書きを変えるたびの反映時間・DB や環境変数への依存の扱いを追加で検証する。
3. **利用箇所の検出（EP-04）**: 注入の対応表はコンパイルしたページの分しか無い。製品では静的走査（import の解決を含む）を別に持つ必要がある。
4. **注入の有効化（EP-09）**: 本 PoC は題材の `next.config` が注入ローダを読む前提。利用者のプロジェクトでは P1-3 が残る。
5. **複数ファイルの適用（EP-06）**: 同時更新は保証できない。製品の初期範囲は1ファイルずつに制限するか、3.8 節の状態表示を必須にする。
6. **選択の識別子（EP-01）**: 行・列が変わる編集（文言・要素の追加）を初期範囲に入れるなら、位置に依らない識別の検証が要る。
7. **規模**: 実案件の規模での版の計算・HMR の時間・利用箇所の走査、2つ以上の開発サーバー（方式 B）の負荷。
8. **製品のプロトコルへの統合**: 矩形・計算済みスタイル・予測の知らせを製品の `previewProtocol` に足す場合、今回の検査（nonce・起動インスタンス・知らないキーの破棄・アートボードごとの接続）を同じ強さで入れ、既存の試験（`select-e2e` 等）を回す。

## 8. 再実行の方法

```bash
npm ci
(cd poc/fixture-edit && npm ci)
npm run poc:edit:unit        # 単体（題材を書き換えない）
npm run poc:edit:e2e         # 実ブラウザ（ハーネスを自分で起動。題材は最後に必ず元へ戻して一致を確認）
npm run poc:edit:method-b    # 方式 B の比較実験（NM=symlink で 1 回目の失敗を再現）
npm run poc:edit             # 手で触るとき: http://127.0.0.1:3262 （POC_EDIT_FAULTS=1 で試験用の故障 API）
```

ポート 3260〜3262（方式 B は 3270）が空いていること。e2e は Chrome を `/opt/pw-browsers/chromium` から起動する（`PW_EXECUTABLE` で変更）。ハーネスは使用中のポートでは起動しない（古い開発サーバーと話さないため）。
