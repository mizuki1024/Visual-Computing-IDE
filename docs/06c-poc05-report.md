## 1. 採用した関連付け方式

### 1.1 3種類の関連を、別々の方式で、別々に判定した

| | 関連 | 採用した根拠 | 判定 |
| --- | --- | --- | --- |
| **A** | ブラウザHTTP ↔ サーバーHTTP | **応答ヘッダに載せ返したトレース識別子の一致**（`trace-context`） | **成功** |
| **B** | Reactコンポーネント ↔ HTTP | **ブラウザが要求を送る時点で記録した呼び出しスタック**を、ソースマップで元の位置へ戻し、ソース行を読み直して照合（`request-initiator`） | **条件付き成功** |
| **C** | HTTPレスポンス ↔ 表示値 | **実施しない。** 応答本文も表示値も収集しないため、対応づける材料を持たない | **対象外**（成功扱いにしていない） |

**A が成立しても B・C を成功扱いにしていない。** モデル上も、A の `handles`、B の `requests` は
別々のホップであり、C にあたる `derives` / `maps` は**ホップ自体を作っていない**。

### 1.2 A の方式 — 伝播ではなく「応答側」で対応付ける

ブラウザ側に計装を入れない（`01b` Q-01.0 (a) 非改変）ため、**要求に `traceparent` を載せられない**。
実測でも、サーバー側の入口スパン30本は**すべて根スパン**であり、ブラウザからトレースコンテキストが
届いた形跡は1件も無い（第3章 #1）。したがって対応付けは応答側で行う。

```
ブラウザ ──要求（traceparent なし）──▶ サーバー
                                        └ 入口スパン（根）を作る
ブラウザ ◀──応答（X-Vcide-Trace: 00-<traceId>-<spanId>-01）── サーバー
   │
   └ IDE が CDP で、この応答の requestId とヘッダを同時に受け取る
     → 「このブラウザ内要求」と「このサーバースパン」が結びつく
```

対応付けの成立条件（**1つでも欠けたら対応付けない**。`poc/runner/lib/correlate.mjs`）:

| # | 条件 | 役割 |
| --- | --- | --- |
| 1 | 応答ヘッダから識別子を読めている | **判断の根拠** |
| 2 | その `spanId` のスパンを収集できている | 判断の根拠 |
| 3 | `traceId` も一致する | 判断の根拠 |
| 4 | そのスパンがサーバー側の入口スパンである | 判断の根拠 |
| 5 | メソッドとパスが食い違わない | **補強のみ。これだけでは対応付けない**（食い違えば捨てる） |

> **時刻は記録するが、判断には一切使っていない。** 時間窓による対応付けは
> 「比べるため」に別の関数として実装し、**それでは絞れない場面が実在すること**を数字で示した（第3.3節）。

### 1.3 どのヘッダで返すか — `Server-Timing` から専用ヘッダへ

PoC-01 は `Server-Timing` を使った。本PoCで**公開範囲が広すぎる**ことが実測で分かったため、
専用ヘッダ `X-Vcide-Trace` を足し、IDE 側はそちらを優先して読む（両方読めた場合の一致も検査している）。

| | `Server-Timing` | `X-Vcide-Trace`（専用） |
| --- | --- | --- |
| IDE（CDP）から読めるか | 読める | 読める |
| **ページ上の任意のスクリプトから読めるか** | **読める**（Resource Timing API の `serverTiming`。同一オリジンの**全リソース**について） | **読めない**（Resource Timing API に出ない） |
| クロスオリジンの応答で、ページから読めるか | 読めない（`Timing-Allow-Origin` 未設定） | 読めない（`Access-Control-Expose-Headers` 未設定） |

さらに、**宛先がループバック以外のホストなら、どちらのヘッダも付けない**ようにした
（`poc/fixture-app/ide-instrumentation/otel.cjs`）。開発用の識別子が外部へ出る経路を、
出す側で閉じている。

### 1.4 B の方式 — 「開始したコード」の証拠を4段で確かめる

```
① CDP が記録した initiator.stack（ブラウザ自身が、要求を作った時点で取った呼び出しスタック）
      ↓  上から順に、アプリのスクリプトのフレームを探す
② そのフレームをソースマップで元の位置へ戻す      → src/app/flows/page.tsx:30:23
      ↓
③ そのソース行を読み直し、本当に通信の呼び出しがあるかを確かめる
      ↓                                        → const res = await fetch('/api/listings', …)
④ その行を囲むコンポーネントを、**2つの独立した情報源**で決める
      ソースの読み直し（TypeScript で再解析） ＝ Flows
      ビルド時マニフェストの関数範囲           ＝ Flows      → 一致したときだけ採用
```

**4つが揃わなければ、ノードも関係も作らない。** 理由を付けて「特定していません」と返す
（`no-script-stack` / `no-app-frame` / `source-line-mismatch` / `component-not-agreed`）。

> **DOM 上の近さも、発生時刻の近さも、根拠に使っていない。**
> 「画面のこの要素の近くで、この時刻に通信が起きた」は、本PoCの対応付けに一度も現れない。

## 3. 観測できなかったこと（作らなかった関係）

**ここに挙げたものは、画面にも変換結果にも存在しない。** 代わりの値で埋めていない。

| # | 取れなかったもの | 実測した理由 | 画面での扱い |
| --- | --- | --- | --- |
| 1 | **ブラウザ → サーバーのトレース伝播** | ブラウザ側に計装を入れないため、要求に `traceparent` を載せていない。**入口スパン30本がすべて根**であることが裏づけである | 対応付けは応答側で行う。伝播があるかのように書かない |
| 2 | **Server Component がサーバー内部で行った通信の相手** | `fetch GET http://…/api/listings` のスパンは観測できる。しかし Next.js の `fetch` は `node:http` を通らず、要求にトレースコンテキストが載らない。**受け側のハンドラは別トレースの根**になる | 同一と主張しない。ノードも関係も作らない |
| 3 | **応答が返らなかった通信のサーバー側** | 識別子は応答ヘッダから読む。応答が無ければ読めない | 対応付けない。理由（`no-identity-in-response`）を残す |
| 4 | **文書取得・RSCペイロードの呼び出し元** | ブラウザは「スクリプトが起点でない要求」の呼び出しスタックを記録しない（`initiator.type = other`） | `requests` を作らない。理由（`no-script-stack`）を残す |
| 5 | **`derives`（応答の項目 → 表示値）** | 応答本文を読む必要があり、収集禁止項目にあたる。`02a` 3.5.1 により構造的に推定 | **コンポーネントから切断マーカー** |
| 6 | **`maps`（カラム → 応答項目）** | 同上（PoC-01 / PoC-03 と同じ判断） | 作らない |
| 7 | **どの DOM 要素が、どの通信の応答で描かれたか** | B が答えるのは「誰が通信を**始めた**か」までである | ②（描いた）と ②'（始めた）を**別のノード**にし、間に線を引かない |

### 3.1 A と B は繋がっているが、「値の出所」は繋がっていない

```
 ① 表示された値 ──renders──▶ ② コンポーネント(RegionBadge)
                                  ✕── ここから先は観測していません（props の由来）

 ②' コンポーネント(Flows) ──requests──▶ ③ 通信 ──handles──▶ ④ サーバー処理
                                                              └─executes─▶ ⑤ 実行SQL
                                                                   ├─reads────▶ ⑥ テーブル
                                                                   └─projects─▶ ⑦ カラム ×3
```

**② と ②' の間に線は無い。** 同じページのコンポーネントどうしだが、
「描いた」と「通信を始めた」をつなぐ証拠は得ていない。繋ぐと `derives` を実測に格上げすることになる。

### 3.2 「時刻が近い」では決められないことの実測

| 対応付けの規則 | 候補が2件以上になった通信 | 識別情報が無いのに候補が出た通信 | 識別子の答えと食い違った |
| --- | --- | --- | --- |
| **識別子の一致（採用）** | **0 件** | — | — |
| メソッドとパスの一致だけ | **23 / 28 件** | — | — |
| メソッド・パス + 時間の重なり | **3 件**（同一URL同時実行の3件） | **1 件**（中断した通信） | 0 件 |

- **同じURLへの同時実行では、時間窓は3件とも「候補3件」になり、1件に絞れない。**
- **中断した通信は、時間窓なら候補が1件出る。**「1件に絞れた」ように見えるが、
  その通信の応答はブラウザに返っていない。**時間窓は「対応付けてはいけない通信」を対応付ける。**
- 時間窓が1件に絞れた場面で、識別子の答えと食い違ったことは無かった。
  **時間窓はいつも間違うのではなく、間違うときに間違ったと分からない。** これが採らない理由である。

## 4. Reactコンポーネントとの関連付け（B）の結果

### 4.1 成立した範囲

| 計測 | Turbopack | webpack |
| --- | --- | --- |
| 操作で起きた通信 | 15 | 15 |
| 呼び出し元を解決できた | **15 / 15** | **15 / 15** |
| ソースの読み直しで照合できた | **15 / 15** | **15 / 15** |
| 2つの情報源でコンポーネントが一致した | **15 / 15** | **15 / 15** |
| 期待した位置（手書きの正解表）と一致 | **15 / 15・誤答 0** | **15 / 15・誤答 0** |

- **同じ関数の中の別々の行**（`Promise.all` の3行）まで区別できた。
- **ページではなく子コンポーネント**（`FetchButton`）を指した。親を誤って指していない。
- **バンドラ差を解消した。** webpack は生成物が `webpack-internal:///…` の eval されたモジュールで、
  HTTP では取得できない。CDP の `Debugger.getScriptSource` で中身を引き、
  インラインのソースマップを解くことで、Turbopack と同じ精度になった。
  `06b` 2.4節で「webpack は行を解けない」としていた制約は、**この経路では解消した**。

### 4.2 成立しなかった範囲

| 対象 | 振る舞い | 評価 |

| サーバー内部の `fetch`（RSC） | ブラウザに記録が無いので B の対象外 | 第3章 #2 |

### 4.3 B が主張していること / していないこと

| 主張する | 主張しない |
| --- | --- |
| この通信を開始したのは、この**ソース位置のコード**である | この通信の応答が、画面のどの値になったか |
| その位置を囲むコンポーネントは、この**関数**である | このコンポーネントが描いた DOM 要素と、この通信の関係 |
| — | 同じコンポーネントが複数回描かれたとき、**どのインスタンス**が始めたか |

### 6.1 識別子そのものの機密性と、公開範囲（指示 第5節）

識別子（`traceId` / `spanId`）は乱数であり、それ自体に意味は無い。
**問題は値ではなく、誰が読めるかである。** 実測した。

| 読み手 | `Server-Timing` | `X-Vcide-Trace`（専用） |
| --- | --- | --- |
| IDE（CDP） | 読める | 読める |
| **同一オリジンのページ上の任意のスクリプト**（広告・計測タグ・第三者ライブラリを含む） | **読める。** Resource Timing API の `serverTiming` に出る。**自分が出した通信でなくても、同一オリジンの全リソースについて読める** | **読めない。** Resource Timing API には出ない |
| クロスオリジンのページ上のスクリプト | 読めない（`Timing-Allow-Origin` を付けていない） | 読めない（`Access-Control-Expose-Headers` を付けていない） |

実測値（1バンドラあたり）: 同一オリジンのリソース記録のうち `serverTiming` に `traceparent` が
見えたもの **1件**（その実行で起きた API 通信の全件）。専用ヘッダが見えたもの **0件**。
クロスオリジンの応答では、ページ上のスクリプトは**どちらのヘッダも読めず**、
IDE（CDP）からは**読めた**。

**結論と対処**

| # | 分かったこと | 対処 |
| --- | --- | --- |
| 1 | `Server-Timing` は、**ページ上の任意のスクリプトに、同一オリジンの全通信のトレースIDを配る** | **IDE は `Server-Timing` を必要としない**（CDP で応答ヘッダを直接読める）。専用ヘッダに寄せる |
| 2 | 専用ヘッダは、その要求を自分で出したコードからは読めてしまう（同一オリジンの `fetch` は全ヘッダを読める） | 識別子は乱数であり、アプリ自身のコードに渡っても害は無い。**第三者スクリプトへの一斉公開**（1 の経路）とは危険度が違う |
| 3 | 意図しない外部公開 | **ループバック以外のホスト宛には、どちらのヘッダも付けない**ようにした。製品では「開発モードのみ・明示的に有効化」も要る |
| 4 | クロスオリジン | ヘッダはページに読まれないが、**ネットワーク上には流れる**。1〜3 の対処で十分かは、プレビューのオリジン設計（`06a` F-4）と合わせて決める必要がある |

### 7.3 増分の内訳 — 「解析器の読み込みがほぼ全部」は Turbopack でしか成り立たない

| 増分の分解（冷えた状態・初回コンパイル） | Turbopack | webpack |
| --- | --- | --- |
| ローダを1本挟むこと自体 | **+41 ms** | **+8 ms** |
| 注入そのもの（`noop` → `on`） | **+190 ms** | **+1059 ms** |
| うち、ローダが実際に払ったと記録した時間<br/>（解析器 146 ms + 変換 約16 ms） | 約 163 ms | 約 163 ms |
| **説明できない残り** | **約 27 ms** | **約 896 ms** |

1. **起動時間への影響はほぼ無い**（Turbopack +0.5%）。webpack は +6.6% だが、
   `noop` でも同程度増えており、ローダを挟むこと自体の影響である。
2. **Turbopack では、`06b` 2.5節の見立てが裏づけられた。** 増分 190 ms のうち約 163 ms が
   「ワーカー1個あたり1回の解析器読み込み（146 ms）＋ そのプロセスでの初回変換（8.9 ms）＋
   その起動で実際に走った変換（平均 16.5 ms / 起動）」で説明できる。
3. **webpack では裏づけられなかった。** ローダ自身が記録した時間は Turbopack と同じ約 163 ms
   なのに、増分は 1059 ms ある。**約 900 ms は、変換の処理時間でも解析器の読み込みでもない。**
   `06b` 2.5節の「増分のほぼ全部は1回限りの読み込みコストである」は、
   **webpack については誤りである。本報告で訂正する。**
   原因は未特定である（ローダが**内容を書き換える**ことで webpack 側のどの経路が変わるのかは、
   この計測では切り分けられていない）。推測を書かない。
4. **再コンパイルの増分は、バンドラで大きく違う。** Turbopack は +5 ms。
   webpack は冷えた状態で +501 ms、**キャッシュが残っていれば +14 ms**。
5. **ビルドのキャッシュが残っていると、webpack の増分はほぼ消える**（+2.3%）。
   キャッシュが効いている間、ローダは呼ばれない。Turbopack は +30.0% のままで、
   起動のたびに同じ固定費を払っている。
6. **遅延初期化・先読みの余地はある。** 解析器の読み込みはワーカー起動時に先読みでき、
   変換そのものは 1ファイル 0.04〜0.5 ms である。**軽量な JSX スキャナへ置き換える必要は、
   少なくとも Turbopack では無い。** webpack の約 900 ms は原因が未特定なので、
   置き換えで直るとは言えない。本PoCでは**最適化していない**
   （PoC-03 の精度と安全性を下げないため。計測用の記録も環境変数で切り替えてある）。

### 7.4 「+30% 以内」という基準の再評価

| 論点 | 内容 |
| --- | --- |
| **分母が小さすぎる** | 題材はページ7枚・コンポーネント2個である。初回コンパイルは 0.8〜1.1 秒であり、**ワーカー1個あたりの固定費 150 ms が 15〜20% を占める**。実プロジェクトでは分母が大きくなり、同じ固定費の割合は下がる |
| **固定費と変動費が混ざっている** | 増分の主は「ワーカーあたり1回」の固定費であり、ファイル数に比例しない。**割合で測ると、小さいプロジェクトほど悪く見える** |
| **測る対象が1回限りである** | ルートの初回コンパイルは dev server の生涯で1回。開発中の体感を決めるのは再コンパイル（Turbopack +5 ms / webpack キャッシュあり +14 ms）である |
| **条件がそろっていなかった** | `06b` 2.5節は各3回・冷えた状態のみだった。本節は各5回に増やし、**冷えた状態とキャッシュのある状態の両方**、**`noop` との差分**を測った。その結果 Turbopack は +39% → **+27.8%**、webpack は +87.2% → **+100.9%** に動いた（題材にページ2枚を足した影響も含む） |
| **提案する基準** | 割合をやめ、**(a) ワーカーあたりの固定費 ≤ 200 ms**、**(b) 1ファイルあたりの変換 ≤ 1 ms**、**(c) 再コンパイルの増分 ≤ 20 ms** の3つで測る。(a)(b) は両バンドラで満たす。**(c) は webpack の冷えた状態で満たさない**（+501 ms。キャッシュがあれば +14 ms で満たす） |

> **基準は「割合」ではなく「固定費と変動費」で持つべきである。** これが再計測の結論である。
> あわせて、**webpack の未説明の約 900 ms は、基準の置き換え前に原因を特定する必要がある。**

## 9. PoC-05 の判定

| 基準 | 成功の条件 | 実測 | 判定 |
| --- | --- | --- | --- |
| **A ブラウザHTTP ↔ サーバーHTTP** | 識別子などの明確な証拠で対応付く | **27/27（100%）**・取り違え0・両バンドラ一致 | **成功** |
| **A 誤接続しないこと** | 時刻の近さで判断しない | 判断に時刻を使っていない。時間窓では絞れない場面を3件、対応付けてはいけない場面を1件、実測で示した | **成功** |
| **必須ケースの網羅** | 指示の7種すべて | 11ケース実測・両バンドラで全一致 | **成功**（RSC のみ条件付き） |
| **B コンポーネント ↔ HTTP** | 実際に通信を開始したコードの証拠がある場合だけ | **15/15・誤答0**。証拠の無いものは理由付きで作らない | **条件付き成功** |
| **C 応答 ↔ 表示値** | 成功条件に含めない | 実施していない。本文も値も収集していない | **対象外** |
| **UI への接続** | 証拠のある関係だけを表示し、設計を変えない | 既存の変換・レイアウト・描画を再利用。追加はデータセット1つと座標1件 | **成功** |
| **安全性** | 収集禁止項目を集めない | 読んだ応答ヘッダは2キーのみ。本文・クエリ値・Cookie・認証情報を持つ場所が無い | **成功** |

### 判定: **条件付き成功**

**成功と呼べる部分**

- **ブラウザの通信とサーバーの計測が、識別子だけで1対1に対応した。** 同一URLの同時実行・連続実行・
  失敗・リダイレクトを含め、取り違えも重複主張も0である。**時刻は判断に一度も使っていない。**
- **「この通信を開始したコード」を、証拠を持って指せた。** 同じ関数の中の別々の行まで区別し、
  ページではなく子コンポーネントを正しく指した。**Turbopack と webpack の両方で成立した。**
- **証拠が無いものを作らなかった。** 文書取得・中断した通信・サーバー内部の通信は、
  理由付きで「特定していません」と返している。
- **既存の探索画面の設計を変えずに描けた。** 切断は1件減り（証拠が得られたため）、
  残る1件（props の由来）はそのまま残っている。

**「条件付き」である理由**

1. **B は開発ビルド限定である。** ソースマップと要素識別子の注入の両方に依存する（`01b` C-5）。
2. **B はスクリプトが起点の通信に限る。** 文書取得・RSC ペイロード・プリフェッチは対象外であり、
   これは「取れない」ではなく「ブラウザがそもそも記録しない」ことによる。
3. **Server Component が関与する通信は、途中で切れる。** ブラウザ↔サーバーは繋がるが、
   **サーバーの中の通信の相手**を同一と証明できない（第3章 #2）。
4. **取得手段 `request-initiator` は `02d` 1.3節に無い。** 追加の提案であり、未承認である。
5. **検証したのは Next.js 16 + Chrome の1構成**である。他のブラウザ・フレームワークは未検証。

**成功扱いにしていないこと**

- **C（応答と表示値の対応）は成立していない。** `derives` も `maps` も作っていない。
  A が成立しても、**「画面のこの値は、このカラムから来た」とは言えないまま**である。
- **どのインスタンスがその通信を始めたか**は観測していない。
- **本番ビルド**では成立しない。

## 10. 次に検証すべき技術課題

| # | 課題 | なぜ要るか | どこで扱うか |
| --- | --- | --- | --- |
| **1** | **サーバー間のトレース伝播** | Server Component が自分の API を呼ぶ構成で、経路が途中で切れる。`fetch` が `node:http` を通らないのが原因であり、undici 計装か、W3C コンテキストの注入が要る。**伝播を入れると、A と同じ強さの証拠でサーバー内部まで繋がる** | **次のPoC（PoC-02 の前）** |
| **2** | **`derives` をどこまで狭められるか** | A も B も成立したのに、**値の出所は依然としてつながらない**。ここが本プロダクトの中心である。応答本文を読まずに、props 束縛の静的解析と応答キーの構造照合で候補を絞れるか | **PoC-04** |
| **3** | **相関ヘッダの設計の確定** | `Server-Timing` は第三者スクリプトに識別子を配る。専用ヘッダ + CDP で足りることは実測した。**製品では「開発モードのみ」「明示的な有効化」「ループバック限定」をどう組むか**を決める必要がある | 実装フェーズ |
| **4** | **本番ビルドでの縮退** | B はソースマップと注入に依存する。本番ビルドでは A だけが残る。**A だけのときに画面が何を主張するか**（②' が無い状態）は未設計 | 実装フェーズ |
| **5** | **複数経路の同時表示** | 1回の操作で3件の通信が起きる構成を実測した。いまのキャンバスは主経路1本＋減光である。**同時実行を「並んだ3本」として描く設計**が無い（`06a` 11章 #5 の再掲・悪化） | UI 側の設計 |
| **6** | **スクリプト起点でない通信の表現** | 文書取得は必ず起きるのに、呼び出し元を持てない。「呼び出し元が無い」ことを**ナビゲーションとして積極的に示す**のか、切断として示すのかが未決 | UI 側の判断 |
| **7** | **バッジと識別子の規約** | キャンバスは表示順のバッジ、番号付きリストは識別子を出している。今回は変換側で一致させたが、**規約として決まっていない**（`02` 5.3節） | UI 側の判断 |
| **8** | **ビルドコストの基準の置き換え** | 割合の基準は小さい題材ほど悪く見える。7.4節の3つの基準へ置き換えるかを決める | `01b` の基準更新 |
