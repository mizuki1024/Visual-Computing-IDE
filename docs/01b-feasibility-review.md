## 0. 本文書の前提と読み方

### 0.1 確信度ラベル

本文書では、記述の確信度を3段階で明示する。**本プロジェクトの原則「誠実さが第一」に従い、未検証の技術を「実現可能」と断定しない。**

| ラベル | 意味 | 根拠 |
| --- | --- | --- |
| **【事実】** | 公開ドキュメントまたは公開リポジトリで確認した仕様・挙動。出典を付す | 本フェーズでのWeb調査 |
| **【推定】** | 公知の技術仕様から論理的に導ける見込み。直接の出典は未確認 | 技術知識からの演繹 |
| **【仮説】** | 未検証の前提。PoCでのみ真偽を判定できる | — |

> **重要**: 【事実】であっても、それは「一般にそう動作すると文書化されている」ことを意味するに過ぎない。**本プロジェクトの対象構成・対象バージョンで実際に動作することは、いずれの項目についても検証していない。** 本文書の結論は全て「PoCによる確認を前提とした見込み」である。

### 0.2 判定区分

| 区分 | 意味 | Phase 2 での扱い |
| --- | --- | --- |
| **A: 成立見込み高** | 既存の実装事例または公式サポートがあり、主要な障害が見当たらない | 成立を前提にIA設計してよい。ただしPoCは必須 |
| **B: 条件付き成立見込み** | 成立する構成と成立しない構成が明確に分かれる。スコープを絞れば成立しうる | 成立しない構成の扱いをIA設計に織り込む |
| **C: 要検証** | 判断材料が不足。PoCの結果で方針が変わる | 両方の結果に耐える設計にする |
| **D: リスク高** | 本質的な限界があり、要件の再定義が必要 | 要件側を修正する |

### 0.3 結論サマリ

| ID | 問い | 判定 | 最重要の制約 |
| --- | --- | --- | --- |
| **Q-01** | コード変更なしでSQL/HTTPを取得できるか | **B: 条件付き** | 「アプリコードを変更しない」は成立見込み高。「プロジェクトにファイルを一切追加しない」は成立しない可能性が高い。**要件 INS-01 の定義修正が必要** |
| **Q-02** | Server Components / SSR への計装 | **B: 条件付き** | 計装自体は公式サポートあり。ただし **RSCでは「API呼び出し」が存在しない経路が生じ、可視化のフローモデル自体を見直す必要がある** |
| **Q-03** | DOM要素 → ソースコード | **B: 条件付き** | **React 19 で `_debugSource` が削除済み**。ビルド時の属性注入方式が本命。Turbopack 対応が未確認 |
| **Q-04** | 画面の値 → DBカラム | **C: 要検証** | 構造的に L2（推論）にしかならない。**正解率より誤答率の管理が重要** |
| **Q-05** | ブラウザ・サーバーのトレース結合 | **A: 成立見込み高** | 標準規格あり。同一オリジンのローカル開発では障害が少ない |

**全体判定**: 中核価値（M2: 画面要素 → DBカラム）の実証は **成立の見込みがあるが、終端のカラム特定は原理的に推論（L2）に留まる**。これはプロダクトの欠陥ではなく、正しく表示すべき事実である。Phase 2 へは進行可能（判定根拠は[第7章](#7-phase-2-への進行判定)）。

## Q-01. ソースコードを変更せずに SQL と HTTP リクエストを取得できるか

### Q-01.0 問いの再定義 — **本レビュー最大の発見**

調査の結果、元の問い「ソースコードを変更せずに」には、区別すべき2つの意味があることが判明した。

| 解釈 | 内容 | 成立見込み |
| --- | --- | --- |
| **(a) 非改変**: ユーザーが書いたアプリケーションロジックを一切変更しない | 既存の `.tsx` / `.ts` ファイルに手を入れない | **成立見込み高** |
| **(b) 非追加**: プロジェクトディレクトリに一切ファイルを追加しない | `instrumentation.ts` のような新規ファイルも置かない | **成立しない可能性が高い** |

現行の要件 `INS-01` は「ユーザーのソースコードを書き換えずに」としか書いておらず、この区別がない。**(b) を満たす方式は限られ、かつ未検証である。** 要件を (a) に定義し直し、(b) は「望ましいが必須ではない」と格下げすることを提案する（[第6章](#6-要件への反映提案)）。

### Q-01.1 実現方法の候補

| # | 方式 | 概要 | 確信度 | 非改変(a) | 非追加(b) | 評価 |
| --- | --- | --- | --- | --- | --- | --- |
| **1** | **Next.js `instrumentation.ts` + OpenTelemetry** | プロジェクトルートに `instrumentation.ts` を置き、`register()` で OTel SDK を初期化する | 【事実】Next.js 15以降は既定で有効。Next.js 14以前は `experimental.instrumentationHook` が必要 | ○ | **×**（新規ファイルが必要） | **本命**。公式サポート経路 |
| **2** | **`NODE_OPTIONS=--require` によるプリロード** | IDE が dev server を子プロセスとして起動する際、環境変数で計装モジュールをプリロードする | 【事実】Node.js の標準機能。【仮説】Next.js dev server が複数プロセスにフォークした際、子プロセスへ伝播するか未確認 | ○ | ○ | **非追加(b)を満たす唯一の有力候補。要検証** |
| **3** | **ORM固有の計装パッケージ** | Prisma は `@prisma/instrumentation`、Drizzle はサードパーティの計装、素の `pg` は `@opentelemetry/instrumentation-pg` | 【事実】Prisma は公式に OTel 計装を提供し、`prisma:client:operation` / `prisma:engine:db_query` 等のスパンを発行する。Drizzle にも `db.statement` に SQL を載せる計装が存在する | ○ | × | 方式1か2の上に乗る。**単独では成立しない** |
| **4** | **PostgreSQL 側のログ** | `log_statement=all` やサーバーログから SQL を取得 | 【推定】PostgreSQL の標準機能 | ○ | ○ | **どのリクエストが発行したか紐付けられない**。補完的 |
| **5** | **DBプロキシ方式** | IDE が PostgreSQL ワイヤプロトコルのローカルプロキシを立て、`DATABASE_URL` を環境変数で差し替える | 【推定】プロトコル仕様は公開されており技術的には可能。【仮説】実装コストと安定性は未評価 | ○ | ○ | **アプリ計装なしで SQL を取れる唯一の現実的手段**。ただしトレース結合は L2 に落ちる |
| **6** | **HTTPリバースプロキシ方式** | IDE が dev server の前段にプロキシを置き、プレビューをプロキシ経由にする | 【推定】標準的な手法 | ○ | ○ | HTTPは取れるが **SQLは取れない**。方式5との併用が前提 |

### Q-01.2 実装上の制約

| # | 制約 | 確信度 | 影響 |
| --- | --- | --- | --- |
| C-1 | **計装の初期化はアプリ起動時に1度だけ行われる**。IDEが後から接続して計装を注入することはできない | 【事実】`register()` は新しいサーバーインスタンス起動時に1回呼ばれ、サーバーはその完了を待ってからリクエストを処理する | **IDE外で起動済みの dev server には計装できない**。IDEがプロセスを起動することが前提条件になる |
| C-2 | Next.js 14以前は `next.config.js` への `experimental.instrumentationHook` 追加が必要 | 【事実】 | 設定ファイルの変更が必要 = 非改変(a)も部分的に破る。**対象バージョンを Next.js 15以降に絞るべき** |
| C-3 | Edge Runtime では Node.js の `require` フックやネイティブモジュール依存の計装が使えない | 【推定】Edge Runtime は Node.js API の一部しか提供しない | 方式2が Edge では機能しない。`@vercel/otel` は Node/Edge 両対応とされる【事実】が、ORM計装は Node 限定【推定】 |
| C-4 | バンドラ（Turbopack / webpack）がモジュールをバンドルすると、計装がフックすべき `require` が消える場合がある | 【仮説】 | ORM計装が効かない可能性。**最優先の検証項目** |
| C-5 | 方式5（DBプロキシ）では、接続文字列の差し替えが必要 | 【推定】 | 環境変数の上書きで可能だが、アプリが接続文字列をハードコードしている場合は不可 |
| C-6 | 方式4・5では、SQL とそれを発行した HTTP リクエストの紐付けができない | 【推定】 | 時間窓と接続IDによる推定（**L2**）になる。トレース結合の品質が落ちる |
| C-7 | 計装による性能影響 | 【仮説】 | 要件 INS-04（起動 +20%以内 / 遅延 +10ms以内）を満たすか未検証 |

### Q-01.3 最小のPoCで確認する方法

> **本フェーズでは実施しない。Phase 2 と並行して行う。**

**PoC-01: 計装経路の成立確認**

| 項目 | 内容 |
| --- | --- |
| 題材 | Next.js 15 (App Router) + TypeScript + PostgreSQL + Prisma の最小アプリ。ページ3枚、APIルート3本、SQL発行箇所5か所 |

| 手順2 | 方式2（`NODE_OPTIONS=--require`）で同じことができるか。**特に dev server がワーカープロセスを分けた場合に計装が伝播するか** |
| 手順3 | Turbopack 有効時と webpack 時の両方で手順1・2を再実行し、差を記録する |

### Q-01.4 成功・失敗の判定基準

| 基準 | 成功 | 条件付き成功 | 失敗 |
| --- | --- | --- | --- |
| **SQL取得率** | 発行された SQL の 95%以上を、実行されたSQL文付きで取得できる | 80〜95% | 80%未満 |
| **HTTP取得率** | サーバーが受信したリクエストの 99%以上を取得できる | 95〜99% | 95%未満 |
| **親子関係** | SQLスパンが HTTP スパンの子として正しく紐付く（**L1として成立**） | 時間窓推定での紐付けのみ（**L2に降格**） | 紐付けできない |
| **非追加(b)** | 方式2が機能し、プロジェクトにファイルを追加せずに済む | 方式1のみ機能（ファイル追加が必要） | いずれも機能しない |
| **バンドラ** | Turbopack / webpack の双方で機能する | 片方のみ | 双方で不安定 |
| **性能** | 起動 +20%以内、遅延 +10ms以内（INS-04） | 起動 +50%以内、遅延 +30ms以内 | それ以上 |

### Q-01.5 失敗した場合の代替案

縮退は段階的に行う。**いずれの段階でもプロダクトは成立するが、提供できる観測性レベルが下がる。**

| 段階 | 代替案 | 失われるもの | 観測性への影響 |
| --- | --- | --- | --- |
| **代替1** | 方式2が機能しない場合 → 方式1（`instrumentation.ts` を IDE が生成）に妥協する。生成ファイルは IDE が管理し、`.gitignore` に登録、IDE終了時に削除、ユーザーに可視化する | 「プロジェクトに一切触れない」という訴求 | なし（L1維持） |
| **代替2** | ORM計装が機能しない場合 → 方式5（DBプロキシ）で SQL を取得する | HTTPリクエストとSQLの確実な紐付け | **SQL〜HTTP間のエッジが L1 → L2 に降格** |
| **代替3** | 方式5も困難な場合 → SQL は静的解析のみ（コード上のクエリ記述を提示）とし、実行されたSQLは表示しない | 実際に発行されたSQL、実行時間、取得件数 | **SQLノード全体が L2 に降格** |
| **代替4** | 全ての計装が困難な場合 → HTTPのみブラウザ側（L0）で取得し、サーバー内部は静的解析（L2）で描く | サーバー内部の実測 | **サーバー以降が全て L2**。それでも「コード上の経路」は示せるため、プロダクトとしては成立する |

> 代替4 でも成立することが、要件 `NFR-12`（グレースフルデグレード）と `INS-03` の意義である。

## Q-02. Next.js の Server Components / SSR への計装

### Q-02.1 実現方法の候補

| # | 方式 | 概要 | 確信度 |
| --- | --- | --- | --- |
| 1 | **`@vercel/otel` による自動計装** | `registerOTel()` を `instrumentation.ts` の `register()` 内で呼ぶ。App Router の Server Components / Route Handlers / Server Actions を自動計装する | 【事実】`@vercel/otel` と手動の NodeSDK のいずれも、App Router の server components・route handlers・server actions を自動計装すると文書化されている |
| 2 | **fetch の自動計装** | Next.js は Server Components / Route Handlers からの `fetch` 呼び出しに対し、SDK 初期化後に自動でスパンを生成する | 【事実】 |
| 3 | **`onRequestError` フック** | Next.js 15 で追加。Server Components / Route Handlers / Server Actions の未処理エラーで発火する | 【事実】エラーをトレースに紐付ける正しい場所とされている |
| 4 | 手動の NodeSDK 構成 | `@opentelemetry/sdk-node` を直接構成する | 【事実】 |

### Q-02.2 実装上の制約 — **可視化モデルへの影響が最大の論点**

| # | 制約 | 確信度 | 影響 |
| --- | --- | --- | --- |
| **C-1** | **Server Components は、サーバー上のレンダリング中に直接 DB を参照できる。この場合「API リクエスト」というノードが存在しない** | 【事実】RSC の設計思想そのもの | **参考画像の全てが前提としている「ブラウザ → API → サーバー → DB」というフローモデルが、RSC では成立しない。** ブラウザから観測できるのは1回のドキュメント取得だけで、その内部にDB参照が埋まっている |
| C-2 | ストリーミングSSR では、スパンの時間区間が重なる | 【推定】 | タイムライン表現（直列のガントチャート）が破綻する。並行・入れ子の表現が必要 |
| C-3 | Client Components と Server Components の境界が、トレース上では連続して見えない | 【推定】 | 「どこまでがサーバーで、どこからがブラウザか」を可視化する必要がある |
| C-4 | Server Actions は HTTP POST として実行されるが、URLがエンドポイント名を表さない | 【推定】 | フロー図上のラベル付けに工夫が要る |
| C-5 | Turbopack 環境での自動計装の挙動 | 【仮説】 | 未確認。Q-01 C-4 と同じ |
| C-6 | Next.js 14以前では `experimental.instrumentationHook` が必要、15以降は既定で有効 | 【事実】 | 対象バージョンの絞り込みが必要 |

> **C-1 は要件への影響が大きい。** 現行の `FR-20`（ページ単位のデータ取得フロー）は、暗黙に「ブラウザ発のHTTPリクエストが起点」を前提としている。RSC では起点が「ドキュメント取得」であり、その内部に複数のDB参照が入れ子になる。**フローのデータモデルを「HTTPリクエスト列」ではなく「スパンの木構造」として定義し直す必要がある。** 要件追加を提案する（[第6章](#6-要件への反映提案)）。

### Q-02.3 最小のPoCで確認する方法

**PoC-02: RSC / SSR 計装の成立確認**

| 項目 | 内容 |
| --- | --- |
| 題材 | PoC-01 の題材に、次の3パターンのページを追加する |
| パターン1 | **Server Component 内で直接 DB を参照**するページ（API経由でない） |

### Q-02.4 成功・失敗の判定基準

| 基準 | 成功 | 条件付き成功 | 失敗 |
| --- | --- | --- | --- |
| **RSC直結DB** | パターン1でサーバースパンとSQLスパンが親子で取得できる | SQLスパンは取れるが親子関係が不明 | SQLスパンが取れない |
| **3パターン網羅** | 3パターンすべてで成立 | 2パターン | 1パターン以下 |
| **木構造再構成** | スパンの親子関係から、1ドキュメント取得内のDB参照回数と順序を再構成できる | 回数のみ分かる | 再構成できない |
| **境界判別** | Client / Server の境界をスパン属性またはコンポーネント種別から判別できる | 静的解析での推定（L2）なら可能 | 判別できない |

### Q-02.5 失敗した場合の代替案

| 段階 | 代替案 | 観測性への影響 |
| --- | --- | --- |
| **代替1** | RSC内部のスパンが取れない場合 → RSC によるレンダリングを「サーバー内部処理」という**1つの集約ノード**として表示し、内訳は静的解析で補う | 集約ノード内部が **L2** |
| **代替2** | ストリーミングの時間表現が困難な場合 → タイムラインを「直列の代表経路」に簡略化し、並行実行があったことを注記で示す | タイムラインの正確性が落ちる（**表示を L2 相当として扱う**） |
| **代替3** | RSC 全体が観測できない場合 → **MVP の対象を Client Component + Route Handler 構成に限定**し、RSC 主体のプロジェクトは「一部機能が利用できません」と明示する | 対象プロジェクトが狭まるが、誠実さは保たれる (FR-07) |

## Q-03. DOM要素とソースコードの対応付け

### Q-03.0 調査で判明した重要な事実

> **【事実】React 19 で Fiber の `_debugSource` プロパティが削除された（facebook/react PR #28265）。**
>
> React 18 までは Fiber ノードが `_debugSource`（ファイル名・行番号）を保持しており、「ブラウザから該当ソースを開く」系のツールはこれに依存していた。React 19 ではこれが削除され、代替として **`_debugStack`**（その JSX 要素が生成された箇所のスタック）が開発ビルドで保持される。React DevTools 自身もコンポーネントスタックからソースを解決する方式に移行している。各ツールは `_debugStack` + ソースマップ解決によって同等の機能を再実装している。

この事実は、方式の優劣を大きく変える。**Fiber 依存の方式は React のバージョンによって壊れる実績がある**ため、ビルド時注入方式の相対的な優位が高い。

> **【事実】Onlook（本プロダクトの参照元）は、ビルド時に JSX へ `data-oid` 属性を注入する Babel プラグイン方式を採用している。** webpack / esbuild / vite 等のバンドラ向けプラグインを提供し、視覚的に編集された際は oid から対応する JSX を特定してパッチし、HMR でリロードする。Tailwind クラスの編集では、AST 走査により対象クラスのみを更新し、整形とコメントを保持する。

### Q-03.1 実現方法の候補

| # | 方式 | 概要 | 確信度 | RSC対応 | 安定性 |
| --- | --- | --- | --- | --- | --- |
| **1** | **ビルド時の属性注入（`data-oid` 方式）** | ビルド時に各 JSX 要素へ一意IDを属性として注入。DOM に残るため、ブラウザ側から直接読める | 【事実】Onlook が実装し稼働している | **○**（HTMLに属性が残るため RSC でも機能する） | 高（Reactの内部実装に依存しない） |
| 2 | **Fiber の `_debugStack` + ソースマップ解決** | React 19 の開発ビルドが保持するスタックを解析し、ソースマップで元の位置に戻す | 【事実】React DevTools および複数のツールがこの方式を採用 | △（RSC の DOM には Fiber がない場合がある）【推定】 | 中（React内部実装に依存。過去に破壊的変更の実績あり） |
| 3 | `__source` prop（`@babel/plugin-transform-react-jsx-source`） | React 18 までの `_debugSource` の供給源 | 【事実】React 19 では Fiber に載らない | × | **低（React 19 で実質的に無効）** |
| 4 | DOM構造・テキスト内容のヒューリスティック照合 | 静的解析したJSX構造と実DOMを突き合わせる | 【推定】 | ○ | 低（精度が出ない） |

**推奨**: 方式1を本命とし、方式2を補完（属性注入ができない要素のフォールバック）とする。

### Q-03.2 実装上の制約

| # | 制約 | 確信度 | 影響 |
| --- | --- | --- | --- |
| **C-1** | **ビルド設定への介入が必要**。Next.js の既定コンパイラは SWC であり、Babel プラグインを有効にすると SWC の最適化経路から外れてビルドが遅くなる | 【推定】Next.js の文書化された挙動 | 開発体験の劣化。SWC プラグインとして実装する選択肢もあるが実装コストが高い |

| **C-3** | UIライブラリ（shadcn/ui 等）を経由した要素は、注入先がライブラリ内部の JSX になる | 【推定】 | **ユーザーのコードを指さない**。注入対象をユーザーのソースディレクトリに限定する必要がある。限定すると、ライブラリ由来の DOM 要素は選択できなくなる |

| C-6 | 同一コンポーネントが複数箇所で使われている場合、見た目の編集が全使用箇所に波及する | 【推定】R-04 と同一 | 編集前の影響範囲提示が必須 |

## Q-04. 画面の値と DB カラムの対応付け精度

### Q-04.0 構造的な結論 — **この対応付けは原理的に L2 である**

Q-01〜Q-03 が成功し、HTTP も SQL も実測（L0/L1）できたとしても、**「画面に出ているこの値が、properties テーブルの area カラムに由来する」という主張そのものは、推論（L2）にしかならない。**

理由は次の通り。

1. 実測できるのは「HTTPレスポンスのJSON」と「実行されたSQL文」であり、**両者を結ぶマッピング（どのカラムがどのJSONキーになったか）は実測されていない**。ORM の内部変換は観測の外にある。
2. 実測できるのは「DOM に表示された文字列」であり、**それが props のどの経路で来たかは実測されていない**。
3. 値の一致（`"千葉県"` が SQL 結果にも JSON にも DOM にもある）は **必要条件であって十分条件ではない**。同じ値が複数カラムに存在しうる。

したがって、**順方向トレースの端から端までを「実測」と表示してはならない。** これは本プロダクトの観測性モデルの核心であり、要件 `OBS-09`〜`OBS-12` として明文化することを提案する（[第6章](#6-要件への反映提案)、および `01-product-requirements.md` 5.4節）。

### Q-04.1 実現方法の候補

| # | 方式 | 概要 | 確信度 | 寄与する確度 |
| --- | --- | --- | --- | --- |
| **1** | **実行されたSQLのパース** | L1 で取得した実SQL文を構文解析し、参照テーブルと SELECT 句のカラムを抽出する | 【推定】SQLパーサは成熟技術 | **高**。実測されたSQLに対する決定的な解析のため、推論の中では最も確かい |
| 2 | **ORM計装のスパン属性** | Prisma は `model` / `operation` をスパン属性に持つ | 【事実】`prisma:client:operation` 等のスパンを発行する | 高 |
| 3 | **静的解析（AST + 型情報）** | コード上のクエリ記述、レスポンス型、props 型の連鎖を辿る | 【推定】 | 中。動的構築では破綻する |
| 4 | **構造照合** | SQL結果セットの列構成と、レスポンスJSONのキー構成を突き合わせる | 【推定】 | 中。別名・加工があると破綻 |
| 5 | **値照合** | DOM の値 / JSON の値 / SQL結果の値が一致するか | 【推定】 | **補強材料にしかならない**。単独では一意に定まらない |

**推奨**: 1〜5を組み合わせ、**一致した証拠の数に応じて確度（高/中/低）を算出する**。単一の方式に依存しない。

### Q-04.2 実装上の制約

| # | 制約 | 確信度 | 影響 |
| --- | --- | --- | --- |
| C-1 | **`SELECT *` ではカラムを特定できない** | 【事実】SQLの性質 | 結果セットのメタデータから列名は取れる【推定】が、どの列が使われたかは不明 |
| C-2 | ORM がカラム名と異なるフィールド名を使う（別名、キャメルケース変換、`@map`） | 【事実】Prisma の `@map` 等 | マッピング表を ORM のスキーマ定義から読む必要がある |
| C-3 | 値が加工されている（日付整形、連結、計算、条件分岐） | 【推定】 | 値照合が効かない。静的解析でも追跡困難 |
| C-4 | 同じ値が複数カラム・複数テーブルに存在する | 【推定】 | 値照合で一意に定まらない。**誤答の主要因** |
| C-5 | `map` による繰り返しで、DOM要素と配列添字の対応が必要 | 【推定】 | Q-03 C-4 と連動 |
| C-6 | JOIN、集計、サブクエリ、ビュー経由 | 【推定】 | 由来カラムが複数または不定になる |
| C-7 | 動的に組み立てられるクエリ、生SQL文字列の連結 | 【推定】 | 静的解析は不能。ただし **実行されたSQL（方式1）なら解析できる** |

> C-7 は重要な示唆を含む。**実行時トレース（L1）が取れていれば、静的解析の最大の弱点である動的クエリを回避できる。** Q-01 の成否が Q-04 の精度を直接左右する。

### Q-04.3 最小のPoCで確認する方法

**PoC-04: 対応付け精度の測定**

| 項目 | 内容 |
| --- | --- |
| 題材 | PoC-01 の題材を拡張し、**難易度別に分類した50個の画面要素**を用意する |
| 難易度1（易） | 単純な `SELECT col1, col2 FROM t` の結果をそのまま表示（15個） |
| 難易度2（中） | `SELECT *`、ORM の別名マッピング、`map` 内の表示（15個） |
| 難易度3（難） | JOIN、計算値、条件分岐による表示、整形済みの日付（15個） |
| 難易度4（不能想定） | 静的なリテラル、クライアント生成値、複数ソースの合成（5個） |
| 手順 | 50要素それぞれについて、人手で正解（テーブル名・カラム名、または「DB由来でない」）を確定させ、グラウンドトゥルースとする。その上でツールの出力と突き合わせる |
| 出力の分類 | **正解 / 誤答（違うカラムを自信を持って提示）/ 候補提示（複数の候補に正解が含まれる）/ 特定不能（正しく諦めた）** の4分類で集計する |

### Q-04.4 成功・失敗の判定基準

> **判定方針（再掲）**: 「正解率70% / 誤答0% / 特定不能30%」は、「正解率90% / 誤答10%」より **望ましい**。誤答は信頼を破壊し、ユーザーを誤った修正に導く。

| 基準 | 成功 | 条件付き成功 | 失敗 |
| --- | --- | --- | --- |
| **誤答率（全体）** | **2%以下** | 5%以下 | 5%超 |
| **正解率（難易度1）** | 95%以上 | 85%以上 | 85%未満 |
| **正解率（難易度2）** | 70%以上 | 50%以上 | 50%未満 |
| **正解率（難易度3）** | 40%以上、または候補提示で正解を含む | 候補提示でも正解を含まないが誤答もしない | 誤答する |
| **難易度4の扱い** | 全て「DB由来でない」または「特定不能」と正しく返す | — | 誤ってDBカラムを提示する |
| **確度の較正** | 「確度:高」と表示したものの正解率が 95%以上 | 90%以上 | 90%未満（**確度表示が信用できない = 最悪の失敗**） |

> **最後の基準が最も重要。** 確度ラベルが実態と乖離していれば、観測性モデル全体が無意味になる。

### Q-04.5 失敗した場合の代替案

| 段階 | 代替案 | 失われるもの |
| --- | --- | --- |
| **代替1** | カラム単位の特定精度が出ない場合 → **テーブル単位での提示に粒度を落とす**。「properties テーブル由来（カラムは特定できませんでした）」 | カラム名の提示 |
| **代替2** | 単一の答えが出せない場合 → **候補の複数提示**に切り替える。「area / prefecture のいずれか」 | 断定的な回答 |
| **代替3** | 自動特定が困難な場合 → **ユーザーによる手動の対応付け（アノテーション）を併用**する。一度対応付けたら記憶し、再利用する | 完全自動という体験。ただし**精度は上がる** |
| **代替4** | 全く精度が出ない場合 → **順方向トレースを「経路の提示」に留める**。「この要素 → PropertyCard → GET /api/properties → properties テーブル」までを示し、カラムには踏み込まない | 中核価値の一部。ただし M2 の大半は残る |

> **代替3（手動アノテーション）は、仮説 H-03 が覆った場合の主たる受け皿である。** 完全自動を諦める代わりに、確度を人間が担保する。プロダクト原則1とは整合する。

## Q-05. ブラウザとサーバーのトレース結合

### Q-05.1 実現方法の候補

| # | 方式 | 概要 | 確信度 | 非侵襲性 |
| --- | --- | --- | --- | --- |
| **1** | **CDP によるリクエストヘッダ注入** | IDE がブラウザを制御下に置き、送出される全リクエストに `traceparent` ヘッダを付与する | 【推定】CDP のリクエストインターセプト機能による。【仮説】性能影響は未評価 | **最高**（アプリにもページにも手を入れない） |
| 2 | **ブラウザ側 OTel 計装のスクリプト注入** | IDE がプレビューページに計装スクリプトを注入し、`fetch`/`XHR` をフックする | 【事実】ブラウザ計装は `fetch`/`XHR` に `traceparent` を自動注入する。ただし **ブラウザ計装は experimental** と明記されている | 高（ページに script を注入） |
| 3 | **`Server-Timing` ヘッダによる逆方向の伝達** | サーバーがトレース情報をレスポンスヘッダで返し、ブラウザ側が親子関係を構成する | 【事実】`exposedHeaders` に含まれていればブラウザ計装が読み取り、より正確な親子関係を構成できる | 中（サーバー側の設定が必要） |
| 4 | **時間窓マッチング** | URL・メソッド・タイムスタンプで突き合わせる | 【推定】 | 最高だが **L2**。並行リクエストで誤結合のリスク |

**推奨**: 方式1を本命、方式2を次点、方式4をフォールバックとする。

### Q-05.2 実装上の制約

| # | 制約 | 確信度 | 影響 |
| --- | --- | --- | --- |
| C-1 | **`traceparent` は CORS のセーフリストに含まれていない** | 【事実】whatwg/fetch issue #911 で議論中の課題 | クロスオリジンのリクエストでは **preflight が発生**し、サーバーが許可しないとヘッダが落ちる。**ローカル開発の同一オリジンでは問題になりにくい**が、外部API呼び出しでは機能しない |
| C-2 | ブラウザ側の OTel 計装は experimental であり、Node.js 版に比べ機能が限定される | 【事実】 | 方式2の安定性に懸念 |
| C-3 | CDP でのリクエストインターセプトは、全リクエストを一度停止させるため性能影響がある | 【仮説】 | プレビューの体感速度が落ちる可能性。要計測 |
| C-4 | RSC の初回ドキュメント取得は `fetch` ではなくナビゲーションであり、計装の対象が異なる | 【推定】 | Q-02 C-1 と連動。ナビゲーションにもヘッダを注入する必要がある（方式1なら可能）【推定】 |
| C-5 | ヘッダを注入することでアプリの挙動が変わる可能性（厳格なヘッダ検証をするミドルウェア等） | 【仮説】 | 稀だが起こりうる。無効化オプションが必要 |

| 基準 | 成功 | 条件付き成功 | 失敗 |
| --- | --- | --- | --- |
| **結合率** | 100リクエスト中 100件が結合される | 95件以上 | 95件未満 |
| **誤結合** | **0件**（並行リクエスト下でも） | 0件（直列のみ） | 1件以上 |
| **ナビゲーション** | 初回ドキュメント取得も結合できる | fetch のみ | — |
| **性能** | ページロード時間の増加が 10%以内 | 30%以内 | それ以上 |

### Q-05.5 失敗した場合の代替案

| 段階 | 代替案 | 観測性への影響 |
| --- | --- | --- |
| **代替1** | CDP ヘッダ注入が機能しない場合 → 方式2（スクリプト注入）に切り替える | なし（L1維持） |
| **代替2** | いずれのヘッダ方式も機能しない場合 → 方式4（時間窓マッチング）に落とす | **ブラウザ〜サーバー間のエッジが L1 → L2 に降格**。並行リクエスト時は「結合の確度: 低」と表示する |
| **代替3** | 誤結合が許容できない場合 → **ブラウザ側トレースとサーバー側トレースを結合せず、2つの独立したビューとして並置**する。ユーザーが目視で対応付ける | 1本のフローという中核体験が失われる。**M2 の価値が大きく下がるため、最後の手段** |

## 5. 観測性モデルの精査結果

> 本章は、ユーザー指示「各イベント・ノード・接続線で、何が実測され、何が推論されているかを個別に判断する」に対応する。詳細な規約は `01-product-requirements.md` 5.4節に反映する。

### 5.1 核心的な結論

**順方向トレース（画面要素 → DBカラム）は、7つのホップのうち 5つが L0/L1（実測）であっても、2つの「値の結びつき」が L2（推論）であるため、経路全体としての主張は L2 である。**

観測性レベルは **経路単位ではなく、ノード・エッジ・属性の単位で個別に判定しなければならない。** そして経路全体の確度は、構成要素の中で最も弱いものに等しい（**最弱環の原則**）。

### 5.2 正準トレースの分解

題材: 「PropertyCard に表示されている『千葉県』は、properties テーブルの area カラムから来ている」という主張。

| # | 対象 | 種別 | レベル | 根拠 | 弱点 |
| --- | --- | --- | --- | --- | --- |
| 1 | DOM要素とそのテキスト `"千葉県"` | ノード | **L0** | DOMの直接読み取り | — |
| 1→2 | DOM要素 → `data-oid` → JSX位置 | エッジ | **L1** | ビルド時注入（Q-03方式1） | 注入がユーザーソースに限定される |
| 2 | コンポーネント `PropertyCard` とソース位置 | ノード | **L1** | 同上 | 開発ビルド限定 |
| 2→3 | `props.area` → レスポンスJSONの `properties[0].area` | エッジ | **L2** | 静的解析 + 値照合 | **値の一致は必要条件に過ぎない。加工・条件分岐があると破綻** |
| 3 | HTTPリクエスト `GET /api/properties`（URL・ヘッダ・ステータス・時間） | ノード | **L0** | ブラウザ側の計測 | — |
| 3→4 | ブラウザのリクエスト ↔ サーバーの受信 | エッジ | **L1** | `traceparent` 伝播（Q-05方式1） | 失敗時は L2（時間窓）に降格 |
| 4 | サーバーハンドラの実行（開始・終了・時間） | ノード | **L1** | OTel 自動計装 | 計装が前提 |
| 4→5 | ハンドラ → 発行SQL | エッジ | **L1** | 同一トレース内の親子スパン | Q-01代替2採用時は L2 |
| 5 | 実行されたSQL文・実行時間・取得件数 | ノード | **L1** | ORM計装（`db.statement`） | 計装が前提 |
| 5→6 | SQL → テーブル `properties` | エッジ | **L1相当** | **実測されたSQL文の決定的な構文解析** | 動的テーブル名でも実SQLなら解析可能 |
| 6 | テーブル定義（カラム・型・制約） | ノード | **L0** | DBへの直接照会 | — |
| 5→7 | SQL → カラム `area` | エッジ | **L1相当 または L2** | SELECT句に列挙されていれば L1相当。**`SELECT *` なら L2** | クエリの書き方に依存 |
| 7 | カラム `area`（型・制約） | ノード | **L1相当** | テーブル定義の照会 + 実測SQLの解析 | `SELECT *` の場合はノード自体が L2 |
| 7→3 | カラム `area` → レスポンスJSONのキー `area` | エッジ | **L2** | ORMのマッピング推定 | **ORMの内部変換は観測外。別名・加工があると不能** |
| 経路 | 主張全体「この表示は `properties.area` 由来」 | 経路 | **L2** | **最弱環 = #2→3 と #7→3** | — |

### 5.3 この分解から導かれる表示規約

| 規約 | 内容 |
| --- | --- |
| **観測性はノード・エッジ・属性ごとに保持する** | 経路単位の単一ラベルにしない |
| **経路要約は最弱環のレベルを表示する** | 14 の構成要素のうち 12 が L0/L1/L1相当 でも、2つが L2 なら経路は L2 |
| **最も弱い箇所をユーザーに示す** | 「この経路で最も確度が低いのは、props とAPIレスポンスの対応付けです」と名指しする |
| **実測区間と推論区間を視覚的に分ける** | 1本の線の中でも、区間ごとに実線/破線を切り替える |
| **「実測されたSQL」と「推測されたカラム対応」を同じ扱いにしない** | ユーザー指示の直接の要請 |

> **この分解は、ユーザー指示「実測されたAPI通信と、静的解析で推測したDBカラムの関係を、まとめて『実測』と扱わないでください」への直接の回答である。** 上表の #3（L0）と #7→3（L2）は、同じフロー上にありながら確度が3段階異なる。

## 7. Phase 2 への進行判定

### 7.1 判定: **進行可能（条件付き）**

### 7.2 進行してよい理由

| # | 理由 |
| --- | --- |
| 1 | Q-01・Q-02・Q-05 について、**公式にサポートされた実現経路が存在することを公開ドキュメントで確認できた**。全てが未知の賭けではない |
| 2 | Q-03 について、**同種のプロダクト（Onlook）が実際に稼働している方式を確認できた**。原理的な不可能性はない |
| 3 | PoC の結果によって変わるのは「取得できる情報の粒度と確度」であり、**画面構成・情報階層の骨格ではない**。IA設計は粒度に対して頑健に設計できる |
| 4 | 本レビューで判明した3つの構造的事実（RSCのフローモデル、React 19の仕様変更、順方向トレースのL2性）は、**いずれも PoC を待たずに IA 設計へ入力できる確定情報**である |
| 5 | 各項目に段階的な代替案があり、**最悪の場合でも観測性レベルが下がるだけでプロダクトは成立する**（Q-01代替4、Q-04代替4） |

### 7.3 Phase 2 が織り込まなければならない確定事項

PoC の結果に関わらず確定しており、IA設計の前提とすべきもの。

| # | 確定事項 | IA設計への要請 |
| --- | --- | --- |
| **1** | **RSC では「API ノード」が存在しない経路がある** | フロー図は「ブラウザ→API→サーバー→DB」の直線モデルを前提にできない。**スパンの木構造を描ける表現**が必要 |
| **2** | **要素 → コードの対応付けは開発ビルド限定であり、ライブラリ由来の要素では成立しない** | 「選択できない要素」「編集できない要素」の表現が必須。無言で無反応にしない |
| **3** | **順方向トレースの終端（カラム特定）は構造的に L2 である** | 経路の中で確度が変化することを表現する UI が必須。1本の線を単一の確度で描けない |
| **4** | **計装は IDE がプロセスを起動した場合にのみ機能する** | 「外部で起動済みの dev server に接続した」状態を、機能制限付きとして表現する必要がある |
| **5** | **ストリーミングSSR では処理が時間的に重なる** | タイムラインは直列のガントチャートでは足りない |
