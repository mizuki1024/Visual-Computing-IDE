## 4. 指摘一覧

### 4.1 実際の不具合（再現した、またはコード上で経路が確定している）

#### F-01 位置だけの識別子で、同じ位置に来た別の要素へ選択と書き込み先が移る — 重要度 **高**（製品化前の課題・PoC の EP-01 の範囲を狭める）

| 項目 | 内容 |
| --- | --- |
| 対象 | `src/server/anchors.ts:92-93`（識別子 = `sha1(file:line:col)`）・`:294-317`（照合は識別子・タグ・囲むコンポーネントだけ）、`poc/edit/engine.cjs:120-132`（行:列・タグ・コンポーネントの一致だけで要素を決める）、`poc/edit/public/ui.js:205-223`（再解決は同じ識別子なら成功） |
| 条件 | 選んだ要素の行が消える・並びが変わるなどで、**同じ (ファイル:行:列) に、同じタグ・同じコンポーネントの別の要素**が来る。兄弟の `<dd>`・`<li>`・同じ字下げの `<div>` で起きやすい |
| 現在の挙動 | 製品の `resolveSelection` が6段の照合をすべて通して `resolved` を返す（RV07）。HMR 後の DOM では、その識別子は新しい要素に付いているので、PoC の画面は「選択を再解決しました — 同じ識別子・6段の照合を通過」と出す。このあと下書きを作ると `baseHash` は新しい内容から作られるので、エンジンは**別の要素の token を書き換える位置**を返す（RV08） |
| 期待する挙動 | 選んだ要素と同じであることを確かめられないときは「特定できません」とし、別の要素を選ばない（06h 3.2 の主張・`02e` EP-01） |
| 根拠 | RV07・RV08（`docs/06h-review-results/review-repro.txt`） |
| 影響 | 利用者が選んでいない要素のクラスを書き換える。差分確認（S-14）で行が見えるので利用者が気づく余地はあるが、画面は「再解決した」と言っている |
| 推奨 | 位置に依らない同一性の確認を足す（例: 選択時の要素の内容の指紋 — タグ・属性名の並び・className のリテラル・子の構造 — を保持し、再解決・下書きの作成・適用の直前に照合する）。それまでは、ソースが変わった後（外部変更・適用・取り消し）の再解決は「識別子が同じでも再選択を求める」に縮退する |
| PoC 結論への影響 | **EP-01 の「条件付き成功」の条件を狭める**: 「同じ行・列を保つ自分の変更の後」は成立、「ソースが外部で変わった後」は誤選択がありうる。06h の E32 は識別子が**消える**場合だけを試していた。PoC-03・Phase 7B-2 の識別子の設計に由来するため、探索モードの選択（7B-2）にも同じ限界がある（表示だけなので書き込みの害は無い） |

#### F-02 書き込み範囲の確認が「プロジェクトの根の中」で、「src/ の中」ではない — 重要度 **中**（製品化前の課題）

| 項目 | 内容 |
| --- | --- |
| 対象 | `poc/edit/engine.cjs:288-297`（`:294` で `realpath` が根の中かだけを見る） |
