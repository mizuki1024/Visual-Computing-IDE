## 1. 設計矛盾の整理 — `rsc-direct` に `derives` は要らないのか

指示 第2節。**これを先に片付けないと、何を作るべきかが決まらない。**

### 1.1 突き合わせたもの

| 出典 | 主張 |
| --- | --- |
| `02a` 3.5.2 / `02` 4.2 | `rsc-direct` のホップ列は `renders → binds →（**derives なし**）→ invokes → executes → reads/projects → maps`。「推論ホップが1つ減るため、**確度はむしろ高い**」 |
| `06d`（PoC-02 実測）5.1 | 「**② と ②'' の間に線は無い。同じファイルの同じ関数であってもである。**」描画したコンポーネントと SQL を実行したコンポーネントが未接続 |

### 1.2 確認事項への回答

#### (1) 描画と SQL 実行の関係を、何が証明できるか

| 候補 | 実測での成否 |
| --- | --- |
| 描画スパンの子孫に SQL がある | **証明にならない。** 描画スパンは**ルート単位**である（`06d` 2.2 実測）。`/lin-f` のように1ページに2本の SQL があると、どちらがどの表示値かを何も語らない |
| SQL スパン開始時の呼び出しスタック | **取れない。** アプリのフレームが 0/8（`06d` 3.1 実測） |
| 呼び出し入口の呼び出しスタック（`server-call-stack`） | **「どのコンポーネントが SQL を実行したか」は証明できる**（`06d` Gate B・本PoCでも 13/13 帰属）。しかし「その結果が**どの表示値になったか**」は語らない |
| 同じコンポーネント名であること | **証明にならない。** ケースG が反例である。`LinG` は SQL を実行し、かつ値を描くが、両者は無関係である |
| ソースの静的解析（本PoCで追加） | **証明ではない。推定（L2）である。** ただし参照の連鎖を根拠として提示できる |

**結論**: 描画と SQL 実行を結ぶ実測の手段は存在しない。本PoCでも作れていない。
結べるのは **L2 の推定**だけである。

#### (2) 「`derives` が不要」という説明は正しいか

**ノードの有無としては正しい。関係の有無としては誤りである。**

`derives` は `02a` 3.5.1 で **レスポンスのキー → `PropBindingSite`** と定義されている。
`rsc-direct` には**レスポンス（JSON）そのものが存在しない** — 取得結果はプロセス内の
JavaScript の値のまま props へ渡る。したがって `derives` の始点ノードが無く、
**この関係をそのまま構成することはできない。** 設計文書の記述はここまでは正しい。

しかし、`derives` が担っていた**問い**は消えていない。
「取得結果のどの項目が、この表示値になったか」は `rsc-direct` でも必要であり、
未解決のまま残る。PoC-02 の実測（② と ②'' の切断）は、まさにこの穴である。

> **`derives` が無いことは、`derives` が表していた無知が無いことを意味しない。**
> ノードが1つ減った結果、**関係の種別が変わった**だけである。

#### (3) 必要な関係は別の種類のものか

**そうである。** 本PoCは次を提案する（`02a` 3.5.1 への追加提案。**設計文書は変更していない** — 第1.4節）。

| 種別 | 値 | 定義 | 既定レベル | 根拠 |
| --- | --- | --- | --- | --- |
| 関係 | **`supplies`** | **`ComponentDef`（値を描いた）→ `ComponentDef`（取得を実行した）**。この表示値は、その取得の結果から来ている | **L2**（昇格しない） | `static-analysis`（既存の取得手段。新設していない） |

`derives` との違い:

| | `derives` | `supplies`（提案） |
| --- | --- | --- |
| from | レスポンスのキー | 値を描いたコンポーネント |
| to | `PropBindingSite` | 取得を実行したコンポーネント |
| 成立する経路 | `client-fetch` / `server-action` | **`rsc-direct`** |
| 由来の列 | 別に `maps` が要る | **ホップの `candidates[]` が持つ**（`02a` 3.5.3） |
| レベル | L2 | L2 |

`rsc-direct` では `maps`（`DbColumn` → レスポンスのキー）も構成できない — 対応づける
相手のノードが無いためである。よって `rsc-direct` が必要とするのは
**`derives` + `maps` の2本ではなく、`supplies` 1本**である。
**ゼロ本ではない。**

#### (4) 直接 DB 取得だから確度が高い、と言えるか

**言えない。3つの実測・解析が、いずれも否定する。**

| # | 根拠 | 内容 |
| --- | --- | --- |
| 1 | **最弱環が変わらない** | `client-fetch` の最弱環は `derives` / `maps`（ともに L2）。`rsc-direct` の最弱環は `supplies`（L2）。**ホップ数は減るが、いちばん弱いところの値は同じ L2 である。** 経路の確からしさは最弱環だけが決める（OBS-10）ので、確度は上がらない |
| 2 | **裏付けの材料はむしろ少ない** | `client-fetch` では応答 JSON という**実在する中間成果物**があり、値を読まずにキー構成だけを照合する余地がある（`01b` Q-04.1 方式4「構造照合」）。`rsc-direct` にはその成果物が**存在しない**。照合できる相手が1つ減っている |
| 3 | **減ったホップは実測の区間だった** | `rsc-direct` で消えるのは `derives`（L2）だけでなく `requests`（L0）と `handles`（L1）でもある。**実測できていた区間が2つ減り、推定が1つ減る。** 実測／推定の比は改善しない |

PoC-02 の実測の言い方を借りれば、**「ホップは減ったが切断は減っていない」**。
本PoCはそれに1つ足す — **切断を埋めたのは推定であって、実測ではない。**

> なお、`03` 4.6節は既に「UX として `rsc-direct` を肯定的に表示してはならない」と
> 定めており、その理由の4番目に「較正されていない。PoC-04 でのみ検証できる」と書いてある。
> **本PoCの結論は、その禁止を追認し、根拠を与えるものである。** UX 側の修正は要らない。

#### (5) 本PoCで静的解析が `rsc-direct` のほうがよく効いたこと

ケースA〜G（すべて `rsc-direct`）では 20 箇所中 8 箇所を1列に確定できた。
一方、既存の `client-fetch` 経路（`/listings`）では **0 箇所**である（`useState` で連鎖が切れる。第4.4節）。

**これは「`rsc-direct` のほうが確度が高い」ことを意味しない。**
解析手法（AST による参照の連鎖）が届く範囲の差であって、観測性レベルの差ではない。
どちらも結論は L2 である。混同してはならない。

## 2. 採用した静的解析方式

### 2.1 2つの情報源を組み合わせる。役割が違い、互いを補強しない

```
L1相当  実行された SQL の SELECT 句の構文解析
        → 「その取得が返す行には、どの鍵があり、各鍵の由来はどの列か」
L2      TypeScript の AST ＋ 記号解決による参照の連鎖
        → 「この表示値は、その行のどの鍵を参照しているか」
────────────────────────────────────────────────────────
結論    L2（推定）。**実測の SQL を使っても昇格しない**
```

**なぜ実測の SQL を使うのか。** ソースに書いてある SQL 文は、
(a) 動的に組み立てられると存在せず（補助ケースX）、
(b) 書いてある文と走った文が同じとは限らない。
`01b` Q-04.2 C-7 の「実行時トレースがあれば静的解析の最大の弱点である動的クエリを回避できる」を
そのまま実装した。**逆向きには使っていない** — 実測の SQL は列の解決にだけ使い、
参照の連鎖の根拠にはしていない。

### 2.2 実装（`poc/runner/lib/lineage.mjs`）

TypeScript Compiler API で `src/` 全体の `Program` を作り、JSX の子の式から**前向きに**たどる。
抽象値は次の8種である。

| 種別 | 意味 | 候補になるか |
| --- | --- | --- |
| `qres` / `rows` / `row` | 取得結果のオブジェクト／行の集まり／行1つ | ならない |
| **`field`** | 行の1列（鍵つき） | **なる（1件）** |
| **`anyfield`** | 行のどれかの列（**キーが動的**） | **なる（その SQL の全列）** |
| `tuple` | `Promise.all` の結果 | ならない |
| `props` | コンポーネントの props オブジェクト | ならない（`.x` でたどる） |
| `literal` | ソースに書かれた定数 | **ならない** |
| `unknown` | 追えなかった（理由つき） | **ならない** |

たどる構文:

| 構文 | 扱い |
| --- | --- |
| 変数の初期化子 | たどる。**ただし一度でも代入し直される変数は `unknown`** |
| 分解束縛（`const { rows } = …`） | たどる。**別名（`{ rows: list }`）も経路として記録する** |
| 配列の分解束縛 + `Promise.all` | 添字で要素を選んでたどる |
| `arr.map((row) => …)` のコールバック引数 | 反復元の要素としてたどる |
| props（`function C({ label })` / `props.x`） | **その C を描いている JSX すべてを探し、属性式の和をとる。1つに絞らない** |
| メンバ参照 / 添字参照 | 鍵が定数なら `field`、動的なら **`anyfield`** |
| 三項演算子 | **`whenTrue` と `whenFalse` の和。条件式は見ない**（第2.3節 R3） |
| `??` / `\|\|` / `&&` | 左右の和（結果はどちらか一方の値そのもの） |
| テンプレート / 二項演算 / 単項演算 | 和をとり、**加工済みの印**を付ける |
| 関数呼び出し | **白表（`PURE_CALLS`）のみ通す。それ以外は `unknown`**（第2.3節 R4） |

**スコープは TypeScript の記号解決に任せている。** 名前の文字列比較をしていないため、
同名の別変数は構造的に別物になる（ケースD で実測）。

### 2.3 誤対応を作らないための保守規則

**この6つが本PoCの芯である。** どれも「わからないときは候補を出さない」側に倒している。

| # | 規則 | 防いでいる誤り | 実測した効き目 |
| --- | --- | --- | --- |
| R1 | 追えない式は `unknown` にし、候補を出さない | 推測での接続 | `x-outside` / `g-env` |
| R2 | **三項演算子の条件式は見ない。分岐の判定に使った列は由来ではない** | 条件に現れた列を表示値の由来にする | **`e-inline`**（最重要の罠） |
| R3 | 固定値になる経路が1本でもあれば「確定」にしない | 条件次第で定数になる値を列に断定する | `e-orconst` |
| R4 | **白表に無い関数呼び出しは、引数を通さず `unknown`** | 引数を捨てる関数（`outsideLabel()`）を素通りさせる | `x-outside` |
| R5 | **実行された SQL を観測していない取得の列は候補にしない** | 走っていない問い合わせの列を由来にする | 未読み込みページの12箇所がすべて `none`（第4.5節） |
| R6 | **参照の鍵が SELECT 句に無ければ候補を出さない。テーブルも主張しない** | 名前の一致だけでの接続 | **`g-shadow`**（局所変数名が列名と同じ罠） |

### 2.4 根拠に使っていないもの

| 使わなかったもの | 理由 |
| --- | --- |
| **値の一致** | 必要条件であって十分条件ではない（`01b` Q-04.0 #3）。そもそも値を読んでいない |
| **実行時刻の近さ** | `06c` / `06d` と同じ規律。時間窓は実装すらしていない |
| **SQL 文の一致** | 同じ文が複数箇所から出る題材が実在する（`06d` 3.1 の `/rsc-dup`） |
| **ソース上の SQL リテラル** | 動的 SQL では存在しない。書いてある文と走った文は別物である |
| **ページのパス・DOM 上の近さ・コンポーネント名の一致** | ケースG が反例である |

## 3. 推定できる関係 / 推定できない関係

### 3.1 推定できる

| 関係 | 条件 | レベル |
| --- | --- | --- |
| 表示値 → 取得結果の1列 | 参照の連鎖が解け、加工も分岐も動的キーも無く、実測 SQL の SELECT 句に鍵がある | **L2** |
| 表示値 → 取得結果の複数列（候補） | 連鎖は解けるが、連結・分岐・動的キーで1つに決まらない | **L2** |
| 表示値 → テーブル（列は不明） | 連鎖は解けるが列が決まらない（`SELECT *` / 別名のない集計）。`01b` Q-04.5 代替1 | **L2** |
| SQL の別名（`AS`）の先の実列 | SELECT 句の `as` と `column` を分けて持つ | **L2** |
| props の別名・多段の受け渡し | 子の JSX 使用箇所をすべて集めて和をとる | **L2** |
| 同名の別変数の区別 | TypeScript の記号解決 | **L2** |

### 3.2 推定できない（本PoCで候補を出さないと決めたもの）

| # | 関係 | 理由 |
| --- | --- | --- |
| 1 | **表示値と列の値が一致すること** | 値を読んでいない。読んでも十分条件にならない |
| 2 | **実行時にどちらの分岐を通ったか** | ソースの形からは決まらない。候補を複数のまま残す |
| 3 | **動的キーがどの列を指したか** | 同上。その SQL の全列を候補にする |
| 4 | **`SELECT *` の列** | 実行された SQL からも決まらない。テーブルまでに落とす |
| 5 | **解析範囲（`src/`）の外で作られる値の由来** | ライブラリ内部を追わない |
| 6 | **白表に無い関数を通った値の由来** | 本体が引数を捨てうる |
| 7 | **`useState` / `fetch` の応答を経由した値の由来**（`client-fetch`） | 第4.4節。**MVP の主経路がここで切れる** |
| 8 | **再代入される変数を経由した値の由来** | 初期化子だけを見ると嘘になる |
| 9 | **JSX スプレッド属性（`{...props}`）を通った props** | どの属性がどこから来たか決まらない |
| 10 | **`maps`（カラム → 応答項目）** | `rsc-direct` に応答が存在しない。対応づける相手が無い |
| 11 | **`derives`（応答のキー → props）** | 同上。始点ノードが無い（第1.2節） |
| 12 | 集計・式の由来列（`count(*) AS n` 等） | 1つの列に帰属しない。テーブルまでに落とす |

### 4.3 とくに重要な3つの実測

**(1) `e-inline` — 条件の判定に使った列は、表示値の由来ではない**

```tsx
<p data-poc-field="e-inline">{row.plan === '標準プラン' ? '標準' : '拡張'}</p>
```
`row.plan` はソース上に現れる。素朴な実装は `listings.plan` を由来にする。
**本PoCは候補を出さない。** 三項演算子の条件式を評価対象から外しているためである（R2）。

**(2) `g-shadow` — 名前の一致は根拠にならない**

```tsx
await pool.query('SELECT code, region FROM poc.listings ORDER BY id LIMIT 1');
const region = '表示用の固定ラベル';
<p data-poc-field="g-shadow">{region}</p>
```
同じコンポーネントに `region` 列を取る SQL があり、局所変数も `region` である。
**本PoCは候補を出さない。** `region` の宣言は文字列リテラルの初期化子に解決され、
取得結果への参照が一つも無いためである（スコープ解決は TypeScript に任せている）。

**(3) `d-same-name-a` / `d-same-name-b` — 同名変数を取り違えない**

```tsx
{a.rows.map((row) => <li data-poc-field="d-same-name-a">{row.code}</li>)}   // poc.listings
{b.rows.map((row) => <li data-poc-field="d-same-name-b">{row.name}</li>)}   // poc.regions
```
どちらも `row` だが、別々の SQL・別々のテーブルに解決した。

### 4.4 既存の `client-fetch` 経路ではどこで切れるか（**母数の外**）

| 表示箇所 | 正解 | 結果 | 切れた場所 |
| --- | --- | --- | --- |
| `/listings` の `region`（`src/app/listings/page.tsx:17`） | `listings.region` | **候補なし** | `call-not-whitelisted:useState` |

**これは誤答ではないが、MVP の主経路がこの方式では届かないことを意味する**（第11章）。

| 実測の関係は実測として表示 | `observabilityOf(source)` だけが観測性を決める。アダプタは観測性を書けない |
| 静的解析に基づく関係は推定として表示 | `static-analysis` は `SOURCE_LEVEL` で L2。**実測 SQL を併用しても昇格する経路が型の上で無い** |

## 8. データ保護の検証

> 設計方針は PoC-01 / 02 / 03 / 05 と同じ。**集めてから消すのではなく、集めない。**

### 8.1 収集しないもの

| 禁止項目 | 本PoCでの状態 |
| --- | --- |
| 実際に表示された値 | **持たない。** 保持するのは文字数と文字種（`{chars, cls}`）だけ。テストで形まで固定 |
| レスポンス本文 | 入る場所が無い（スキーマに存在しない） |
| DB の行データ | **読んでいない。** 由来の判定に値を一切使わない |
| SQL のパラメータ値 | 取得時点で除去（`redacted` に件数だけ残す） |
| Cookie / 認証情報 / 接続文字列 | 計装側の許可リストで落とす |
| 実案件のソース・DB | 使っていない。隔離した架空アプリとローカルの使い捨て PostgreSQL のみ |

### 8.2 静的解析に固有の論点 — ソースをどこまで持ち出すか

**これは PoC-04 で初めて出た論点である。** 静的解析はソース全体を読むため、
記録に何を残すかを別に決める必要がある。

| 項目 | 決めたこと |
| --- | --- |
| 解析の場所 | **ローカルのプロセス内だけ。** 外部サービスへ送信しない（送信する経路を実装していない） |
| 記録に残すソース | **「描いている式」1つだけ**（例 `row.region`、最大90文字・改行なし）と、`06d` 以来の「照合した1行」。**ソース全文・ファイルの中身を持たない**。テストで長さと改行の有無まで固定 |
| ファイルパス | プロジェクトルートからの相対パス。**絶対パスを残さない**（テストで `/Users/` を禁止） |
| 参照の連鎖（trail） | ファイル名と行番号、props 名、メソッド名のみ。**値も式の全文も含まない** |
| 外向き通信 | 観測結果に `localhost` / `127.0.0.1` 以外の URL が現れないことをテストで確認 |

### 8.3 検証

`tests/poc04.spec.mjs` 第17節で、`docs/06e-poc04-matrix.json` と `src/data/observation.poc04.ts` の
全文に対して次を検査している（いずれも**通過**）。

接続文字列 / DB のパスワード / Cookie / Authorization / アクセストークン / パスワード /
**表示された値（DB の行データに実在する地名）** / 絶対パス / 本文を持つ項目 / 行データの配列 /
`localhost` 以外への URL。

さらに計測ランナー自身（`poc04.mjs`）が、書き出し前に同じパターンで自己検査して落ちるようにしてある。

### 9.3 母数が小さいことの明示

`01b` Q-04.3 は「難易度別に分類した**50個**の画面要素」を題材に指定している。
**本PoCの母数は 20（+ 補助3 + 参考1）であり、満たしていない。**
指示 第3節のケースA〜G に合わせて題材を構成したためである。

したがって「**誤答率 0%**」は、**20箇所についての実測**であって、
母集団の誤答率が 2% 以下であることの証拠にはならない。
20箇所で誤答0なら、真の誤答率の95%信頼上限はおよそ **14%** である（`1 - 0.05^(1/20)`）。
**`01b` Q-04.4 の「誤答率2%以下」を統計的に主張するには、母数が1桁足りない。**
これが第10章を「成功」ではなく「条件付き成功」とする主因である。

## 10. 判定

### 10.1 基準ごとの判定

| 基準 | 結果 | 判定 |

| 誤答率（全体）2%以下 | **0%（0/20）** | **成功**（ただし母数が小さい — 第9.3節） |

| 既存686件の回帰 | 686/686 | **成功** |

### 10.2 判定: **条件付き成功**

**成立したこと**

1. ケースA〜G の全20箇所で**誤った候補を1件も提示しなかった**。危険な9箇所（条件分岐の固定値・列名と同名の局所変数・無関係な SQL・範囲外の関数・走っていない SQL）で、すべて推定を控えた。
2. 単純な対応・props の別名・多段の受け渡し・同名変数・SQL の別名・動的 SQL の6種で、**由来を1列に確定できた**（8/20）。
3. 加工・条件分岐・動的キーでは**候補を複数のまま残し**、すべて正解を含んだ（7/7）。
4. `SELECT *` では**テーブルまでに粒度を落とした**（`01b` Q-04.5 代替1 が実際に機能することの実証）。
5. 推定を**実測へ格上げしていない**。キャンバス上で実測と推定が混ざらず、証拠が無い場合は切断のまま残る。
6. `rsc-direct` の設計矛盾に、実測と解析で裏付けた結論を出した（第1章）。

**条件（これらが満たされるまで「成功」としない）**

| # | 条件 | 理由 |
| --- | --- | --- |
| **1** | **母数が `01b` Q-04.3 の 50 要素に足りない（20）** | 「誤答率0%」を精度の主張にできない（第9.3節） |
| **2** | **`client-fetch` 経路で1箇所も到達できていない** | MVP の主経路である。`useState` で連鎖が切れる（第4.4節） |
| **3** | **確度ラベルの較正が未判定** | `02` 9章の「導入可否は PoC-04 の後」という宿題が解けていない（第9.4節） |
| 4 | 題材が1アプリ・1ファイル構成に偏っている | Context / 状態管理ライブラリ / Server Action / ストリーミングを含まない |
