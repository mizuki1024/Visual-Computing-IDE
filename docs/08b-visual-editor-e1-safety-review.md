## 3. 外部変更との競合（F-03）

### 3.1 方式の比較（調べた結果）

| 方式 | 何を防ぐ | 限界 | E1.1 |
| --- | --- | --- | --- |
| 内容ハッシュの照合（E1） | 照合の時点までの変更 | 照合〜rename の間は検出できない。照合は「読んだ時点」の事実 | 残す（早く止める） |
| アドバイザリロック（`flock`・鍵ファイル） | **協調する**書き手どうし | 外部のエディタ・整形・AI はこの鍵を見ない。Node の標準 API に `flock` は無い（鍵ファイルの O_EXCL で代用） | 鍵ファイルを残し、取り除きの競合を直した。エンジンどうしの取り決めにすぎない |
| 強制ロック（mandatory locking） | 全ての書き手 | Linux 5.15 で削除。macOS に無い | 使えない |
| ファイルリース（Linux `F_SETLEASE`） | 他のプロセスが開いたことを知る | Node の標準 API に無い。所有者でないと取れない | 使えない |
| fd による同一性の確認（`fstat` の dev・inode） | 名前が別の実体へ置き換わったこと | 確認と使用の間は残る | 照合・退避リンクの照合に使う |
| 原子的な置き換え（一時ファイル＋`rename`） | 途中で切れた内容（停止しても前か後のどちらか） | **条件付きでない**（名前が指す実体が何であっても置き換える） | 残す |
| `renameat2(RENAME_EXCHANGE)`（Linux）・`renamex_np(RENAME_SWAP)`（macOS） | 置き換えた元の実体を確実に手元に残す | Node の標準 API に無い（ネイティブ拡張が要る） | 使えない |
| `renameat2(RENAME_NOREPLACE)`・`link()` | 「名前が無いときだけ作る」 | 「名前が X を指すときだけ置き換える」ではない | `link` を退避リンクに使う |
| `O_TMPFILE`＋`linkat` | 名前の無い一時ファイル | Node の標準 API で `linkat(AT_EMPTY_PATH)` が無い | 使えない |
| **退避リンク（E1.1 で採用）** | 照合〜rename の間の**同じ実体への上書き**、照合〜退避リンクの間の**置き換え** を rename の**後**に検出し、外部の版へ戻す | link と rename の間の置き換え・置き換え前から開いていた fd | 採用（第3.2節） |

**存在しない保証を前提にしない**: POSIX にも Node にも「名前が実体 X を指しているときだけ置き換える」原子的な操作は無い。したがって、協調しない外部の書き手との競合を通常のファイル操作で 0 にはできない。E1.1 は「検出できる範囲を最大にし、検出したら外部の版を残す」ことと、「検出できない範囲を結果に明示する」ことを目標にした。

### 3.2 退避リンクの手順（`fsio.replaceSourceFile`）

```
 照合（範囲・同一性・内容）→ 一時ファイル（O_EXCL・fsync）→ 最後の照合 → パスの照合（同一性）
   → link(書き込み先, .orig.tmp)        ← 置き換える元の実体に2つ目の名前（リンク数 2 の間、他のエンジンは範囲の検査で止まる）
   → rename(一時ファイル, 書き込み先)    ← 原子的。書き込み先の名前は常にどちらかの内容
   → .orig.tmp を開いて照合: 照合した inode か・内容が基準とバイト一致か
        一致   → .orig.tmp を外す（外す直前・直後の fstat で、開いていた fd からの書き込みも見る）→ 読み直し → replaced
        不一致 → 外部の変更（上書き、または退避リンクの前の置き換え）。自分の実体に .ours.tmp を付けてから
                 rename(.orig.tmp, 書き込み先) で外部の版を戻す → conflict-restored（自分の版が書いた内容のままなら .ours.tmp を外す）
```

* 「照合」を rename の**後**に、**置き換えた元の実体そのもの**（名前ではなく inode）に対して行う。パスで書く外部の書き手は rename の後には元の実体に届かないので、上書きはすべて照合の前に終わっている。
* 外部の版を戻す途中に、自分の版へさらに外部が書いた場合も `.ours.tmp` に残し、要確認にする（S4(h)）。
* ハードリンクを使えないファイルシステムでは書かない（`snapshot-failed`・`failed`・`written: false`）。

### 3.3 検出できる競合・防げる競合【実測: `edit-safety-unit`】

| 外部の操作 | いつ | 修正前 | 修正後 |
| --- | --- | --- | --- |
| 上書き（O_TRUNC） | 下書きの後・照合の各段 | 書かない | 書かない（S2） |
| rename による置き換え | 下書きの後・照合の各段 | 書かない | 書かない（S2） |
| 上書き | 最後の照合の後（RV03） | **committed・外部の変更を失う** | 書いていない扱い・外部の版が残る（S4(a)） |
| 上書き | 退避リンクと rename の間 | （段が無い） | 外部の版へ戻す・`conflict`・`transient`（S4(b)） |
| rename による置き換え | 最後の照合の後 | **committed・失う** | 書かない（パスの照合）（S4(c)） |
| 上書き | rename の直後 | `failed`・`written: true` | `uncertain`・外部の版が勝つ（書き戻さない）（S4(e)） |
| 開いていた fd からの書き込み | 退避リンクの照合の後・外す前 | （段が無い） | 外部の版へ戻す（S4(f)） |
| 外部の版へ戻す途中の、自分の版への上書き | — | — | 両方の外部の版を残し要確認（S4(h)） |
| 同じエンジンの2つ目の適用 | 置き換えの途中 | （段が無い） | `busy`（S3(a)） |
| 同じジャーナルの別のエンジン | 置き換えの途中 | （段が無い） | `busy`（S3(b)） |
| 別のジャーナルのエンジン | 最後の照合の後に committed | **両方 committed・片方を失う** | 後のエンジンは書かない・先の変更が残る（S3(c)） |
| 別のジャーナルのエンジン | 退避リンクと rename の間 | （段が無い） | リンク数 2 で範囲の検査が止める（S3(d)） |

### 3.4 検出できない競合（再現条件・影響・緩和策）

| # | 競合 | 再現条件 | 影響 | 緩和策 |
| --- | --- | --- | --- | --- |
| R-1 | link と rename の間の、rename による外部の置き換え | 外部のエディタ（JetBrains の safe write・vim の一部の設定・`git checkout`・一部の AI ツール）が、IDE の `link()` と `rename()` の**連続する2つの系呼び出しの間**に、自分の rename を完了する。試験は同期点で再現（S4(d)）【実測】 | 外部の版が失われ、エンジンは `committed` と報告する | 窓は連続する2つの系呼び出しの間だけ（E1 の窓は照合・lstat・ハッシュを含む）。`committed` の `assurance.undetectable` に `replace-save-between-link-and-rename` を必ず入れる。E4 以降の画面で「上書きしない」を保証の語にしない |
| R-2 | 置き換えの前から開いていた fd で、確定の後に書く | 外部のプロセスが書き込み先を開いたまま（O_TRUNC で開いていない）にし、IDE の確定の**後**にその fd で書く（S4(g)）【実測】 | 書かれた内容は名前の無い元の実体へ行き、失われる。エンジンは `committed` | rename による保存全般（外部のエディタ自身のものも含む）と同じ性質。開いた時点で切り詰める書き手（多くのエディタ・`fs.writeFile`）は、開いた時点で内容が変わるので照合で検出される。外す直前・直後の fstat の変化は検出して内容を残す（`late-write`） |
| R-3 | 確定の後の外部の書き込み | 確定の後なら何でも | `committed` は確定の時点の事実。いまの内容は保証しない | 検証（`verified`）は受け取った時点のいまの版を照らす。`outcome.staleSinceVerification` |
| R-4 | 鍵の同時の取り除きの3者の競合 | 古い鍵を3つのプロセスが同時に取り除き、退けた鍵を戻す前に3つ目が新しい鍵を作る | 2つのプロセスが鍵を持ちうる | 2者の競合は直した（S7 鍵の競合）。3者はエンジンの同期点が無く再現していない【推定】 |

| 確かめたこと | 結果 |
| --- | --- |
| パスの検査の時点 | 解決（第1段）・下書き（第2段）・適用（第3段）・書き込みの入口・最後の照合・退避リンクの直前・書いた後【静的】 |
| `realpath`・`lstat` の使い方 | 根の実体から葉まで1区間ずつ `lstat`（リンクを拒否）・`realpath` と字面の一致・`realpath(root/src)` の中【静的】 |

| 差し替えへの耐性 | 修正後（Linux）: 8段のどこで差し替えても src/ の外には**一時的にも**作らない（各段で外のディレクトリを観測）【実測: S5】 |
| `rename` の時の同一性 | 退避リンクの直前にパスの照合。rename は固定したディレクトリの中の名前どうし |

## 5. 安全性の脅威モデル

| 主体 | 例 | 想定 | E1.1 で守ること | 守れないこと |
| --- | --- | --- | --- | --- |
| A1 利用者のエディタ・整形・AI（悪意なし・協調しない） | VS Code・Prettier・JetBrains・vim・Claude Code 等 | 同じファイルへ任意の時点に保存する（上書き・置き換えの両方） | 第3.3節の表 | 第3.4節 R-1・R-2 |
| A2 IDE のエンジン（協調する） | 同じ IDE の別の操作・同じジャーナルの別のプロセス | 鍵に従う | 直列（`busy`） | 鍵の3者の競合（R-4） |
| A3 別の IDE のエンジン（鍵を共有しない） | 別の作業ディレクトリの IDE が同じプロジェクトを編集 | 協調しない書き手と同じ | リンク数 2 の間の拒否・退避リンク | R-1 と同じ窓 |
| A4 停止 | SIGKILL・電源断・OOM | 任意の段で止まる | 書き込み先は常に前か後。復旧は確定を取り消さず、外部の内容を持つファイルを消さない（S7・S8） | 持ち主を確かめられない記録（PID の再利用・別のホスト）は自動で片付かない |
| A5 同じ権限の敵対的なプロセス | 対象プロジェクトの依存・スクリプト | src/ のディレクトリを差し替え続ける | src/ の外に作らない・書かない（Linux） | 固定したディレクトリそのものの移動。そもそも同じ権限で任意のファイルを書けるので、IDE が「代理で外へ書く」ことだけを防ぐ（混乱した代理人にならない） |
| A6 対象のアプリ（プレビューの中のスクリプト） | 悪意のある題材 | 偽の検証の報告を送る | 報告の中身の照合（第2節 F-05） | 報告の出所（E2） |
| A7 IDE 側の記録の改ざん | `.ide-runtime` を書き換えられるプロセス | ジャーナルを書き換える | 形・txId と一時ファイルの名前の照合・範囲の検査（S6） | 記録を書き換えられる時点で IDE と同じ権限がある |

**信頼の境界**: 対象プロジェクトは IDE と同じ OS の利用者の権限で動く。IDE はそれより強い保護を作れない。E1.1 が目指すのは、(1) IDE が src/ の外へ書かない・作らない、(2) IDE が利用者の変更を**黙って**失わない（失いうる窓は結果で明示する）、(3) 確かめられない結果を成功と言わない、の3つ。

## 6. 修正した内容

### 6.1 外部変更との競合（`fsio.ts`）

* 退避リンク（第3.2節）・外部の版の書き戻し（`restoreExternal`）・外す前後の fd の照合（`verifySnapshot`）。
* 最後の照合の後・退避リンクの直前に、パスでもう一度範囲と同一性を照合する（置き換えを rename の前に見つける）。
* 読み出しは `O_NOFOLLOW|O_NONBLOCK` で開いた fd から（リンクを辿らない・FIFO で止まらない）。照合は inode も比べる。

### 6.2 ディレクトリの差し替え（`fsio.ts`）

* 書き込み先の親ディレクトリを `O_RDONLY|O_DIRECTORY|O_NOFOLLOW` で開き、開いた実体が検査したもの（dev・inode）と同じかを確かめる。
* Linux では以後の操作をすべて `/proc/self/fd/<fd>/<名前>` で行う。使えない OS ではパスで行い、E1 と同じ事後の確かめを残す。結果に `pinned` を返す。

### 6.3 結果の契約（`engine.ts`）

* `uncertain` を追加（書いた／不明。従来の `failed`・`written: true|'unknown'`）。`failed` は書いていないものだけ。
* `committed` に `assurance`（`displacedOriginalVerified`・`readBackVerified`・`directoryPinned`・`undetectable`）。
* `conflict` に `transient`・`kept`・`needsAttention`。

### 6.4 鍵（`fsio.acquireLock`）

* 古い鍵を取り除くとき、鍵を別名へ rename してから、それが古いと判断した鍵と**同じ inode・同じ中身**かを確かめる（inode の番号は消した直後に再利用されうるため中身も比べる — 試験で inode だけの照合では不十分なことを確かめた）。違えば link で戻して取らない。
* 鍵に nonce を入れ、外すときは自分の nonce の鍵だけを消す。
* 適用・取り消しの第3段の照合を、鍵を取ってから行う。

### 6.5 復旧・ジャーナル（`engine.ts`・`journal.ts`・`fsio.ts`・`scope.ts`）

* 退避リンク（`.orig.tmp`）・自分の版（`.ours.tmp`）の名前は一時ファイルの名前から決まる（ジャーナルの形は変えない）。
* 復旧は最初に、失うものが無いもの（書き込み先と同じ実体／基準・書いた内容とバイト一致）だけを外す。それ以外は残し、適用前へ戻さず `refuse`・要確認。
* 片付けは親ディレクトリだけを検査する（書き込み先のリンク数が 2 で止まった場合も片付く）。
* ジャーナルの `tempName` は `.<書き込み先の名前>.vcide-edit-<txId>.tmp` と一致するものだけ、`recovery.tempName` は同じ規則の `-r<n>` だけを受け付ける。
* 起動時の自動復旧は**組み込んでいない**（責務を広げていない。E2 の引き継ぎ）。

### 6.6 検証（`engine.outcome`）

* `staleSinceVerification` を、検証した文書が描いた全ファイルのいまの版で判断する。

### 6.7 試験

## 7. 修正できない制約

1. **条件付きの rename が無い**（第3.4節 R-1）。Node の標準 API に `renameat2`・`renamex_np` が無く、POSIX にも「名前が X を指すときだけ置き換える」操作が無い。ネイティブ拡張を足せば RENAME_EXCHANGE で窓をさらに縮められるが、依存を増やさない方針のため E1.1 ではしない（判断事項 — 第10.2節）。
2. **開いていた fd の書き手**（R-2）。Linux のリースは Node に無い。
3. **協調しない書き手に効くロックは無い**（Linux の強制ロックは削除済み）。
4. **/proc の無い OS** ではディレクトリを固定できない（第4節）。macOS・Windows・ネットワークファイルシステムは動かしていない。
5. **持ち主を確かめられない記録**（PID の再利用・別のホスト）は安全側で何もしないため、自動では片付かない。プロセスの開始時刻を記録すれば Linux では PID の再利用を見分けられるが、E1.1 では入れていない（E2 の起動時の復旧と合わせて決める）。
6. **検証の報告の出所**（E2）。

## 10. E2 に進むための条件

### 10.1 E2 が E1 から使うもの（API・データの契約）

* 書き込みはすべて `EditEngine` を通す。`ApplyResult` は第3.5節の6種類。E2 の同期の層は `committed` を「成功」と扱わず、`uncertain` を取り消しの対象にしない。
* `committed.assurance.undetectable` を、E4 以降の画面の文言の根拠にする（「外部の変更を上書きしない」を保証の語にしない）。
* `conflict.transient` は、HMR で一瞬だけ自分の変更が描かれうることを意味する（E2 のプレビューの同期で、その描画を「適用済み」と誤認しない）。
* 選択は `ElementSelection`（v3）をそのまま渡す。第2・3段の照合は鍵の中で行う。

### 10.2 E2 開始前に決めること

1. **macOS での扱い**: /proc で固定できない（`directoryPinned: false`）。E2 で書き込みを有効にするのを Linux に限るか、固定なしでも許すか（第4節）。
2. **利用者への伝え方**: R-1・R-2（第3.4節）を、E4 の適用の画面でどう伝えるか。
3. **ネイティブ拡張の可否**: `renameat2(RENAME_EXCHANGE)` で R-1 をさらに縮めるか（依存が増える）。
4. **別の IDE どうしの鍵**: 作業ディレクトリが違う IDE はジャーナルと鍵を共有しない（S3(d)）。利用者ごとの共通の場所に鍵を置くか。
5. **持ち主の確かめ方**: プロセスの開始時刻を鍵・ジャーナルに記録して PID の再利用を見分けるか。

### 10.3 E2 への引き継ぎ

| 項目 | 引き継ぐこと |
| --- | --- |
| 編集後の選択の引き継ぎ | ジャーナルの `afterRev`・`target.afterFingerprint.{hash,structureHash}`。HMR の後の DOM の版が `afterRev` と一致し、その位置の要素の指紋が `afterFingerprint` と一致するときだけ引き継ぐ。`conflict.transient`・`uncertain` の後は引き継がない |
| プレビューと revision の対応付け | 検証の報告の `document.token` を previewGateway の文書の識別子（`SelectionDocument.token`）と接続（nonce・起動インスタンス）に結ぶ。`document.sourceRevs` はサーバーが対応表から作る。E1.1 はこの結び付けを**完了扱いにしていない** |
| 起動時の復旧 | `recover()` は呼ばれていない。編集を有効にした起動で1回呼ぶ。`needsAttention`・`refuse`・残したファイル（`.orig.tmp`・`.ours.tmp`）・別のホストの記録を画面に出す。残したファイルは外部の変更を含みうるので、自動で消さない |
| 検証の後の変化 | `outcome.success` は検証の時点の事実。`staleSinceVerification` を画面で必ず出す |
| 試験 | E2 で書き込みの層を変えるときは `edit-safety-unit` を回す。同期点の名前（`before-rename`・`snapshot-linked`・`renamed`・`snapshot-verified`・`restore-linked`）は試験の契約 |
