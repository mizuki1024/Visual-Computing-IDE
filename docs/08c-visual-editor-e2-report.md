### 1.3 E1.1 から引き継ぐ契約（今回も守った。第6節で照合）

1. 書き込みはすべて `EditEngine` → `fsio.replaceSourceFile` を通す（`src/server/edit/` で fs に書くのは `fsio.ts` だけ）。
2. `committed` を無条件の安全の保証として扱わない（`assurance.undetectable` を常に返す）。`committed` は検証の前は成功ではない。
3. `uncertain` を成功として扱わない・取り消しの対象にしない。
4. `transient`（外部の版へ戻した conflict）・`uncertain` の後に選択を引き継がない。
5. 編集後の選択は `afterRev` と `afterFingerprint` の両方が一致する場合だけ引き継ぐ。
6. `ApplyResult` の種類は 6 つ（committed・refused・conflict・busy・failed・uncertain）。08b 第3.5節の表と一致させる。
7. 既定で無効（`VCIDE_EDIT_E1_WRITE=1` のときだけ）。画面・API の入口は無い。
8. 復旧は終わった記録（committed・failed）・持ち主の生きている記録に触れない。外部の内容を持つファイルを消さない。

## 2. 実装した内容

### 2.1 書き込みの可否に OS を加えた（方針 1）

* `config.editWriteGate(env, platform)`: `{ enabled, reason: 'enabled' | 'env-not-set' | 'platform-unsupported', detail }`。`EDIT_WRITE_PLATFORMS = ['linux']`。
* `editWritesEnabled` はこれを使う。適用・取り消し・復旧・書き込みの入口（`fsio.replaceSourceFile`・`cleanupRecordedArtifacts`）はすべて同じ判定を通る。拒否の文言は OS を挙げる。
* 理由: macOS は `/proc/self/fd` でディレクトリを固定できず、一時ファイルが一瞬 src/ の外に作られうる（08b 第4節）。**これは残るリスクの解消ではなく、確かめていない OS で書かないための取り決め。**

### 2.2 起動時の復旧: 読むだけの点検とファイルを変える復旧の区別（指示 3）

| 関数 | 変えるもの | 書き込みが無効のとき | 有効のとき |
| --- | --- | --- | --- |
| `inspectRecovery()`（新） | **何も変えない**（鍵を取らない・ディレクトリを作らない） | 点検 | 点検 |
| `recover()`（E1.1） | ソース・src/ の一時ファイル・ジャーナル・鍵 | `dry-run`（読むだけ。E1.1 と同じ） | 仕様どおりの復旧 |
| `startupRecovery()`（新） | 有効なときだけ `recover()` | `inspect-only`（点検だけ・`recovery: null`） | 点検 → `recover()` を1回 |

* 点検の各記録: `plannedAction`（none・mark-failed・restore-before・refuse）・**`effects`（その処理が変えるもの: `journal`・`artifacts`・`source`）**・`leftovers`（いま残っているファイル）・`ownerAlive`・`ownerCheck`（`start-time`・`pid-only`・`other-host`・`self`）・`needsAttention`。全体に `mutates: false`・`unreadable`（形の合わない記録の名前）・`prunable`・`retained`（理由つき）。
* 点検の予定は `recover` の判断と同じ規則で作る。`recover` は先に「失うものが無い」一時ファイル・退避リンクを外してから対象を見るため、退避リンクが残って書き込み先のリンク数が 2 の記録では、外した後の状態を**読むだけで**予測する（`fsio.predictRecordedCleanup`・`inspectTargetContent`）。試験の途中で、この予測が無いと点検（refuse）と実際の処理（mark-failed）が食い違うことを見つけて直した【実測】。点検は点検の時点の事実で、実際の復旧は改めて判断する。
* **判断できない記録・残ったファイルを自動で消さない**: 保存期間の整理（`#prune`）は、終わった・期間を過ぎた記録のうち、`needsAttention` の記録と、src/ の下に記録のファイル（一時ファイル・退避リンク・自分の版）が残っている記録を消さない（`retained`）。形の合わない記録は従来どおり読まない・消さない。変更前のコードは要確認の記録を消していた【実測: 第6.1節】。
* 製品の起動からは呼んでいない（D-4）。

### 2.3 持ち主の識別に開始時刻（方針 5）

* `fsio.processStartId(pid)`: `<boot_id>:<tick>`（`/proc/sys/kernel/random/boot_id` と `/proc/<pid>/stat` の 22 番目）。読めなければ null。
* `fsio.judgeOwner(owner, facts)`（純粋な規則）: 別のホスト → 確かめられない（生きている扱い）／pid が死んでいる → いない／記録といまの開始時刻が両方ある → 一致すれば いる・違えば いない（**PID の再利用**）／どちらかが無い（E1.1 の記録・/proc の無い OS）・記録の形が違う → pid だけ（生きていれば いる）。
* ジャーナルの `owner.start`・鍵の `start` に記録する。`parseJournal` は `start` が無いか、正しい形のときだけ読む。
* 範囲: E2 の仕様の「起動時の復旧」（S-5）に要るため、復旧の持ち主の判断と鍵の古さの判断に使った（D-6）。別のホストの記録（コンテナの作り直しでホスト名が変わる）は従来どおり何もしない。

### 2.4 自分が書いた変更の後の選択の引き継ぎ（`carrySelection(txId, DOM の選択)`。07d 3.3）

**読むだけ。** 次をすべて満たすときだけ、適用後の版の新しい対象（以後の下書き・適用は通常の3段の照合を通る）を返す。1つでも外れれば `carried: false`・`reselect: true`・理由。

| 段 | 条件 | 外れたときの理由 |
| --- | --- | --- |
| 1 | txId の記録がこのプロジェクトの `state: 'committed'`（transient の conflict・uncertain・failed・prepared・applying は対象外） | `not-committed`・`tx-unknown` |
| 2 | `kind: 'apply'` で、記録に `afterFingerprint` がある（取り消しの記録は引き継がない） | `not-carriable` |
| 3 | その適用を取り消していない | `reverted` |
| 4 | DOM の選択の版（`data-vcide-rev`）＝ `afterRev` | `dom-not-at-after` |
| 5 | 探索の7段の照合（DOM の版＝対応表の版＝ファイルの版）を通り、同じ要素（識別子・ファイル・行・列・タグ・コンポーネント） | `target-unresolved`・`target-moved` |
| 6 | いまのファイルの内容が書いた内容（`afterHash`）とバイト一致 | `changed-since-commit` |
| 7 | その位置の要素の指紋が `afterFingerprint` の `hash` と `structureHash` の両方と一致 | `fingerprint-mismatch` |

* 探索モードの照合（`anchors.resolveSelection`）は変えていない（読むだけで使う）。
* 外部変更が入った後に、外部の保存が書いた内容とバイト一致の状態へ戻った場合は、内容で判断するので引き継ぐ（試験 Y4 で明示）。

### 2.5 ApplyResult の種類の照合

`APPLY_STATUSES = ['committed','refused','conflict','busy','failed','uncertain']`。型の上で `ApplyResult['status']` と同じ集合であることを確かめ（片方だけ変えると型検査で止まる）、試験 Y5 が `engine.ts` の型・08b 第3.5節の表と照合する。**6 種類で一致**【実測】。

### 2.6 検証の結果の出所の明示（指示 2）

## 4. document.token と previewGateway の対応（実測。`edit-sync-e2e`）

製品の `PreviewGateway`（`.libjs` の本物）を、使い捨ての題材の `next dev` の前に置き、Chromium の2幅（1440・375）で中継の URL から `/properties` を開いた。中継の記録は `RelayObserver` で受け、判定には探索の `bindDocument` をそのまま使った。

| 確かめたこと | 結果 |
| --- | --- |
| 文書に中継の識別子（`data-vcide-doc`・32桁の16進）がある | ある（2幅とも） |
| その識別子を持つ通信が中継の記録にちょうど1件（`/properties`・200・document） | 1件（2幅とも） |
| 幅ごとに別の文書か | 別（識別子が違う） |
| 適用の前、探索の `bindDocument` は同定するか | `identified`（2幅とも） |
| 中継の記録に無い識別子 | `token-not-in-session`（同定しない） |
| HMR の後、文書の識別子は変わるか | **変わらない**（文書を読み直していない） |
| HMR の後、中継を通った同じパスの RSC の取り直し | **2件**（2幅の取り直しの合計。どちらの文書が取り直したかは中継の記録で区別できない【推定: 1幅につき1件】） |
| HMR の後、探索の `bindDocument` は同定するか | **`unidentified`（`refetched-after-document`）**（2幅とも） |
| HMR の後の文書の識別子も、中継の記録の1件にあるか | ある（偽の識別子ではない） |

**読み方**: 中継の識別子は「中継がいまの起動で実際に返した文書」の同定に使える。しかし、探索の規則は HMR の後の DOM を「描き直された可能性がある」として同定しないため、編集の検証（HMR の後に測る）にはそのまま使えない。**どの規則で結ぶかは決めていない（D-3）**。E2 のこの段の検証の結果は `documentBinding: 'not-checked'` で、`verified` を中継との結び付けの証拠として扱わない。

この試験の選択は、中継のスクリプトの select の知らせ（iframe の親が要る）ではなく、試験が同じ規則で DOM から作った。ページは iframe ではなく最上位で開いた。**製品の画面・MessagePort・nonce を通した経路は確かめていない。**
