## 4. 変更したプロトコル

**探索のプロトコルは変えていない**: `PROTOCOL_VERSION = 3`・`ElementSelection`・`parseSelection`・`parseAgentMessage`（hello / connect / mode / select / 場所の知らせ）はそのまま。探索の `select` に項目を足すと探索側は今までどおり捨てる（E21-19）。

編集の知らせは同じ MessagePort・同じ版・同じ nonce の上の**別の種類**（`ev: 1`）:

| 向き | 種類 | 中身 | 検査 |
| --- | --- | --- | --- |
| IDE → スクリプト | `edit-observe` | `req`（求めの番号） | スクリプト側で source・v・nonce・kind・ev・req の形 |
| スクリプト → IDE | `edit-observation` | `req`・`state`（ok / detached / none）・`selection`（ElementSelection v3）・`rect`・`style`（許可した 23 の見た目の値）・`doc`・`soft`・`rsc {started, settled}`・`vw`・`vh` | 型・版・拡張の版・nonce・求めの番号・知らないキー・`selection` は `parseSelection`・スタイルの名前は許可の一覧・値は英数と記号の一部（URL・文字列が入らない）・`settled ≤ started` |
| ページ → 中継 | RSC の要求のヘッダ `x-vcide-doc` | 要求を出した文書の識別子（32桁の16進） | 中継が形を見て記録し、**開発サーバーへ渡さない** |

* スクリプトは**求められたときだけ**答える（自分からは送らない）。探索の画面（LivePreview）は `edit-observe` を送らないので、探索の受け口に新しい知らせが届くことは無い。
* 送らないもの: 本文・属性の値・フォームの値・Cookie・className（E2.1 では使わない）。位置はブラウザから受け取らない（サーバーが決める）。矩形・スタイルは画面の表示用で、サーバーへは送らない。
* fetch の包み: 同じ origin への `rsc: 1` の要求にだけ名乗りを足し、数える。それ以外は元の fetch をそのまま呼ぶ。`editSync` が無効なら包まない（既定のスクリプトは1バイトも変わらない）。

## 5. アートボードごとの接続管理

* 画面: アートボードごとに `MessageChannel`・nonce・接続の識別子（乱数）・開発サーバーの起動・IDE の起動（`ideBoot`）を持つ。hello は**その iframe の window から**来たものだけを受け、探索のプレビューの iframe とは混ざらない。新しい文書が答えたら前の port を閉じる。
* 受け口（`acceptEditPortMessage`）: 別のアートボードの接続・いまの接続でない port（古い MessagePort）・nonce の違い・開発サーバーの入れ替わり・IDE の起動し直しを、それぞれ理由をつけて捨てる。
* サーバー: アートボードごとに「いまの接続（識別子・文書の識別子・起動・登録の時刻）」を1つ持つ。新しい接続は前の接続と**その選択を置き換える**（選択は失効し、戻さない）。別のアートボードが登録した文書の識別子は登録しない。要求ごとに IDE の起動・開発サーバーの起動・接続・文書・ビューポート（1440×900 / 375×812）を確かめる。
* 状態: 画面は 接続中（connecting）・接続済み（connected）・切断（disconnected）・再接続（reconnecting）、選択は selected・verifying・stale・unresolved・disconnected と、文書更新（`document-replaced`・`not-selected`）・選択失効（stale）・再選択が必要（`data-reselect`）を区別する。
* 同じルートでも同じ文書として扱わない（文書の識別子は応答ごと。E21-03・E21-13）。同じ JSX の要素を選んでも、DOM のインスタンス（アートボード・文書・何番目か）とソースの定義（ファイル・行・列・識別子）を別の項目で返す（E21-02）。

## 6. 選択状態と版の同期

選択（`select`）: 起動・接続・文書・ビューポートの検査 → 文書の照合 → `readonlyEdit.resolveTarget`（探索の7段: DOM の版＝対応表の版＝読み直したファイルの版・タグ・位置の再計算・ソースの読み直し、＋書き込み範囲・内容のハッシュ・指紋）。通れば `selected`。版の違い・別の要素は `stale`、識別子が無い等は `unresolved`。

| 状態 | 意味 |
| --- | --- |
| selected | 編集対象（ソースの定義）に結び付いた。文書の照合は別の段で、未確認のこともある（selected を文書の確認に格上げしない） |
| verifying | 画面が観測・照合を待っている |
| stale | 前の選択はもう使えない（ソースの変更・別の要素・DOM から外れた・文書の更新）。**再選択が必要。戻さない** |
| unresolved | 選んだ要素の描画位置を特定できない（探索の照合の理由つき） |
| disconnected | 起動・接続・文書・ビューポートのどれかが合わない |

## 7. HMR の後の扱い

* 画面は selected の間 1.5 秒ごとに、選んだ DOM ノードをスクリプトに描き直させ（`edit-observe`）、`recheck` する。サーバーは `reresolveTarget`（選んだ時点の版・内容・指紋と、いまの DOM・対応表・ファイルがすべて一致するときだけ通す）。
* **1つでも違えば stale で、その選択は二度と selected に戻らない**（同じ要求を何度送っても。E21-09）。新しい版の要素として引き継がない。選び直せば新しい対象（新しい版・指紋）として解決する（E21-10）。
* `carrySelection()`（自分が書いた適用の後だけの引き継ぎ。afterRev・afterFingerprint の hash と structureHash・いまの内容・対応表・`uncertain`・`conflict.transient` の除外）は**変えていない**。E2.1 の画面・API からは呼ばない（適用の道が無い）。HMR の通常の再描画を自分の適用と混同しない。
* 状態の更新だけの再描画（Client Component のボタン）では版が変わらないので selected のまま【実測】。ソースの変更・同じ行と列への別の要素は stale【実測】。

| ケース | 結果（実ブラウザ） |
| --- | --- |
| 1 同じ要素のソースの更新（Server Component・Client Component） | stale → 選び直すと新しい版で selected |
| 2 別の要素への置き換わり（同じ行・列に `<span>`） | stale（前の `<button>` を維持しない）→ 選び直すと `<span>` |
| 3 ページの読み込み直し | 新しい接続・前の選択は失効 |
| 4 Client Component の再描画（状態の更新だけ） | selected のまま |
| 5 Server Component の取り直し（RSC） | 両方の文書が自分の取り直しとして照合済み。変えたファイルの選択は stale・変えていないファイルの選択は selected |
| 6 古い MessagePort | 画面もサーバーも受けない |
| 7 一方のアートボードだけの更新 | 他方の接続・選択・文書の照合は変わらない |
| 8 両方の更新 | 両方とも新しい文書・前の選択は失効 |

## 8. RSC の取り直しの識別方法（D-3）

**問題**（`08c` 第4節・L-9）: 中継の記録には、RSC の取り直しを**どの文書が出したか**が無い。探索の `bindDocument` は、同じパスの取り直しが文書の後に1件でもあれば同定しない（安全側）。2枚が同じルートを開くと、他方の取り直しでも同定できない【実測: `tdd-red/before-behavior-probe.log` P1】。

**追加した識別子と観測**:

1. 文書のスクリプトが、自分の文書の RSC の要求に自分の文書の識別子（中継がその文書の応答に付けたもの）を `x-vcide-doc` で名乗る。
2. 中継はそれを読み、その要求の記録に添える（開発サーバーへは渡さない）。台帳は、名乗りが台帳の文書にあれば `initiator`、無ければ「名乗ったが台帳に無い」とする。
3. スクリプトは自分が出した RSC の要求の数（開始・応答の受け取り）を数え、観測で申告する。

**照合の規則**（`bindEditDocument`）:

* 文書: 識別子が台帳の HTML の応答ちょうど1件・パスが一致・2xx を送り終えた・ページ内の遷移が無い・別のアートボードの文書でない。
* 取り直し: 文書の後の**同じパスで出どころの分からない** RSC が1件でもあれば `rsc-unattributed`（未確認）。その文書を名乗る RSC が台帳と申告で同じ数・すべて送り終えていれば `self`、申告の方が多ければ `rsc-pending`（一時的）、台帳の方が多ければ `rsc-count-mismatch`（誰かがこの識別子を名乗った）、失敗があれば `rsc-failed`。**別の文書を名乗る RSC は、この文書の照合を落とさない。**
* 保持の上限で外した記録があれば `ledger-evicted`（推測で埋めない）。

実測（製品の経路）: Server Component の HMR の取り直しは、2枚とも自分の文書を名乗って中継を通った（`self`・各1件）【実測】。Mobile の `router.refresh()` は Mobile の数だけが増え、Desktop は照合済みのまま【実測】。中継へ名乗り無しで RSC を送ると、2枚とも `rsc-unattributed` で未確認になった【実測】。不正な RSC の要求（Next が 500 を返す）は `rsc-failed` で未確認になった【実測: 試験の途中の観測】。

## 9. 検証結果の信頼境界

| 段 | 何で確かめたか | 何を言えるか | 何を言えないか |
| --- | --- | --- | --- |
| 文書 | 中継の台帳（サーバーの記録）と、スクリプトが申告した文書の識別子 | その識別子を持つ HTML の応答が、いまの起動で実際に中継を通った | iframe にいま表示されているのが本当にその文書か（申告はアプリと同じ JavaScript の世界の値） |
| 接続 | 画面の MessageChannel・nonce・接続の識別子・起動、サーバーの登録 | 要求が、そのアートボードのいまの接続・いまの起動から来た | 悪意のあるアプリが自分の iframe の値を偽ること（同じ origin の他方の iframe の値を読むことも含む） |
| 取り直し | 台帳の名乗り＋スクリプトの申告の数 | どの文書の取り直しかを区別できた、または区別できない（未確認） | 名乗りそのものの真正さ（申告） |
| ソース | 探索の7段・内容のハッシュ・指紋（サーバーがファイルを読み直す） | 選んだ要素の版がいまのソース・対応表と一致し、その位置の JSX がその要素 | — |
| 描画 | **確かめていない**（`render: 'not-verified'`） | — | DOM が応答・ソースどおりに描かれたか |

* 文書の照合の水準は `document-identified` か `unverified` だけで、**`verified` という水準は作っていない**（E21-16）。selected を文書の確認に格上げしない。

* ブラウザの時計とサーバーの時計の差は考えていない（同じ機械で実測。クラウドで差がある場合の扱いは E4 の前に決める）。

## 10. 復旧情報の読み取り専用対応（D-4）

* `GET /api/edit-sync/state` が、選んだプロジェクト（実行中でなくても最後に選んだもの）について `inspectRecovery()` を呼び、要確認の記録の数と内容を返す。画面はそれを表示する（「読むだけ。自動で書き戻し・削除はしません」）。

### 15.2 E3「編集用の要素選択」へ進むための条件

E3 は利用者の確認の後に始める。進めるときに決める・作るもの:

1. **編集可能・不可能の判定**: いまの `TargetView.classReason`（className が文字列リテラルでない理由）を E3 の判定の入口にする。条件付き・テンプレート・関数呼び出しの className（`FilterPanel` の題材）・スプレッド・`cn()` 等を「編集不可（理由つき）」に分ける。判定は**ソースの読み直しで**行い、DOM の class から推測しない。
2. **コンポーネント定義と利用箇所**: E2.1 は DOM のインスタンス（何番目か）とソースの定義を分けたが、**どの利用箇所（親のどの JSX）から描かれたか**は区別していない（画面にもそう書いている）。E3 では import の解決と利用箇所の静的走査（EP-04・F-09）を足し、利用箇所が1つに決まらなければ「定義を変える＝全利用箇所に効く」と明示する。
3. **複数箇所への変更影響**: 定義を変えると、同じ定義の全インスタンス（2枚のアートボードの両方）に効く。E3 は影響の数（インスタンス・利用箇所・ファイル）を数え、2枚のアートボードの両方で同じ定義を選んでいることを同期の層で確かめる（いまは別々の対象として解決する）。
4. **動的な className**: 実行時の値（props・state・条件）で決まる className は、E3 では編集不可とし、推測で書き換え先を決めない。
5. **E4 での適用前の検証**: 適用の直前に、E2.1 の `recheck` と同じ照合（版・内容・指紋・文書・接続）をサーバーで通すこと、適用後の検証の報告を `bind-report` の規則でいまの2枚の文書に結び付け、エンジンの判定（`documentBinding`）に組み込むかを決めること、描画の検証（K-2）の方法、R-1・R-2 を適用の画面でどう伝えるか（08b 10.2(2)）、IDE 間の鍵（08c L-5）。
