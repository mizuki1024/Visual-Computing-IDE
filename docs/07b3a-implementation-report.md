## 1. 実装した経路

```
ブラウザ（プレビューの iframe, 中継の origin）
   │ GET /api/listings など（クエリ・Cookie はそのまま転送するが、中継は値を読まない）
   ▼
プレビュー中継（IDE のプロセス内, 7B-1）── 転送したその場で記録 ──→ 観測の台帳（起動ごとのセッション）
   │                                   method / path / クエリの有無 / 種類 / 状態 / 時刻
   │                                   応答の X-Vcide-Trace（読んで**ブラウザへは渡さない**）
   ▼
next dev（IDE が起動。NODE_OPTIONS=--require boot.cjs, POC05_TRACE_HEADER=1, POC05_SERVER_TIMING=0）
   └─ 計装（PoC-01 方式2）→ .ide-runtime/spans/<この起動の runId>.jsonl（スパン・マスク済みの SQL）

IDE の画面 ─ POST /api/runtime/observations {run} ─→ 起動の照合（違えば observation: null と理由）
                                                 → 台帳の通信 ＋ そのトレースのスパンだけ ＋ Phase 6F の SQL 解析
           ← LiveRunObservation ─ adapter.fromLiveRun → validateDataset → layout → ExploreStore.showLive
```

### 2.1 契約への影響（`06g` 第8章の手順に従った）

**関係種別（`RELATION_SPEC`・12件）は変えていない。取得手段を1つ足した。**

| 追加 | 内容 | 反映先 |
| --- | --- | --- |
| `preview-relay`（L0） | IDE のプレビュー中継が転送した HTTP の要求と応答の記録 | `src/lib/model.ts`（`SourceId` / `SOURCE_LEVEL` / `SOURCE_LABEL`）・`02d` 1.3 の表と **1.3.3 節（新設）**・`02a` 3.2 / 3.5.1.1 の表の取得手段の欄 |

`browser-network` を名乗らなかった理由（`02d` 1.3.3）:

- 記録の取り手は**ブラウザではなく中継**である。ブラウザのキャッシュで済んだ通信・別 origin への通信は中継に現れない
- 所要時間は「中継が受けてから送り終えるまで」で、ブラウザが測った値ではない
- 同じ名前にすると、この2つの差が画面から消える

L0 にした理由: 方法・パス・状態は転送した当事者として直接見ている（推論を含まない）。

**この取得手段はどの関係の根拠にもならない**（ノードだけ）。特に `requests`（開始元の帰属）には入れていない — 中継の記録は誰が送ったかを語らない（M1 決定 C を維持）。単体試験で、中継の記録で `requests` を作ると `validateDataset` が拒否することを確かめた。

## 3. 実測と推定の分類

**この段階で作るものは、すべて実測（L0 / L1 / L1相当）である。推定の関係は1本も作らない。**

| 要素 | 取得手段 | 観測性 | 作る条件 | 作らない場合 |
| --- | --- | --- | --- | --- |
| ③ 通信（`HttpExchange`, 観測位置 `browser`） | `preview-relay` | 実測（L0） | 中継が転送した | — |
| `handles` ③→④ | `trace-context` | 実測（L1） | 応答の専用ヘッダのトレース識別子が指すスパンが、いまの起動の収集ファイルにあり、そのスパンのパスが転送したパスと一致する | **作らない。時間の重なりに降格しない**（PoC-01 との違い）。理由を通信の詳細に書く |
| ④ サーバー処理（`Span`） | `trace-span` | 実測（L1） | 同じトレースの Next.js のルート単位のスパン（`AppRouteRouteHandlers.runHandler` / `AppRender.getBodyResult`）。無ければ HTTP の受付スパン | 同上 |
| `executes` ④→⑤ | `trace-span` | 実測（L1） | SQL のスパンが ④ の子孫（同じトレースの親子の連鎖） | 別のトレースの SQL は、時刻・文が同じでも結ばない |
| ⑤ 実行SQL | `orm-instrumentation` | 実測（L1） | 同上 | — |
| `reads` ⑤→⑥ / ⑥ テーブル | `sql-ast-parse` | 実測（L1相当） | 構文解析で決まった、**読み取り**の対象のテーブル | 書き込み先（INSERT / UPDATE / DELETE）は `reads` にしない。解析に失敗・解析器が無いときは作らない |
| `projects` ⑤→⑦ / ⑦ カラム | `sql-ast-parse` | 実測（L1相当） | SELECT / RETURNING 句の結果列で、スキーマ・テーブル・列が決まったもの（Phase 6F） | ORDER BY / WHERE などだけで使う列・集計・`*` は描かず、理由を残す |

**PoC-01 の記録との違い（観測していないものを書かないための違い）**

| | PoC-01（記録済み） | 7B-3A（いまの起動） |
| --- | --- | --- |
| テーブル・カラムの定義 | 情報スキーマに照会（型・NULL・行数） | **照会していない。** 型・NULL・行数は「未取得」と書く（IDE は対象の DB の接続情報を持たない・読まない） |
| トレース識別子が取れないとき | time-window に降格して結ぶ | **結ばない** |
| 通信の取得手段 | `browser-network`（CDP） | `preview-relay` |

**作らないもの（7B-3B 以降）**: ①表示された値・②コンポーネント・`requests`（通信を起こしたコード）・`derives` / `maps`（応答のどの項目がどの値になったか）。キャンバスには通信から「ここより上流は結んでいません（この通信を起こしたコード・表示された値）」の切断を必ず出す。**同じページで起きた・時刻が近い・SQL が一致する、を理由に結んでいない**（単体試験で、同時刻・別トレースの SQL を結ばないことを確かめた）。

## 4. 実行ライフサイクル

| 指示 | 実装 | 確認 |
| --- | --- | --- |
| 開始時に新しい観測セッション | `DevServerManager` が running になった時点で `observations().begin(instance:pid:startedAt)`。引き継いだ起動（IDE の再起動）でも新しく作る | E2E 1・6 |
| 起動をまたいで混ぜない | (1) 中継は転送のたびに**その起動の鍵**を付けて記録し、台帳はいまのセッションと違う鍵を捨てる (2) 収集ファイルは起動ごとに別（7A の runId）で、読むのはいまの起動のものだけ (3) API は起動の鍵が違えば観測を返さない（`observation: null`・`stale-run`） (4) 画面は起動の鍵が変わったら観測と表示を捨てる | 単体 3・5 / E2E 6 |
| 停止後に実測中のように見せない | running 以外の状態でセッションを閉じる。API は観測を返さない。画面は観測の行を消し、キャンバスを元に戻し「実測中ではありません」と書く | E2E 6 |
| 情報が無ければ未観測 | 「まだ通信はありません（未観測）」/「サーバー処理・SQL は観測していません（理由）」/ 通信の詳細に「サーバー処理: 結んでいません — 理由」/「この処理の下で SQL は観測されませんでした」の切断 | E2E 7 / 単体 6 |
| 機密情報を保存しない | 下の表 | 単体 2・5 / E2E 5 |

| 保存しないもの | どこで止めているか |
| --- | --- |
| クエリ文字列の値 | 中継がパスとクエリの有無だけにする（`classifyRelayRequest`）。URL の全体を持たない |
| ヘッダ・Cookie・Authorization | 中継が値を読むのは決めた3つのヘッダだけ（要求 2・応答 1）。その他は**読まずに転送するだけ** |
| 要求・応答の本文 | 中継は本文を記録しない（HTML へのスクリプトの差し込みは 7B-1 のまま） |
| SQL のパラメータ値・リテラル | 計装が取得時点で除去（PoC-01 `mask.cjs`）。E2E で `LIMIT` の数値も残っていないことを確認 |
| 接続文字列・DB のパスワード | 計装の許可リストで落とす。IDE は対象の `.env` を読まない |
| 個人情報・行データ | 取得しない（計装は行を読まない。中継は本文を読まない） |
| 絶対パス | 観測の API に収集ファイルの場所を出さない |

**トレース識別子の公開範囲を狭めた。** 7A の起動は Server-Timing にトレース識別子を載せていた（ページ上の任意のスクリプトが読める — PoC-05 の実測）。7B-3A では専用ヘッダだけにし、**中継がそれを読んでブラウザへは渡さない**。E2E で、ブラウザに届いた応答に `X-Vcide-Trace` も Server-Timing の traceparent も無いこと、ページの中のスクリプトから Resource Timing で読めないことを確かめた。

> **同じ JavaScript の世界のスクリプトを完全には信用できない。** プレビューの中のアプリ自身のスクリプトは、中継が差し込んだスクリプトと同じ文書で動く（7B-2 第6.1節）。7B-3A の観測はページの中のスクリプトから何も受け取らない（中継とサーバーの計装だけで取る）ので、アプリが観測を偽る経路は「実際に通信を送る」ことに限られる。**アプリが送った通信は、アプリが送った通信として正しく記録される**が、それが利用者の操作によるものかは区別しない。

## 9. 未検証事項・残る制約

1. **実物の Codespaces**（7B-1 / 7B-2 から継続）。加えて、https の転送では `Sec-Fetch-Dest` が送られて種類が `document` / `fetch` になるはずだが、確かめていない
2. **題材は `poc/fixture-app` だけ。** 計装（PoC-01 方式2）の束が対象の依存を前提にしている（`pg` / Prisma）。他のドライバ（`mysql2` など）や Edge ランタイムの SQL は観測できない（計装の対象外 — 「SQL は観測されませんでした」と出る）
3. **webpack で起動したプロジェクト**は確かめていない（Turbopack のみ）
4. **中継を通らない通信は現れない**: ブラウザのキャッシュで済んだもの・別 origin への通信・Service Worker が返したもの。HMR の WebSocket も数えていない
5. **サーバーの中から出た通信**（`server-internal`。PoC-02 Gate A）は描いていない。`POC02_UNDICI` を起動先に渡していないため
6. **どのコードが SQL を実行したか**（`queries` / `server-call-stack`）は取っていない。`POC02_CALLSITE` を渡しておらず、ソースマップの戻しも IDE に統合していない。サーバー処理の詳細に「どのコンポーネント・どの行が SQL を実行したかは観測していません」と書いている
7. **カラムの型・テーブルの行数**は取得していない（情報スキーマに照会しない。IDE は対象の DB の接続情報を読まない方針）
8. **キャンバスの配置**: SQL は2本・カラムは5つまで描く。超えた分は数と理由を出す（M1 第5.1節 #4 の M4 の課題のまま）。右上のパネルがキャンバスの右側を覆う（7B-2 から継続）
9. 応答の後に閉じるスパンがあるため、表示した直後に経路が描き足されることがある（観測の取り直しで同じ通信を描き直す）
10. 収集ファイルは起動の間ずっと増える。台帳は最大 200 通信・6 万スパンで打ち切り、超えたら数を出す。長時間の起動での読み取りの重さは測っていない
11. アプリ自身のスクリプトが送った通信も同じように記録される（第4節の注記）。利用者の操作による通信かは区別しない
12. **トレース識別子の専用ヘッダは、アプリのプロセスの中（計装）で付く。** アプリのコードが別の要求のトレース識別子に書き換えることは防げない。
    断る照合を1つ置いた: 識別子が指す受付スパンのパスが、中継が転送したパスと違えば結ばない（単体 6）。同じパスの別の要求のトレースへの付け替えは見抜けない
13. Windows は未確認（7A と同じ。Phase 6F の解析器を絶対パスで読む）

## 10. 次の 7B-3B へ進むか

**7B-3A は成立した。進んでよいと判断する。ただし、次の2点は 7B-3B の最初に決める必要がある。**

| 7B-3B が前提にするもの | 状態 |
| --- | --- |
| いまの起動の通信 → サーバー処理 → SQL → テーブル・カラム（証拠つき） | **成立**（実ブラウザ・実物の DB。`validateDataset` 通過） |
| 起動・停止・再起動で混ざらない | **成立** |
| 選択した要素（7B-2）→ コンポーネント・ソース位置 | 成立（7B-2） |
| **要素と通信を結ぶ証拠** | **まだ無い。** 7B-3A は意図して結んでいない |

7B-3B で決めること:

1. **要素 → 通信の証拠をどこから取るか。** 中継の記録は開始元を語らない（`preview-relay` は `requests` の根拠にならない）。使えるのは PoC-05 の `request-initiator`（ブラウザが記録する呼び出しスタック）だが、**IDE は利用者のブラウザの CDP を持たない。** 代わりにプレビューの中のスクリプトでスタックを取ると、それは同じ JavaScript の世界のアプリが偽れる情報になる。どちらを使うか、使えないなら何を「結べない」と出すかを先に決める
2. **Server Component（rsc-direct）の経路**では、要素 → SQL の証拠は `server-call-stack`（PoC-02）になる。`POC02_CALLSITE=1` を起動先に渡し、サーバー側のソースマップの戻しとソースの読み直しを IDE に統合する必要がある（第9節の6）

client-fetch の G1 / G2（値の由来）は、指示どおり着手していない。
