## 1. 正式化した決定

8件すべてを `02a` / `02d` に反映し、**実装側に機械的な検査を置いた**。
検査は `src/lib/model.ts` の `RELATION_SPEC` と `validateDataset()` であり、`tests/model.spec.mjs` が実行する。

> **表を2つ持たない。** Phase 6F で、SQL の構文解析器が2つあったことが1つの不具合を
> 5つのデータセットへ広げた。同じ失敗を仕様と実装の間で繰り返さないため、
> `02a` 3.5.1節の表と `RELATION_SPEC` は同じ内容であり、**食い違いはテストが検出する。**

### 1.1 決定 A — `queries` を関係として採用する

| | 内容 |
| --- | --- |
| 関係 | `queries` : **`DataAccessSite` → `SqlStatement`** / L1相当 / `server-call-stack` |
| 帰属の粒度 | **ソース位置まで。** 囲む `ComponentDef` は文脈として表示するが、端点ではない |
| インスタンス | **同定しない。** 「同じコンポーネントが複数回描かれる場合、どの描画が対象かは同定していません」を帰属のノードに必ず表示する |
| 取得位置の証拠 | ホップが `endpoints.from`（`file` / `line` / `col` / 囲むコンポーネント名）を持つ。**ノードの識別子は行までだが、端点は列まで持つ** |
| 重複の確認 | `executes` とは**始点の型が違う**（`Span` ではない）。`requests` とは**終点の型が違う**（`HttpExchange` ではない）。既存の関係で表現できない |

> **なぜ始点が `Span` では足りないか。** Next.js の描画スパンは**ルート単位**であり、
> コンポーネント単位ではない。1ページに2本の SQL があるとき、スパンの親子は
> どちらがどのコードかを語らない（`06d` 2.2 の実測）。

### 1.2 決定 B — `supplies` の端点を2つのソース位置にする

**`ComponentDef → ComponentDef` としては正式化しなかった。**

| | 内容 |
| --- | --- |
| 関係 | `supplies` : **`DataAccessSite` → `PropBindingSite`** / L2 / `static-analysis` |
| 向き | **データの供給方向で定義する**（取得位置が値を供給する） |
| 探索の向き | 画面の経路は利用者の逆向き探索（描画位置 → 取得位置）に進む。ホップは `orientation: 'against-data'` を宣言する |
| 端点の証拠 | `endpoints.from` = 値を描いた位置（`lineage.site`、列まで）、`endpoints.to` = 取得を呼んだ位置（**実測した呼び出しスタックの frame**） |

#### 名称の衝突と、採った最小変更案

**`06f` 3.4節は端点の名として `DataFetchSite` を提案していたが、その名のオブジェクトは `02a` に存在しない。**
存在するのは `DataAccessSite`（`02a` 3.1節。種別に `ORM呼び出し / 生SQL / fetch / 外部SDK` を既に持つ）である。

| 案 | 影響範囲 | 採否 |
| --- | --- | --- |
| `DataFetchSite` を新設する | `02a` 3.1 / 1.1（レイヤー図）/ 2章（識別子）に新しいオブジェクトが増える。`DataAccessSite` と役割が重なり、**どちらを使うかの判断が実装のたびに要る** | **不採用** |
| **既存の `DataAccessSite` を端点にする** | `02a` 3.1 に注記（3.1.1節）を足し、2章に識別子の形式を1行足すだけ。既存の属性（種別・ソース位置）がそのまま使える | **採用** |

あわせて次の2点を `02a` に明文化した。

| # | 内容 |
| --- | --- |
| 1 | `DataAccessSite` の既定レベル L2 は、**静的解析で見つけた場合**の値である。実測した呼び出しスタックから同定した場合、そのサイトの観測性は L1相当である（観測性はオブジェクトごとに取得手段から決まる — `02d` 1.1節） |
| 2 | 識別子は**列まで**持つ（`bind:<パス>:<行>:<列>` / `fetch:<パス>:<行>:<列>`）。実測では1行に「要素の位置」と「式の位置」が同居する（`src/app/lin-a/page.tsx:18:11` の `<li>` と `:18:54` の `{row.region}`）。行だけでは両者を区別できない |

#### 実装側で足した2つの成立条件

表示ノードは `ComponentDef` であり、`PropBindingSite` を**担っている**に過ぎない。
担えていないまま線を引くと「コンポーネントからコンポーネントへ」に戻る。そこで条件を2つ足した。

| # | 条件 | 満たさない場合 |
| --- | --- | --- |
| 5 | 静的解析が見た**描画位置**と、要素識別子が指す位置が、**同じファイルの同じ行**であること | 関係を作らない（従来どおり切断） |
| 6 | 静的解析が見た**取得の呼び出し位置**と、計装が実測した呼び出し位置が**一致**すること | 関係を作らない。一致しなければ、静的解析は別の取得について語っている |

**既存の3データセットは両方を満たす**（`lin-a`: 描画 18行 / 取得 12行、実測の frame も 12行。`lin-c`: 20行 / 13行、frame も 13行）。
したがって表示は変わらない。

### 1.3 決定 C — `requests` の観測と帰属を分ける

| 区別 | 対象 | 取得手段 | 観測性 |
| --- | --- | --- | --- |
| **通信そのものの観測** | `HttpExchange` **ノード** | `browser-network` / `trace-span` | L0 / L1 |
| **開始元の帰属** | `requests` **関係** | `request-initiator` / `server-call-stack` のみ | **L1相当** |

- `requests` : **`DataAccessSite` → `HttpExchange`** / L1相当。`02a` の「L0 / 根拠: ブラウザ側の計測」を改めた。
- **ブラウザのネットワーク計測は、この関係の根拠として認めない。** 計測が与えるのは通信の存在であって、誰が始めたかではない。
- **スタックが取れなければ関係を作らない。** ノードは作る。「通信は観測できたが、誰が始めたかは分からない」が正しい状態である（OBS-05）。
- 実装は既にこのとおりだった（`flows` / `rsc-svc` にのみ `requests` がある）。M1 で**仕様が実装に追いついた**。

### 1.4 決定 D — 取得手段を関係種別とは別の軸として管理する

`request-initiator` / `server-call-stack` を `02d` 1.3節の表に正式に追加した（ともに **L1相当**）。
「L1相当」とした根拠（記録の出所・写像の決定性・独立した照合・使わないもの・成立しない場合）は `02d` 1.3.1節に書いた。

| | 関係種別（`02a` 3.5.1） | 取得手段（`02d` 1.3） |
| --- | --- | --- |
| 決めるもの | from / to の型 | 観測性 |
| 多重度 | 1つの関係が複数の取得手段を持ちうる | **1つの取得手段が複数の関係を支えうる** |

実例: `server-call-stack` は `requests` と `queries` の**両方**を支えている（`06d` 6.1節）。
したがって「`server-call-stack` という関係を追加する」という整理は誤りである（`06f` I-1）。

### 1.5 決定 E — `HttpExchange` に観測位置を持たせる

| 値 | 意味 |
| --- | --- |
| `browser` | ブラウザのネットワーク記録に現れた通信 |
| `server-internal` | **サーバーの中から出た通信。ブラウザには現れない** |

関係は分けない（始点・終点の型が同じであるため）。属性で区別する。
実装では `kind: 'http'` のノードに必須とし、検査する。

> **区別をモデルに置かず文言だけで行うと、2種類を同じ数え方で合計する実装が書ける。**
> 「ブラウザから見える通信が1件ある」と読める表示は、`rsc-direct` の成立条件
> （ブラウザから見える API 通信が 0 件）そのものを壊す。

### 1.6 決定 F — 流入とデータの合流を区別する

| 値 | 意味 | 実測の例 |
| --- | --- | --- |
| `shared-object` | **別々の関係（または根拠）が同じ対象を指しているだけ。** データは合流していない | ⑤ への `executes` + `queries`（4件）／③' への `invokes` + `requests`（1件）／③ への `derives` + `maps`（合成1件） |
| `data-merge` | 実際に複数の入力が1つの出力になった | **無い。MVP では作れない** |

`data-merge` を作れない理由: 「2つの列がこの1つの表示値になった」と言うには、
表示値が両方に依存している証拠が要る。本プロダクトは**表示された値も取得した行も読まない**（NFR-20）。
静的解析が得るのは「この式が2つの参照を含む」であり、それは**候補が2つある**こと（`multiple-candidates`）であって合流の観測ではない。
実装は `data-merge` を拒否する。

> **流入が2本あることを確度の根拠にしない。** 2本の線はそれぞれ自分の観測性を持つ (OBS-09)。
> 「2つの根拠があるから確かだ」は較正を要する主張であり、A段階では行わない。

### 1.7 決定 G — `ComponentInstance` を導入しない

MVP 段階で新しいインスタンス識別機能は導入しない。**代わりに制約を明文化した**（`02a` 3.1.1節）。

| # | 制約 | 実装側の担保 |
| --- | --- | --- |
| 1 | 関係の帰属の粒度は `definition` か `source-location` のいずれか。**実行時インスタンスへの帰属を作らない** | `RELATION_SPEC` に `attribution` を持ち、`runtime-instance` を拒否 |
| 2 | 帰属のノードは「この位置のコードであることまでです。同じコンポーネントが複数回描かれる場合、どの描画が対象かは同定していません」を必ず表示する | 文言を `ATTRIBUTION_SCOPE_NOTE` に1か所だけ置き、テストで固定 |
| 3 | 1つの JSX が複数の DOM 要素を生んだ場合、個数を出し「どの使用箇所が何番目を描いたかは観測していません」を併記する | 同上 |
| 4 | インスタンスの同定を前提とする機能は MVP の対応範囲外として `SupportMatrix` に載せる | **未実施。** `06f` 4.4節の表に「同じコンポーネントの複数インスタンス → どのインスタンスかを主張しない」として既出。`SupportMatrix` は画面がまだ無いため **M4 で載せる**（第5.2節 #8） |

**`06f` 3.5節の案A（`ComponentInstance` を置く）は採らない。** 観測できない区別を仕様が要求することになる。

### 1.8 決定 H — RSC の確度に関する較正されていない主張を削除した

| 文書 | 削除・撤回した記述 | 置換 |
| --- | --- | --- |
| `02a` 3.5.2 表 | `rsc-direct` の最弱環欄「（`derives` が無い分、経路が短く確度は相対的に高い）」 | 最弱環を **`supplies`** に改め、括弧内を削除 |
| `02a` 3.5.2 注記 | 「`rsc-direct` の経路が `client-fetch` より確度が高くなりうる…推論ホップが1つ減るため」 | 実測4点（最弱環は L2 のまま／切断は減っていない／中間成果物が無く裏付けは少ない／減ったホップに実測区間が含まれる）と、**経路種別の間に確度の順序を置かない**という決定 |
| `02` 4.2 注記 | 同趣旨 | 撤回の追記（結論「短さを情報不足として表示しない」は維持） |

### 1.9 決定 #9 — 構成の照合だけでは `maps` を作らない

`02d` 1.3.2節に明文化した。

| 決めたこと | 内容 |
| --- | --- |
| 単独で根拠にしない | **`maps` / `derives` を `structural-match`（キー構成の照合）単独で作ってはならない。** キー名の一致は、コード上でその値がそこへ渡ったことの確認ではない |
| 確認できない場合 | **関係を作らず、切断を維持する**（OBS-05） |
| 実装 | `RELATION_SPEC` の `insufficientAlone` に `structural-match` / `value-match` を置き、唯一の根拠である場合を拒否する |

> **これは `06f` 4.3節 V2 の合否条件を上書きする。** V2 は「応答のキー名だけを読み、
> SELECT 句の別名・列名の集合と照合して1対1が立つか」を見る検証だったが、
> **1対1が立っただけでは `maps` を作らない。** 同名の別物（同じ名前の別テーブルの列、
> 加工を通ったキー）を排除できないためである。V2 の位置づけは
> 「候補の絞り込みが成立するかの確認」に下がり、`maps` の生成条件は
> **コード上のデータ伝播を確認できること**になる。

## 6. Phase 7A が使うモデル契約

Phase 7A は次の4つを前提にしてよい。**いずれも機械的に検査される。**

| # | 契約 | 置き場所 |
| --- | --- | --- |
| 1 | **関係種別は12件の閉じた集合**であり、各関係は from / to の型・既定レベル・認める取得手段・帰属の粒度・上限を持つ | `src/lib/model.ts` の `RELATION_SPEC`（＝ `02a` 3.5.1節の表） |
| 2 | **表示ノードの種別は関係の端点の型ではない。** 端点は `ObjectTypeId` であり、`PropBindingSite` / `DataAccessSite` / `ResponseKey` は他のノードに担われる | `NODE_OBJECT_TYPE` / `ENDPOINT_CARRIER` / `SITE_IDENTIFIED` |
| 3 | **向き・端点のソース位置・流入の意味・通信の観測位置は、ホップ／ノードが明示的に宣言する。** 省略は違反である | `ModelHopInput.{orientation, endpoints, convergence}` / `ModelNodeInput.exchangeScope` |
| 4 | **観測性の決定点は `observabilityOf` だけである。** 関係の表はレベルを宣言するが、観測性を上書きしない | `observabilityOf` / `validateDataset` の R4 |

新しいデータセット・新しい変換を書いたら、`validateDataset()` を通すこと。
**検査は違反を1件で打ち切らず、全件返す。**
