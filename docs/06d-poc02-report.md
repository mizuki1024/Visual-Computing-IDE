## 2. 採用した方式

### 2.1 Gate A — undici の計装による W3C Trace Context の伝播

`06c` 第3章 #2 の原因は「Next.js の `fetch` が `node:http` を通らない」ことだった。
undici は `diagnostics_channel` を通るので、そこに計装を入れると**送信側の client
スパンが作られ、要求に `traceparent` が注入される**。受け側の `instrumentation-http`
はそれを取り出し、入口スパンの親にする。

```
Server Component
  └ fetch('http://127.0.0.1:3300/rows')
      └ [app] undici client スパン ──traceparent──▶ [svc] 入口スパン（親 = client スパン）
                                                      └ [svc] pg.query スパン
      ※ 3つは **同じ traceId** である
```

対応付けの成立条件（**1つでも欠けたら対応付けない**。`poc/runner/lib/propagate.mjs`）:

| # | 条件 | 役割 |
| --- | --- | --- |
| 1 | 送信側に client スパンがある | 判断の根拠 |
| 2 | 受信側の入口スパンの `parentSpanId` が、その client スパンの `spanId` と一致する | **判断の根拠** |
| 3 | `traceId` も一致する | **判断の根拠**（別トレースならここで落ちる） |
| 4 | 子の入口スパンが2本以上なら、対応付けない | 判断の根拠 |
| 5 | 宛先のパスが食い違わない | **補強のみ。これだけでは対応付けない** |

> **時刻は記録するが、判断には一切使っていない。** 時間窓による対応付けは
> 比較用に別の関数として実装し、**それが誤って繋ぐ場面が実在すること**を数字で示した（第3.3節）。

### 2.2 Gate B — 「スパンが始まった場所」と「呼び出した場所」は違う

**これが本PoCで最も重要な実測である。**

Next.js の描画スパン（`next.span_type = AppRender.getBodyResult`、名前 `render route (app) /rsc-db`）は
**ルート単位**であり、コンポーネント単位のスパンは存在しない。したがって
「このスパンの子孫に SQL がある」ことは、**どの Server Component が実行したかを何も語らない**。

最初に試したのは「SQL スパンが始まった瞬間の呼び出しスタックを取る」方式だった。**これは失敗した。**

```
SQL スパン開始時のスタック（実測）
  Tracer.startSpan
  Client.handleConfigQuery       ← ここでスパンが作られる
  Client.query
  PendingItem.patchedCallback    ← **接続プールが空いたときのコールバックの中**
  BoundPool._acquireClient
  （ユーザーのコードのフレームは1つも無い）
```

| 計測 | 全4条件とも |
| --- | --- |
| SQL スパン開始時のスタックに、アプリのコードのフレームがあった件数 | **0 / 8** |

`pool.query()` を呼んだ時点ではスパンは作られない。接続プールが空いた時点の
コールバックの中で作られる。**呼び出し元は、その時点でスタックから消えている。**

そこで、**呼び出しの入口でスタックを取り、OpenTelemetry のコンテキストに載せて運ぶ**。

```js
// poc/fixture-app/ide-instrumentation/otel.cjs（抜粋）
Pool.prototype.query = function (...args) {
  if (context.active().getValue(CALLSITE_KEY)) return orig.apply(this, args);  // 外側だけ
  const ctx = context.active().setValue(CALLSITE_KEY, { at, frames: captureFrames(60) });
  return context.with(ctx, () => orig.apply(this, args));
};
// スパン開始時に、そのスパンの**親コンテキスト**から取り出す
onStart(span, parentContext) { parentContext.getValue(CALLSITE_KEY) }
```

> **これは親子関係が正しく付くのとまったく同じ仕組みに相乗りしている。**
> 計装がコールバックを包んでコンテキストを復元するから、親子が付く。
> 同じ復元で、呼び出し元のスタックも一緒に戻ってくる。**別の推測を足していない。**

### 2.3 帰属の成立条件 — PoC-05 の4段をサーバー側へ移した

```
① 呼び出しの入口（Pool.query / globalThis.fetch）で取ったスタック
      ↓  上から順に、注入範囲のソースへ戻せるフレームを探す
② ソースマップで元の位置へ戻す                  → src/app/rsc-db/page.tsx:12:24
      ↓
③ そのソース行を読み直し、本当にデータ取得の呼び出しがあるかを確かめる
      ↓                                        → const r = await pool.query('SELECT …')
④ その行を囲むコンポーネントを、**2つの独立した情報源**で決める
      ソースの読み直し（TypeScript で再解析） ＝ RscDb
      ビルド時マニフェストの関数範囲           ＝ RscDb   → 一致したときだけ採用
```

**4つが揃わなければ、ノードも関係も作らない。** 理由を付けて「特定していません」と返す
（`no-entry-callsite` / `no-app-frame` / `source-line-mismatch` / `component-not-agreed`）。

> **SQL 文の一致も、時刻の近さも、ページのパスも、根拠に使っていない。**
> 「同じページで、この時刻に、この SQL が走った」は、本PoCの帰属に一度も現れない。

### 2.4 関係種別と取得手段の追加提案（`02a` / `02d` への提案）

| 種別 | 値 | 定義 | 既定レベル | 根拠 |
| --- | --- | --- | --- | --- |
| 取得手段 | `server-call-stack` | サーバー側でデータ取得の呼び出しの入口に記録したスタックを、ソースマップで戻し、ソース行で照合したもの | **L1相当** | 計装自身の記録（推測ではない）＋ 決定的な写像。`request-initiator`（`06c` 4.4節）のサーバー版 |
| 関係 | `queries` | **ComponentDef → SqlStatement**。そのコンポーネントのコードがこの SQL を実行した | **L1相当** | 同上 |

> `02a` 3.5.1節の `executes` は **Span → SqlStatement** であり、始点の種別が違う。
> **同じ名前を流用していない。** `02d` 1.3節・`02a` 3.5.1節への追加提案であり、
> **設計文書は更新していない**（`06c` 4.4節と同じ扱い）。
> 実装は `src/lib/model.ts` にコメント付きで入れてある。

### 3.3 「別トレースになったときに、誤って同一経路にしない」ことの実測

伝播を入れない条件は、`06c` 第3章 #2 の状態そのものである。
受け側の処理は**別トレースの根**になる。このとき3つの規則を比べた。

| 規則 | 伝播あり | **伝播なし** |
| --- | --- | --- |
| **親子関係 + トレースID（採用）** | 5/5 を正しく対応付け | **0 件。1本も繋がない** |
| 宛先のパスの一致だけ | 候補1件 | 候補1件（**別トレースのスパンを指す**） |
| パスの一致 + 区間の内包（時間窓） | 候補1件（答えと一致） | **候補1件（別トレースのスパン）** |

| 伝播なしの条件での計測 | Turbopack | webpack |
| --- | --- | --- |
| **時間窓なら繋いでしまう通信** | **4 件** | **4 件** |
| そのうち受け側が**別トレース**だった件数 | **4 件**（＝全部） | **4 件** |
| **採用規則が繋いだ件数** | **0 件** | **0 件** |

- **時間窓は、伝播が成立していないときに「1件に絞れた」ように見える。** しかしその1件は
  別のトレースの根であり、同じ経路ではない。**時間窓は「対応付けてはいけない通信」を対応付ける。**
- 応答が返らない通信（空きポート）では、時間窓でも候補は 0 件だった。受け側が存在しないためである。
- `06c` 第3.2節の結論（「時間窓はいつも間違うのではなく、間違うときに間違ったと分からない」）が、
  **サーバー間でも同じように成り立つ**ことを実測で確認した。

### 3.4 並行実行（`01b` Q-02 C-2）

`/rsc-parallel` の3本は `Promise.all` で同時に投げている。

| 計測 | 値 |
| --- | --- |
| 描画スパンの子として観測した SQL スパン | **3 本** |
| 区間が重なった組 | **1 組**（重なり 1.32 ms） |
| 各スパンの所要時間 | 4.63 ms / 2.35 ms / 2.32 ms |

- **タイムラインに必要な情報（開始・終了・親子）は3本とも揃っている。**
- **ただし「3本が完全に重なる」わけではない。** 接続プールの都合で、実際に区間が重なったのは
  1組だけだった。**「並列に書いたから並列に重なる」とは限らない。**
  並行実行の表現は、書き方ではなく**観測した区間**に従うべきである。
- スパンの開始順は実行ごとに変わる（13→15→14 のこともある）。**順序を安定した事実として扱えない。**

### 3.5 バンドラの差異（Turbopack / webpack）

| 項目 | Turbopack | webpack |

| Gate A の判定 | **全ケース一致** | **全ケース一致** |
| Gate B の判定 | **全ケース一致** | **全ケース一致** |

| スタックに出るフレームの形 | `.next/dev/server/chunks/ssr/*.js`（**実ファイル**） | `webpack-internal:///(rsc)/./src/...`（**仮想URL**） |
| ソースマップの引き方 | 隣の `.js.map` を読む | 生成物の `eval("…")` ブロックから**インラインのソースマップを取り出して索引を作る** |
| 索引の規模 | ディスク上のマップ **8 件** | eval モジュール **491 件** |

> **webpack では、サーバー側の生成物に CDP が使えない。**
> `06c` 4.1節はブラウザ側で `Debugger.getScriptSource` を使って解決したが、
> サーバー側にはその経路が無い。代わりに `.next` 以下の生成物を走査し、
> `eval("…")` に包まれたモジュールのインラインソースマップから索引を作った
> （`poc/runner/lib/srvmap.mjs`）。**これで Turbopack と同じ精度になった。**
>
> 試して**効かなかった**ことも記録しておく:
> `--enable-source-maps` は eval されたモジュールのスタックを書き換えなかった。
> `webpack.devtool = 'source-map'` は Next.js の dev サーバーが上書きするため効かなかった。
> どちらも**実測で確かめたうえで採らなかった**。

## 6. 観測の正確性 — 4つの区別

| 区分 | 本PoCでの内容 | モデル上の扱い |
| --- | --- | --- |
| **① 実際に観測した処理** | 文書取得 / 描画スパン / サーバー内部通信の client スパン / 受け側の入口スパン / SQL スパン（文・区間・成否）/ 呼び出しの入口のスタック / 要素識別子 | ノードとホップを作る。`source` は `browser-network` `trace-span` `trace-context` `orm-instrumentation` `sql-ast-parse` `db-introspection` `element-anchor` `server-call-stack` のいずれか。**すべて実測** |
| **② 静的解析で推定した関係** | **本PoCでは1つも作っていない** | `binds` / `derives` を作っていない。`static-analysis` の `source` を持つ要素は 0 件 |
| **③ 証拠が無く不明な関係** | ② と ②'' の間 / props の由来 / カラムと結果の項目 / 伝播が無いときの相手側 / `/rsc-helper` の実行元コンポーネント | **関係を作らない。** 切断マーカー（`cuts`）または `skipped` に理由付きで残す |
| **④ 計測対象外の処理** | Server Action / ストリーミング境界 / Edge Runtime / 本番ビルド / 表示された値そのもの / 取得結果の中身 | `notObserved` に理由付きで列挙（観測結果 JSON の `meta.notObserved`。第4.2節・第5章） |

### 6.1 関係種別の意味を混同していないことの確認

| 関係 | from → to | 本PoCで作ったか | 根拠 |
| --- | --- | --- | --- |
| `renders` | ComponentDef → DomElement | **作った**（`/rsc-db`） | 要素識別子（`element-anchor`） |
| `requests` | ComponentDef → HttpExchange | **作った**（`/rsc-svc`。**サーバー内部の通信**に対して） | 呼び出し入口のスタック（`server-call-stack`） |
| `handles` | HttpExchange → Span | **作った**（文書取得・サーバー内部通信の両方） | 文書取得は応答ヘッダの識別子、サーバー内部は親子関係 |
| `invokes` | Span → Span | **作った** | 描画スパン → client スパンの親子 |
| `executes` | **Span** → SqlStatement | **作った** | スパンの親子 |
| `queries`（**新規提案**） | **ComponentDef** → SqlStatement | **作った** | 呼び出し入口のスタック |
| `reads` / `projects` | SqlStatement → DbTable / DbColumn | **作った** | 実測 SQL の構文解析 |
| `derives` / `maps` / `binds` | — | **作っていない** | 証拠が無い |

> **`requests` と `queries` を分けている。** 前者は通信、後者は SQL である。
> 取得手段は同じ（呼び出しスタック）だが、**到達する先の種別が違うので同じ関係にしていない。**
> **`executes` と `queries` も分けている。** 前者の始点はスパン、後者の始点はコンポーネントである。
> `/rsc-db` の実行SQL には**この2本が別々に入っている**（根拠が別だから）。

### 8.2 伝播の範囲 — `06c` 6.1節の問題への対処

`06c` で「`Server-Timing` はページ上の任意のスクリプトに同一オリジンの全通信のトレースIDを配る」ことを実測した。
本PoCは**要求にトレースコンテキストを注入する**ので、公開範囲の問題が1つ増える。

| 対処 | 実装 | 検証 |
| --- | --- | --- |
| **ループバック宛にしか注入しない** | undici の計装の `ignoreRequestHook` が、ループバック以外の宛先を**計装対象から外す**。計装しなければ**スパンも作られず、`traceparent` も付かない** | `poc/fixture-app/ide-instrumentation/loopback.cjs` を**計装とテストの両方が使う**（判定を2箇所に書かない）。poc02 §4 で外部ホスト・プライベートIP・`0.0.0.0`・解釈不能な値が**すべて対象外**になることを検査 |
| **既定で無効** | `POC02_UNDICI` が立っているときだけ伝播する。既定では PoC-01 / 03 / 05 と同じ条件 | 伝播なしの条件での実測（第3.3節） |
| 識別子を応答に載せるのは開発機の中だけ | `06c` の仕組みをそのまま使用（ループバック以外には載せない） | poc05 の既存検査 |

### 10.3 PoC-02 全体の判定

### **条件付き成功**

**成功と呼べる部分**

- **Server Component がサーバー内部で直接 DB を読む経路を、証拠を持って可視化できた。**
  5ケースすべてで、描画スパンの子孫として SQL を観測し、**どの Server Component のどの行が
  その SQL を実行したか**を特定した。同じ SQL 文を別の2箇所から実行する題材でも取り違えていない。
- **「スパンが始まった場所は、呼び出した場所ではない」ことを実測で示し、方式を変えた。**
  SQL スパン開始時のスタックには、呼び出し元のフレームが **0/8** で存在しない。
  この事実があるから、Next.js 内部のスパンの存在をコンポーネントへの帰属と読み替えていない。
- **サーバー間のトレース伝播が成立した**（`06c` 第10章 #1 の解消）。別プロセスの
  サービスまで、ブラウザ↔サーバーと同じ強さの証拠で繋がった。
- **別トレースを同一経路にしていない。** 伝播が無い条件では1件も対応付けず、
  **時間窓なら4件繋いでしまう**場面を数字で示した。
- **Turbopack と webpack で結果が一致した。** webpack のサーバー側生成物（eval されたモジュール）は
  CDP が使えないが、生成物のインラインソースマップから索引を作って同じ精度にした。
- **既存の探索画面の設計を変えずに描けた。** 新しい画面も新しい描画部品も作っていない。

**「条件付き」である理由**

1. **`01b` Q-02.3 / Q-02.4 の範囲を全部は埋めていない。** Server Action（パターン3）と
   ストリーミング（`Suspense` 境界）と Client/Server 境界の判別が**未実施**である。
   Q-02.4 の「3パターン網羅」「境界判別」は判定していない。
2. **帰属は開発ビルド限定である。** ソースマップと要素識別子の注入の両方に依存する（`01b` Q-03 C-5）。
   本番ビルドでは成立しない。
3. **帰属は「アプリのソース（`src/`）の中で呼ばれた場合」に限る。** 2つ目のサービスの中の
   SQL や、ライブラリの中から発行される SQL には帰属を作れない（注入範囲の外）。
4. **ORM 経由の直読みを試していない。** 直読みの題材はすべて素の `pg` である。
   Prisma の内部は独自のエンジン層を通るため、同じ方式が成り立つかは**未検証**である。
5. **取得手段 `server-call-stack` と関係 `queries` は `02d` / `02a` に無い。** 追加の提案であり、未承認である。
6. **検証したのは Next.js 16 + Node 24 + Chrome の1構成である。** 他のバージョン・ランタイムは未検証。
7. **伝播ヘッダの製品設計が未確定である。** ループバック限定にしたが、同じ開発機の別プロセスには届く。

**成功扱いにしていないこと**

- **値の出所は依然としてつながっていない。** `derives` も `maps` も作っていない。
  Gate A も Gate B も成立したのに、**「画面のこの値は、このカラムから来た」とは言えないまま**である。
  これは PoC-05 の結論と同じであり、**本PoCでも1歩も進んでいない。**
- **同じコンポーネントが複数回描かれたとき、どのインスタンスがその SQL を実行したか**は観測していない。
- **Next.js 内部のスパンの内訳**（`createComponentTree` などの細かい段）は、取れてはいるが
  コンポーネントへ帰属できないため、画面に出していない（`03` 第671行 Q-14 は未解決のまま）。
