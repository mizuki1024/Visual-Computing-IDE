## 0. 分類の定義と原則

### 0.1 3区分の定義

| 区分 | 定義 | 判定の問い |
| --- | --- | --- |
| **A: 中核価値の実証に絶対必要** | これが無いと「画面要素からDBカラムまで1本の図で辿れる」という仮説そのものを検証できない | **「これを削ったら M2 のデモが成立しなくなるか？」** |
| **B: MVP完成までには必要だが、中核価値の実証後でよい** | 実用に耐えるMVPには必要だが、仮説検証（A群の完成とユーザーテスト）の後に着手してよい | **「実証デモは成立するが、日常使用には耐えないか？」** |
| **C: 後続フェーズで実装する** | ビジョン上は必要だが、MVPの範囲外 | — |

### 0.2 分類の原則

1. **要件IDは変更しない。** 既存のIDをそのまま維持し、A/B/C のラベルを付与する。
2. **要件を削除しない。** C に分類されたものは「不採用」ではなく「後続フェーズへの配置」である。
3. **A群は最小に保つ。** A群が膨らむと仮説検証が遅れ、検証前に大量の実装が無駄になるリスクが増す。
4. **誠実さに関わる要件は A から外さない。** 観測性の表示規約を後回しにすると、検証段階で「正しそうに見える誤った図」をユーザーに見せることになり、検証結果そのものが汚染される。
5. **秘密情報の保護は A から外さない。** 他人のプロジェクトで検証する時点で既に必要になる。

### 0.3 元の優先度 (P0/P1/P2) との関係

Phase 1 の P0/P1/P2 は「MVPに入るか」の分類だった。今回の A/B/C は **「MVPの中での実装順序」** を加えた再分類である。

| 旧 | 新 | 件数の変化 |
| --- | --- | --- |
| P0（MVP必須） | **A または B** に分割 | P0 の約半数が B へ移動 |
| P1（MVP直後） | **B または C** | 大半が C |
| P2（将来） | **C** | 変化なし |

> **最大の変更点**: 旧 P0 だったビジュアル編集 (FR-13〜FR-16) を **B** に移した。方針「可視化を中核、編集は副次的」に従い、中核価値の実証には編集機能が不要であるため。

### 1.2 A群の実装順序（依存関係）

```
① FR-01 → FR-02 → FR-03          解析基盤
   └ FR-07                        対応範囲の明示

② FR-30 → FR-31                   プロセス起動（計装の前提）
   └ INS-01, INS-02, INS-08        計装の注入

③ FR-41                           サーバー計装（SQL/リクエスト捕捉）  ◀ PoC-01/02 の成否
   └ FR-52                         実行SQLの表示
   └ FR-50, FR-51                  DBスキーマ・データ

④ FR-10 → FR-11 → FR-11b          プレビューと要素選択           ◀ PoC-03 の成否
   └ FR-12                         静/動判定
   └ FR-40                         ブラウザ通信捕捉

⑤ FR-42                           トレース結合                   ◀ PoC-05 の成否
   └ FR-20, FR-20b                 フローのデータモデルと描画
   └ FR-21                         3ビュー同期

⑥ FR-22 → FR-23                   順方向トレース ◀◀ M2 達成点    ◀ PoC-04 の成否
   └ FR-18                         ページ切替

全工程に並走: OBS-01/02/05/06/09/10/11, NFR-12/14/17/20/21
```

> **観測性と安全性の要件（OBS群・NFR群）は、最後にまとめて追加できない。** データモデルに観測性レベルを持たせること (OBS-01, OBS-09) は③の時点で設計に組み込む必要がある。

### 1.3 M2 の達成条件（Definition of Done）

A群が完成したと判定する基準。**デモが「動く」ことではなく、「正しく動き、正しく限界を示す」ことを条件とする。**

| # | 条件 |
| --- | --- |
| 1 | 対象プロジェクトのページをプレビュー表示し、任意の要素をクリックできる |
| 2 | 選択した要素について、フロー図と右パネルに「要素 → コンポーネント → APIまたはRSC経路 → サーバー処理 → SQL → テーブル → カラム → 実値」が提示される |
| 3 | **各ステップに観測性レベルが個別に表示され、実測区間と推論区間が視覚的に区別されている** |
| 4 | **経路の中で最も確度が低い箇所が名指しで示される** |
| 5 | 特定できない要素をクリックした場合、無言ではなく理由が提示される |
| 6 | RSC（Server Component が直接DBを参照する）ページでも、経路が破綻せず表示される |
| 7 | 秘密情報（環境変数、Cookie、認証ヘッダ）がマスクされている |
| 8 | 計装が失敗した状態でも、静的解析ベースの経路が「推定」として表示され、クラッシュしない |
| 9 | 難易度別の50要素（PoC-04 の題材）について、**誤答率が基準内**に収まっている |

### 1.4 A群完成後に行うこと（B群着手前）
