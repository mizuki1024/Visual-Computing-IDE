## 2. 観点ごとの評価

### 2.1 UC-01（表示値から出所を辿る）の理解しやすさ

| 案 | 評価 | 根拠 |
| --- | --- | --- |
| **A** | ○ | **【要件】** 経路サマリ・★・7ステップがすべて1画面に収まり、`01c` M2 達成条件3・4 を満たす。層（ブラウザ/サーバー/DB）が空間として示されるため「どこまで来たか」が位置で分かる。<br>**【検証待ち】** ただし層の読み方（左→右）を**最初に学習する必要がある**。帯の見出しは 10px で、初見では見落としうる |
| **B** | △ | **【要件】** 達成条件は満たす。ホップの説明を7件すべてパネルに置いたため、**パネル単独で経路が最後まで読める**のは3案中B案だけである。<br>**▲ 懸念** キャンバスが索引に徹しているため、**経路の全体の形（⑦→③ の折り返し）がほぼ読めない**。「`properties.area` が応答に戻ってくる」という UC-01 の肝が、細い折り返し線と ★ だけで表現されている |
| **C** | ◎ | **【要件】** ゾーン名が「ブラウザ**で起きたこと**」という完全な日本語で、全ホップに平易な説明が常時出ている。UXR-01（中核体験の開始に専門用語の理解を要求しない）を**画面上で**満たしているのは C案のみ。<br>**【要件】** 詳細パネルが420pxあり、`03` 3.5節の文言を圧縮せずに置けている（A案は2行、B案は2行に折り返すが C案は最も読みやすい） |

### 2.2 視線の自然な流れ

| 案 | 評価 | 根拠 |
| --- | --- | --- |
| **A** | △ | **【要件】** 操作の起点はプレビュー（左）→ 結果はキャンバス（中央）→ 説明はパネル（右）で、左→右の一方向。<br>**▲ 懸念** キャンバス内部が**左→右の3帯 + 下辺を回る折り返し**であり、視線が「右へ進んで → 左下へ大きく戻る」。外側（左→右）と内側（右→左の戻り）の方向が衝突する |
| **B** | ◎ | **【要件】** プレビュー（大）→ ストリップ（縦スクロール的に上→下）→ パネル（上→下）。**3段すべてが同じ向き**で、視線が折り返さない。UXR-11 の「1操作で経路が出る」体験と最も素直に一致する |
| **C** | ○ | **【要件】** プレビュー（小）→ キャンバス（上→下）→ パネル（上→下）。向きは揃っている。<br>**△** ただし起点のプレビューが360pxと小さく、**操作の起点が視覚的に主役でない**。「ここをクリックするのだ」の誘導はB案に劣る |

### 2.3 余白（UI-05「余白を大胆に取る。情報密度を上げるために余白を削らない」）

| 案 | 評価 | 根拠 |
| --- | --- | --- |
| **A** | ○ | **【要件】** ノード間隔 170px 前後を確保。ただしサーバー帯（③→④ の折れ線 / ④→⑤ の説明 / 切断マーカー）が**キャンバス中央部に3要素を押し込んでおり局所的に密**になっている |
| **B** | △ | **【要件】** キャンバスの余白は十分。**ただし詳細パネルが3案で最も密**で、7ステップ × （説明 + 種別 + 識別子）の21行が400px幅に詰まっている。UI-05 の精神には反していないが、快適ではない |
| **C** | ◎ | **【要件】** ノード間隔 92px の縦リズムに、ゾーン枠の内側余白が加わる。ゾーン枠の右側に意図的な空白を残しており、将来ホップあたりの情報を1つ足せる余地がある |

### 2.4 情報密度（UI-20 / `03` 10.4 申し送り2「段階0の情報量を守る」）

> 本モックは段階2だが、**「見栄えのために値を1つ足す」判断が起きていないか**という観点は同じく適用される。

| 案 | 評価 | 根拠 |
| --- | --- | --- |
| **A** | ○ | **【要件】** キャンバス上の文字は、ノードラベル14個 + ホップ説明7個 + 帯見出し3個。属性値は0。UI-15 を満たす |
| **B** | ◎ | **【要件】** キャンバス上の文字はノードラベル14個 + 推定の符号2個のみ。**3案で最も少ない**。「フロー図は属性値を持たない」（UXR-26）を最も厳格に体現している |
| **C** | △ | **【要件】** キャンバス上の文字が最多（ノードラベル14 + ホップ説明7 + ゾーン名3 + 切断2 + 減光群3 = 29）。属性値ではないため UI-15 違反ではない。<br>**▲ 懸念** ただし **`03` 10.4 申し送り2 が警戒している「文字を足したくなる傾向」の、最も進んだ形**である。段階0（未選択）でこの密度を維持できるかは別途検証が必要 |

### 2.5 データフローの読み取りやすさ

| 案 | 評価 | 根拠 |
| --- | --- | --- |
| **A** | ◎ | **【要件】** ⑦→③ の折り返しが**キャンバス全体を使った大きな環**として描かれ、「DBのカラムが応答に戻ってくる」という経路の非直線性が最もよく見える。3帯により「どの層にいるか」が常時わかる。切断マーカーがサーバー帯の外へ向かう枝として置かれ、経路本体と混同されない |
| **B** | ▲ | **【要件】** 7ステップの**順序**は最も読みやすい（単純な縦1列）。<br>**▲ 懸念** しかし**経路の形は読めない**。⑦→③ が幅24pxの細い折り返しに圧縮され、★ だけが手がかりになる。OBS-11（最弱環の名指し）は満たすが、**最弱環が「経路のどこか」は図から分からない**。パネルの「⑦→③」という表記に依存している |
| **C** | ○ | **【要件】** 3ゾーンにより層は明確。全ホップに説明があるため、図だけで経路を言語化できる。<br>**△** ⑦→③ の折り返しはゾーン枠の外側を通るため A案より控えめ。ただし ★ チップと「カラムと応答項目の対応づけ（推定）」が線のそばにあり、意味は伝わる |

### 2.6 観測性の誠実さ

> 本プロダクトの価値は「見えないことを、見えないと正しく言えること」（`01` 0.2節）。最も重い観点である。

| 案 | 評価 | 根拠 |
| --- | --- | --- |
| **A** | ○ | **【要件】** 実測/推定は線種 + 「推定」語。★ は線上。切断マーカーは理由つき。N0 の「部分対応・1件」と整合。NFR-30 を満たす |
| **B** | ○ | **【要件】** 同上。さらに**7ホップ全部の観測性がパネルに「（実測）」「（推定）」として明記される**点は3案中最も明示的。<br>**▲** ただし**キャンバス上の推定の符号が2個のチップだけ**で、図を眺めた段階の「この経路は確かそうだ」という第一印象が、A案・C案より強く出てしまう恐れがある（UXR-13 の精神に近い懸念） |
| **C** | ◎ | **【要件】** 推定の2ホップに**説明文が常時出ている**（「応答のどの項目が、この値になったか」「カラムと応答項目の対応づけ（推定）」）。切断マーカーの理由も常時表示。**「何が観測できていないか」を読むのに1操作も要らない**。原則6・OBS-05 の表現として最も強い |

### 2.7 参考画像との視覚的一貫性 ——【好み】の比重が最も高い観点

| 案 | 評価 | 根拠 |
| --- | --- | --- |
| **A** | ◎ | **【好み】** 参考画像 `03` `04` `08` の「中央に大きなノードグラフ、左にプレビュー、右に詳細」という構図に最も近い |
| **B** | ○ | **【好み】** 参考画像 `08` の右パネル（番号付き縦リスト）の思想に近いが、中央のグラフが細いストリップになる点は参考画像に前例がない |
| **C** | △ | **【好み】** ゾーン枠と常時表示の説明文は参考画像に前例がなく、**雰囲気としては最も「参考画像らしくない」**。色・質感・余白は共通だが、構図は独自 |

> **この観点だけで決めてはならない。** 参考画像は色・質感・余白・ノード表現の基準であって、**情報構造の基準ではない**（参考画像はファイアウォール・左レール・Codeタブなど、現在の要件から外れた要素を多く含む）。

### 2.8 将来の拡張性（B群・C群の追加に耐えるか）

| 追加予定 | A | B | C |
| --- | --- | --- | --- |
| FR-17 コンポーネントツリー（B・N2 に追加） | ○ 左160pxを拡張 | ○ | △ 左140pxは最も狭い |
| FR-43 タイムライン（B・N5 展開） | ○ | ○ | ○ |
| FR-25 スコープ切替（B・T1〜T3 の俯瞰） | ◎ **3帯レイアウトは多数ノードに耐える** | ▲ **縦1列は T2（ページ全体・数十ノード）で破綻する** | ○ ゾーン内に横方向の余地あり |
| OBS-12 連続線・区間ごとの線種切替（B） | ◎ | △ 折り返しが細く区間が見えない | ○ |
| OBS-03 確度ラベル（B・較正後） | ○ ホップ脇に1チップ追加可 | ◎ パネルの各行に追加可 | ○ 説明文の末尾に追加可 |
| FR-24 コードピーク（B・オーバーレイ） | ○ | ○ | ○ |
| 編集モード（B）への遷移 | ○ | ◎ プレビューが大きいほど編集に移行しやすい | ▲ プレビュー360pxでは編集できない |
| **総合** | **○** | **◎（UC-01 単独では）／▲（俯瞰では）** | **▲** |

> **最大の分岐点は FR-25（スコープ切替）である。** `02b` 3.1節と `03` P3-03 により、ページを開いた直後の既定は **T2（主トレース）** であり、**選択前の俯瞰には数十ノードが並ぶ**。B案の縦1列ストリップ（320px）はこれを収容できない。B案を採る場合、**俯瞰時だけキャンバスを広げる別レイアウトが必要**になり、「1画面・1構成」という単純さが失われる。

### 2.9 実装の複雑性

| 案 | 評価 | 根拠 |
| --- | --- | --- |
| **A** | ▲ | **【要件】** 3帯 × 折れ線 × 下辺を回る折り返しのため、**自動レイアウト（UI-31）が最も難しい**。ノード数が変わると帯の割り当てと折り返しの経路を再計算する必要がある。ホップ説明の配置も衝突回避が要る |
| **B** | ◎ | **【要件】** 縦1列のため自動レイアウトはほぼ自明。折り返しは左マージン1本。**ホップ説明をパネル（通常のDOM）に置いたため、SVG 上のテキスト衝突回避が不要**。3案で最も実装が軽い |
| **C** | ○ | **【要件】** 縦1列 + ゾーン枠。ゾーン枠の高さは内包ノード数から決まるため計算は単純。ホップ説明が SVG 上にあるため衝突回避は必要だが、**縦1列なので横方向に十分な幅があり、A案より容易** |

## 3. 各案の利点・欠点（まとめ）

### A案 — Data Flow First

| | 内容 |
| --- | --- |
| **最大の利点** | **経路の非直線性（⑦→③ の折り返し）が図として読める唯一の案。** 「DBのカラムが応答に戻って画面の値になる」という UC-01 の構造が、言葉を読まなくても分かる |
| 利点 | 層（ブラウザ/サーバー/DB）が空間に対応し、切断がどの層で起きたか一目で分かる。FR-25（俯瞰）への拡張に最も強い。参考画像との一貫性が最も高い |
| **最大の欠点** | **視線が左→右に進んだあと左下へ大きく戻る。** 外側の流れと内側の戻りが衝突し、初見の読み順が定まらない |
| 欠点 | 自動レイアウトが3案で最も難しい（UI-31）。帯見出しが小さく、層の意味が伝わらない恐れ。サーバー帯の中央が局所的に密 |
| 向く条件 | P1（フルスタックエンジニア）を主対象とし、将来 T1〜T3 の俯瞰を本格的に使う場合 |

### B案 — Preview First

| | 内容 |
| --- | --- |
| **最大の利点** | **視線が一方向に流れ、操作の起点（プレビュー）が明確に主役である。** UC-01 は「画面の値をクリックする」から始まるので、体験の順序と画面の重み付けが一致する |
| 利点 | キャンバス上の文字が最少で UXR-26 に最も忠実。詳細パネルだけで経路が最後まで読める。実装が3案で最も軽い。編集モード（B群）への接続が最も自然 |
| **最大の欠点** | **経路の形が読めない。** 最弱環 ⑦→③ が「経路のどこか」を図から読み取れず、パネルの「⑦→③」という表記に依存する。OBS-11 は満たすが、空間的な理解が得られない |
| 欠点 | FR-25（俯瞰・数十ノード）で縦1列が破綻する。詳細パネルの密度が3案で最も高い。図を眺めた印象が「確かそう」に寄り、観測性の誠実さの第一印象が弱い |
| 向く条件 | UC-01 の1本追跡に用途を絞り、俯瞰（UC-07）はキャンバスを広げる別状態で扱うと決める場合 |

### C案 — Comprehension First

| | 内容 |
| --- | --- |
| **最大の利点** | **「何が観測できていないか」を読むのに1操作も要らない。** 推定の2ホップと切断の理由が常時文章で出ており、原則6・OBS-05・UXR-01 を画面上で満たす |
| 利点 | 余白が最も広く、詳細パネルが最も広い（経路サマリを圧縮せずに置ける）。ゾーン名が完全な日本語で、専門用語の事前学習を要求しない。実装は A案より容易 |
| **最大の欠点** | **キャンバス上の文字数が最多で、`03` 10.4 申し送り2（段階0の情報量を守る）に最も近い位置にいる。** 段階0（未選択・数十ノード）で同じ方針を維持すると、文字が画面を埋める |
| 欠点 | プレビューが360pxで、操作の起点が視覚的に主役でない。左パネルが140pxでコンポーネントツリー（B群）の追加余地が小さい。編集モード（B群）に移行しづらい。参考画像との視覚的一貫性が最も低い |
| 向く条件 | 誠実さ（`01c` 原則1）を最優先し、将来 P3（非エンジニア）への拡張を本気で狙う場合 |

## 4. 選定にあたって先に決めるべきこと

> **本書は選定しない。** ただし、どの案が正しいかは次の3つの決定に従属するため、先にそれらを確認することを提案する。

| # | 決めるべきこと | どう効くか |
| --- | --- | --- |
| **1** | **ページを開いた直後の俯瞰（段階0・T2）を、この画面の同じキャンバスで扱うか** | 扱うなら **B案は不適**（縦1列が破綻）。俯瞰を別状態・別レイアウトにしてよいなら B案が最有力 |
| **2** | **「経路の形を見せること」と「経路を言葉で読ませること」の、どちらを一次とするか** | 前者なら **A案**、後者なら **B案 または C案**。これは好みではなく、`01` 原則2（全体像を最初に理解できる）をどう解釈するかの問題である |
| **3** | **P3（非エンジニア）への拡張を MVP の視覚設計に織り込むか、C群まで先送りするか** | 織り込むなら **C案**。`02b` 7章は「表示プロファイル（用語層の切替）」で解くと決めているので、**C案の常時説明は本来そのプロファイル側の仕事**という解釈もありうる |

> **決定3に関する注記**: C案の「全ホップに平易な説明を常時表示」は、`02b` 7章の表示プロファイル（FR-60・C群）で切り替えるべき層と重なる。C案を選ぶ場合、**この説明文を「既定でON、プロファイルでOFFにできる層」として実装する**のが構造的に整合する。A案・B案を選ぶ場合は、同じ説明文を**プロファイルONで足す**形になる。いずれにせよ、説明文は**レイアウトに埋め込まず、切り替え可能な層として設計する**ことを推奨する。
