## 1. 検証した方式

### 1.1 4方式を実測で比べた

| # | 方式 | 実測の結果 | 採否 |
| --- | --- | --- | --- |
| **1** | **ビルド時の要素識別子注入**（JSX へ `data-vcide` を挿入） | **自作22要素 22/22 正解・誤答0。Turbopack / webpack ともに同一の判定** | **採用** |
| 2 | React の `_debugStack` + ソースマップ | Turbopack: クライアント描画16要素のみ行まで正解。**サーバー描画6要素は解けない**。webpack: ファイルは22/22 正解だが**行は解けない** | 不採用（比較用に実測） |
| 3 | `__source` prop / `_debugSource` | **React 19.1.1 の Fiber に `_debugSource` は存在しない**（実測）。`memoizedProps` に `__source` も無い（実測） | 不採用（成立しない） |
| 3b | React の**公開API** `captureOwnerStack()` | 存在する（19.1 で公開）。ただし返るのは**いま処理しているコンポーネント**の由来であり、クリックされた DOM 要素の由来ではない（実測。`RegionBadge` の要素を押しても `Cards` のスタックが返る） | 不採用（問いに答えられない） |
| 4 | DOM 構造・テキストのヒューリスティック照合 | **実装しなかった。** 値照合は必要条件にすぎず（02d 3.3節）、方式1 が誤答0で成立したため採る理由が無い | 不採用 |

### 1.2 採用した方式と理由

**方式1（ビルド時の要素識別子注入）を採用する。** 理由は3つである。

1. **React の内部実装に依存しない。** `_debugSource` が React 19 で消えた事実（Q-03.0）が示すとおり、内部プロパティは壊れる。方式1 は DOM の属性だけを読む。
2. **Client / Server の区別を受けない。** 属性はビルド時に JSX へ入るので、サーバーで描かれた HTML にもそのまま載る。方式2 はここで解けなかった（第2.4節）。
3. **「特定不能」を誤答にしない設計にできる。** 第1.4節の規則による。

### 1.3 実装 — 再出力しないので行番号がずれない

`poc/anchor/transform.cjs` は TypeScript の構文解析器で位置だけを取り、**元のテキストへ属性を差し込む**。
AST から再出力（pretty-print）しない。

```
  <span className="badge-text">{region}</span>
  ↓ 挿入のみ
  <span data-vcide="9d8bc0d72e" className="badge-text">{region}</span>
```

| 性質 | 結果 |
| --- | --- |
| 行番号 | **1行もずれない**（テストで固定: `tests/poc03.spec.mjs`「行数を変えない」「報告した行は、元のソースでも同じ行である」） |
| ソースマップ | **不要**。位置はビルド時に確定し、マニフェストに残る |
| 識別子 | `sha1(相対パス:行:列)` の先頭10桁。**再ビルドで変わらない**。ソースのパスを DOM に出さない |
| 注入先 | **組み込み要素（小文字タグ）だけ**。`<RegionBadge>` のようなコンポーネント要素は DOM 要素にならないので注入しない |
| 除外 | `html` / `head` / `body`（フレームワークが所有する）、`src/` の外、JSX を持たないファイル |

`poc/anchor/loader.cjs` は **webpack ローダ API 1本で webpack と Turbopack の両方に使える**。

### 1.4 誤特定を避けるための中心的な規則

> **要素識別子は、その要素自身に付いているものだけを出所として扱う。祖先の識別子は文脈であって出所ではない。**

これを破ると、`closest('[data-vcide]')` がライブラリ由来の要素を**自作ファイルへ誤って割り当てる**。
実測でも、ライブラリ由来の3要素はいずれも祖先（`src/app/cards/page.tsx` の `<main>`）に識別子を持っていた。
規則があるから「特定不能」と返せている（第4.3節）。

### 2.2 UR-01 / C-2（Turbopack でビルド時注入ができるか）— **できる**

`next.config.mjs` の `turbopack.rules` に webpack ローダを渡すだけで動いた。SWC プラグインも Babel も要らない。

```js
turbopack: { rules: { '*.tsx': { loaders: [{ loader: ANCHOR_LOADER, options: ANCHOR_OPTS }] } } }
```

| 実装でわかったこと | 内容 |
| --- | --- |
| **F-5** | **`as: '*.tsx'` を付けてはいけない。** 付けると Turbopack が出力の拡張子を足し、`'use client'` ページのクライアント入口が `page.tsx.tsx` を解決しようとして 500 になる。Server Component のページだけは通るので**気づきにくい** |
| **F-6** | webpack 側は `enforce: 'pre'` が必要。SWC より前に素の TSX を受け取るため |
| **F-7** | ローダは**並列・別プロセス**で走る。マニフェストは1ファイル1出力にして `rename` で確定させる（競合を避ける） |

→ **UR-01 は解消。`01b` Q-03.5 の代替1（webpack 構成へ限定）は不要である。**

### 2.3 React 19 の実測（内部プロパティを前提にしていないことの裏づけ）

React 19.1.1 / Next.js 16.4.3 / 開発ビルドで、クリックされた要素の Fiber を実際に読んだ。

| 調べたもの | 実測 |
| --- | --- |
| `__reactFiber$<乱数>` / `__reactProps$<乱数>` | DOM 要素に付いている |
| **`_debugSource`** | **Fiber のキーに存在しない**（PR #28265 の削除を実測で確認） |
| `_debugStack` | 存在する。`Error` オブジェクト。スタックはバンドル後のチャンクを指す |
| `_debugOwner` | 存在する。`type.name` から描いたコンポーネント名が読める（`RegionBadge` / `VendorPanel`） |
| `memoizedProps.__source` | **無い** |
| **公開API `React.captureOwnerStack()`** | 存在する。ただし React のイベントハンドラ内で呼ぶと **`at main → at Cards → at ClientPageRoot`** が返る。押された `<span>` を描いた `RegionBadge` は返らない |
| JSX を経由せず `document.createElement` した要素 | **Fiber が付かない**（`__react*` キーが0個） |

> **結論**: **React の公開APIだけでは「この DOM 要素を描いたコンポーネント」を問えない。**
> `_debugOwner` を読めば答えは出るが、それは非公開の内部プロパティであり、`_debugSource` と同じ理由で壊れうる。
> 本PoCは `_debugOwner` を**採用方式に使っていない**（テストで固定: 「採用した方式は React の内部プロパティを使っていない」）。

### 2.4 方式2（`_debugStack` + ソースマップ）を実際に解いた結果

比較のため、最小のソースマップ消費器（`poc/runner/lib/srcmap.mjs`。インデックスマップ対応）を書いて実測した。

| | Turbopack | webpack |
| --- | --- | --- |
| 行まで正解 | **16 / 26** | 0 / 26 |
| ファイルのみ正解（行は不一致） | 0 | **22 / 26** |
| 誤ったファイルを指した | **0** | **0** |
| 解けなかった | 10（うち**サーバー描画6**・ライブラリ由来3・動的DOM1） | 4（ライブラリ由来3・動的DOM1） |

- **Turbopack**: クライアント描画の要素は `_debugStack` を解いて**行まで正しく**戻せた。方式2 も成立する。
- **Turbopack・サーバー描画**: フレームが `about://React/Server/file:///…/.next/dev/server/chunks/ssr/….js` という
  **取得できない疑似URL**になり、ユーザーのソースへ戻せない。→ **RSC で方式2 は成立しない。**
- **webpack**: フレームが `webpack-internal:///(app-pages-browser)/./src/…` を指すので**ファイルは直接読める**。
  行は eval されたモジュール内の座標で、元の行へ戻すには eval 内のインラインソースマップが要る。HTTP では取れないので**解いていない**。
- いずれの方式も**誤ったファイルは1件も指さなかった**。方式2 の弱点は精度ではなく **解けない範囲の広さ**と**実装の重さ**である。

## 4. DOM → コンポーネント → ソース位置 の実測（主対象の通し）

```
①  ブラウザで <span class="badge-text"> をクリック
    └ 本物の click イベントを捕捉リスナーで受ける（製品の選択操作と同じ経路）

②  その要素自身の属性を読む        data-vcide="9d8bc0d72e"
    └ 祖先の識別子（5個）は「文脈」として別に保持する。出所には使わない

③  同一識別子の DOM 要素を数える   3 個中 1 番目
    テキストノードの索引を取る      #0
    値の形だけを取る                5 文字・和文      ← 値そのものは読み出さない

④  ビルド時のマニフェストを引く    9d8bc0d72e →
       src/components/RegionBadge.tsx:8:7  <span>  @RegionBadge（定義は 4 行目）

⑤  ソースを読み直して照合           8 行 7 列に <span> があり、
    （変換側とは独立）              囲んでいるコンポーネントは RegionBadge   ✓

⑥  祖先の識別子から包含関係を作る   RegionBadge ← ListingCard ← Cards
```

### 4.1 「A〜E」の区別（指示 第5節）

| | 内容 | 判定 | 根拠 |
| --- | --- | --- | --- |
| **A** | DOM 要素を特定できた | **成立** | 本物の click の `event.target` を取得。26/26 |
| **B** | 対応するコンポーネントを特定できた | **成立** | 要素自身の識別子 → マニフェスト。自作22/22、誤答0 |
| **C** | 正しいソースファイルを特定できた | **成立** | 手書きの正解表と一致。さらにソースの読み直しで照合 |
| **D** | 正しい JSX 位置（行・列）を特定できた | **成立** | 同上。変換が再出力しないので行がずれない |
| **E** | **その値の由来まで特定できた** | **不成立** | **props の由来は観測していない。** 関係を作っていない。第5章 |

> **A〜D が成立しても E は成立していない。** `RegionBadge` は `region` を props で受け取るだけであり、
> その props がどこから来たかは、このコンポーネントのソースにもブラウザの DOM にも書かれていない。
> **`derives` を実測として扱っていない。ホップも作っていない。**

## 5. 観測できなかったもの（作らなかった関係）

**ここに挙げたものは、画面にも変換結果にも存在しない。** 代わりの値で埋めていない。

| # | 作らなかった関係 | 理由 | 画面での扱い |
| --- | --- | --- | --- |
| 1 | **`derives`**（応答の項目 → props） | **props の由来を観測する手段が無い。** `02a` 3.5.1 により構造的に推定（L2）であり、実測の裏づけも無い | **コンポーネントから切断マーカー**「ここから先は観測していません / props の由来」 |
| 2 | **`requests`**（コンポーネント → 通信） | **コンポーネントと通信を結ぶ共通の証拠が得られなかった。** `fetch` の呼び出し元は観測していない | **通信から切断マーカー**「この通信を起こした箇所は特定していません / 証拠が無い」 |
| 3 | `binds`（props の記述箇所 → 値） | 静的解析は行っていない | 作らない |
| 4 | `maps`（カラム → 応答項目） | 確認にはレスポンス本文の読み取りが必要で、収集禁止項目にあたる（PoC-01 と同じ判断） | 作らない |
| 5 | 使用箇所とインスタンスの対応 | 同じコンポーネントが複数箇所で使われると一意に決まらない | 概要に「どの使用箇所が何番目を描いたかは観測していません」と書く |
| 6 | ライブラリ由来 / 動的生成の区別 | DOM だけでは区別できない | どちらも同じ理由（`anchor-missing`）を返す。区別できていないことを `notObserved` に明記 |

**この見た目こそが正しい観測結果である。** 線でつないで1本の経路に見せることはしていない。

### 5.2 導出の訂正を1件行った

経路が途中で切れているのに、右ドックの「この値の出所」が**到達していないテーブル・カラム**を
`poc.listings . 3 列`「実測」と書いていた。**これは嘘である。**

## 9. PoC-03 の判定

`01b` Q-03.4 の基準に当てる。

| 基準 | 成功の条件 | 実測 | 判定 |
| --- | --- | --- | --- |
| **誤答率（自作コンポーネント）** | **0%** | **0%（0 / 22、両バンドラ）** | **成功** |
| **正解率（自作コンポーネント）** | 95%以上 | **100%（22 / 22、両バンドラ）** | **成功** |
| **ライブラリ由来要素** | 「特定不能」と正しく返す | **3件とも「特定不能」。理由も返す。ただし「ライブラリ由来」と「動的生成」を区別できていない** | **条件付き成功** |
| **RSC 要素** | 自作と同等の精度 | **同等（6 / 6、誤答0）** | **成功** |
| **Turbopack** | webpack と同等に機能する | **同等。26要素すべてで判定が一致** | **成功** |
| **ビルド時間** | 注入なしの +30%以内 | 起動 **−0.2% / +0.2%**、ルート初回コンパイル **+39% / +87.2%** | **条件付き成功** |

### 判定: **条件付き成功**

**成功と呼べる部分**（対象として定義したケースで、再現可能な対応付けができている）

- 画面の値 → DOM 要素 → コンポーネント → **ソースファイルと行** が、**両バンドラ・Client / Server の両方で、誤答0で**成立した。
- 同じコンポーネントの複数回描画・ネスト・`map` の繰り返し・ライブラリ枠内の自作 JSX まで対応できた。
- 特定できない要素を**誤特定せず、理由付きで「特定不能」と返す**ところまで成立した。
- **PoC-01 の変換・レイアウト・描画をそのまま再利用**し、UI の設計を変えずにキャンバスへ出せた。

**「条件付き」である理由**

1. **開発ビルド限定**かつ**ビルド設定への介入が必要**である（方式1 の性質）。
2. **注入範囲（`src/`）の外は特定不能**になる。これは正しい振る舞いだが、選択できる要素が狭まる。
3. **ライブラリ由来と動的生成を区別できていない**。`FR-11b`（理由を区別して提示）を**部分的にしか満たしていない**。
4. **ルート初回コンパイルが +39% / +87%** で、`01b` の「成功」基準（+30%以内）に入らない。原因は特定済み（構文解析器の読み込み）で、最適化していない。

**成功扱いにしていないこと**

- **E（値の由来）は成立していない。** `derives` を作っていない。`01b` Q-04.0 の結論（この対応づけは原理的に L2）は**今回の実測でも覆っていない**。
- **ブラウザ側とサーバー側はつながっていない。** `requests` の証拠が無いので関係を作っていない。
- `shadcn/ui` 等の**実在の UI ライブラリでは試していない。** 題材は「`src/` の外にある、JSX を持たない配布形式のコード」で代替した。実在ライブラリ特有の事情（`forwardRef`・`asChild`・ポータル）は未検証である。
- **ポータル・`Suspense` 境界・`React.memo`・条件分岐で入れ替わる要素**は試していない。
- 要素数は26である。**大規模なページ・多数のコンポーネントでの精度と性能は未検証**である。
