## 2. 推奨案

### 2.1 スタイルを書き込む既定の幅

> **推奨: 「その性質を、選んだアートボードでいま決めている指定」に書く。その性質の指定がまだ無いときは「すべての幅（基本）」に書く。** どちらの場合も、書き込み先の幅と、**変わるアートボード／変わらないアートボード**を値の横に常に示し、1操作で「この幅以上だけ」に切り替えられるようにする。

| 例（`p-4 md:p-6`、Desktop 1440 と Mobile 375 を並べている） | 既定の書き込み先 | 示すこと |
| --- | --- | --- |
| Mobile で余白を選ぶ | `p-4`（基本） | 「すべての幅に効きます。ただし md 以上は md:p-6 が優先されるため、Desktop は変わりません」 |
| Desktop で余白を選ぶ | `md:p-6`（md 以上） | 「md（768px）以上に効きます。Mobile は変わりません」 |
| Desktop で、まだ指定の無い角丸を足す | 基本（`rounded-lg` を追加） | 「すべての幅に効きます」＋［md 以上だけにする］ |

| 理由 | 内容 |
| --- | --- |
| 見ている値と書く場所が一致する | 利用者はアートボードで見えている値を変えたい。その値を決めている指定を書けば、見えている値が期待どおりに変わる。基本に固定すると、Desktop で変えたのに Desktop が変わらない（md の上書きに負ける）ことが起きる |
| 新しい上書きを黙って増やさない | 「選んだアートボードの幅に書く」を既定にすると、操作のたびに `lg:` `md:` の上書きが増え、コードが読みにくくなる（原則「コードが正」「生成物は読めるコード」に反する） |
| 毎回尋ねない | 書き込み先を毎回選ばせると操作が止まる（`03` 原則1・9）。既定で進め、影響を見せ、1操作で変えられる形にする |
| Tailwind の考え方と合う | モバイルファーストの基本と上書きの関係を、そのまま利用者に見せられる |

| 採らなかった案 | 理由 |
| --- | --- |
| 常に基本へ書く | 上書きのある性質で「変えたのに変わらない」が起きる（`02e` 1.2節 I-1 と同種の食い違い） |
| 常に選んだアートボードの幅へ書く | 上書きが増え続ける。Mobile での編集は基本になるため、アートボードによって振る舞いが変わって見える |
| 毎回選ばせる | 操作が止まる。影響の提示で足りる |

> **補正（0.2・`04e` R-01）: 「選択した表示幅」と「変更が適用される幅」を区別して示す。** スマホのアートボードで選んでも、書き込み先が基本（variant なし）なら変更は**すべての幅**に適用される。右ドックでは次の3つを別の行・別の語で示す: ①**選択した表示幅**（どのアートボードで選んだか・そこで効いている指定）②**変更が適用される幅**（書き込む指定の variant。基本なら「すべての幅」と書く）③**見た目が変わる幅**（上書きを差し引いた結果。開いているアートボードごとの変化と、開いていない幅は未確認であること）。上の表の「示すこと」は③に当たる。視覚の具体は `04e` 2.5節。

### 2.2 変更をまとめる単位

> **推奨: 3つの単位を分ける。**
>
> | 単位 | 推奨 | 理由 |
> | --- | --- | --- |
> | **操作の単位**（Undo / Redo の1回） | 1つのプロパティへの**1回の確定**。文字入力は確定（入力欄を離れる・確定キー）までを1回、ドラッグは離すまでを1回 | 1文字ずつの Undo は役に立たない。確定の単位は利用者の意図の単位 |
> | **変更案の単位**（下書きの1つ） | 利用者の編集は**「作業中の変更案」1つ**に溜まる（ページ・ファイルをまたいでよい）。**AI の提案と生成（ページ追加・プロジェクト作成）は、それぞれ別の変更案**として届く。利用者は明示操作で作業中の変更案を分けられる（後続予定でも可） | 確認・適用・検証・取り消しの単位を「1つの目的」に揃える。AI の提案を利用者の操作に溶かさない（`02e` 6.9） |
> | **適用の単位** | **変更案の全体を一度に**（全ファイルを書くか、何も書かない）。一部だけ適用したいときは、変更案から**独立した操作を外して**から適用する（外せない場合は理由を示す） | 検証と取り消しが変更案の単位で成り立つ。部分適用を許すと、何が書かれたかの説明が難しくなる |
>
> **注記（0.2・`04e` R-03）: 複数ファイルにまたがる「全ファイルか無か」の適用は UX 上の要求であり、実装済みの保証ではない。** 成立するか、途中で失敗したときに書いたファイルを特定して書き戻せるか、書き戻しにも失敗したときに何を示すかは EP-06 で確かめる（`02e` 8.1）。成立するまで、UI は「何も書き込んでいません」を約束する文言を置かず、適用の結果をファイルごとに示せる構成にする（EC-17・EC-18）。EP-06 が成立しなければ、変更案を1ファイルずつに制限する。

| 補足 | 内容 |
| --- | --- |
| 変更案の大きさの表示 | 変更案には常に「N 件の操作 ／ M ファイル」を示す。大きくなっても自動では分けない |
| 1操作ずつ適用したい利用者 | 変更案を小さく保ち、こまめに適用すればよい（適用は S-14 で1操作）。**「操作のたびに自動で適用する」設定は置かない**（明示的な適用 — ED-11） |
| 外せる操作 | 他の操作と同じプロパティ・同じ範囲に触れていない操作だけ。触れていれば「この操作の後に同じ箇所を変えています」と示して外せなくする |

### 2.3 モード移動時の未適用案の扱い

> **推奨: 未適用の変更案は「下書き」として保持し、適用も破棄もしない。確認を挟まずにモードを移る。** 探索モードは**作業ツリーのコードだけ**を表示し、未適用の変更は持ち込まない。N0 の変更の状態に「未適用の変更 N 件（探索には反映されていません）」を常に出す。編集モードに戻ると、変更案・選択・アートボードの配置が復元される。

| 状況 | 扱い |
| --- | --- |
| 確定済みの操作がある | そのまま下書きに残る |
| **入力途中で、値が有効**（確定していない） | **確定しない**（0.2 で改訂）。値を「入力途中」として選択に結びつけて保持し、下書き・適用前プレビュー・差分に入れない。N0 の変更の状態に「✎ 未確定の入力 1（下書きに入っていません）」。編集モードに戻ると入力欄に値を復元し、［確定］か入力欄の取り消しを選べる |
| **入力途中で、値が不正**（解析できない・使えない値） | 確定しない・適用前プレビューにも入れない。入力した文字列をそのまま「入力途中」として保持し、戻ったときに入力欄の下へ理由（例: 「p-17 はこのプロジェクトの余白の値にありません」）を出す。**黙って捨てない** |
| 適用前プレビューを表示している | モードを移ると閉じる。戻ると再び表示できる |
| 探索モードで経路を見る | 作業ツリーのコードに対する観測だけを使う。下書きの内容で経路を作らない |
| 下書きを持ったまま IDE を閉じる | 下書きは IDE のローカルに残る（下書き保存）。次に開いたとき、基準の版と作業ツリーが違えば競合の判定から始める（UX-E09） |

| 理由 | 内容 |
| --- | --- |
| 作業を失わせない | 破棄すると、出所を確かめに行っただけで編集が消える。UX-E06（動的な値 → 探索 → 戻る）が成り立たない |
| 確定していない値を確定しない（0.2） | モードの移動は「出所を確かめに行く」「状態を見に行く」ためのことが多く、値を決めたという意思表示ではない。確定すると、利用者が決めていない値が下書き・差分に入る。保持して戻ったときに決めてもらう（`02e` 6.10 #5「黙って確定しない」を満たす） |
| 黙ってコードを変えない | 自動で適用すると、明示的な適用（NFR-14・ED-11）を破る |
| 確認ダイアログを置かない | 保持は安全側で取り消し可能なので、尋ねる理由が無い（UXR-25） |
| 探索の誠実さを守る | 下書きは作業ツリーに無いので、探索に混ぜると「動いていないコードの経路」を見せることになる（P-4） |

| Git コミット | IDE は行わない。「コミットはお使いの Git の手順で行ってください」 | 「コミット済み」 |
| 適用前プレビュー | **適用前プレビュー**（方式 A なら「予測」、方式 B なら「作業ツリーには未適用」を添える） | 「ライブ」「実ページ」 |
| 実描画 | **現在のコード**（アートボードの見出し） | — |
| 検証 | **検査**（「検査に通りました（実行した検査 3 件）」「検査で問題が見つかりました」「未検査」） | 「検証済み」「正しく動作します」「成功」単独 |
| AI の提案完了 | 「AI の提案があります（未適用）」 | 「AI が変更しました」（適用と読まれる） |
| 利用箇所 | 「検出できた利用箇所 N 件」 | 「N 箇所で使用」（網羅と読まれる）、「N 箇所で描画」 |
| 描画の回数 | 「このアートボードで M 回描画」 | 「M 件」単独 |
| 定義元 | 「この値の指定: ファイル:行」 | 「スタイル」単独 |
| 影響範囲 | 「確認できた範囲: …」「確認できない範囲: …（理由）」 | 「影響なし」（不明を含むとき） |
| 外部変更 | 「コードが IDE の外で変更されました」 | 「エラー」 |
| 競合 | 「下書きと外部の変更が同じファイルに重なっています」 | 「衝突エラー」 |
| 観測の鮮度 | 「変更前のコードで観測した経路です」「この観測がいまのコードに対応するか確かめられません」 | 「古いデータ」単独 |

> **「実測」「推定」の語は観測にだけ使う**（`03` 4.2節）。適用前プレビュー・下書き・検査の結果に「実測」「推定」を付けない。編集の根拠（「このテキストはコードに直接書かれています」）は、現在のコードを読んだ事実として書き、観測性の語を付けない（C-7）。

### 3.3 禁止表現（`03d` 6章への追加）

| 禁止 | 理由 | 代わりに |
| --- | --- | --- |
| 1つの「完了」で、AI の提案・適用・検査をまとめる | 3つは別の事実 | 「提案があります」「適用しました」「検査に通りました」を別々に |
| 「検証済み」「正しく動作します」 | 実行した検査のこと以上は言えない | 「検査に通りました（実行した検査: 型検査・再描画・対象要素）」 |
| 「影響はありません」（不明な範囲があるとき） | 網羅を保証できない | 「確認できた範囲: … ／ 確認できない範囲: …」 |
| 「N 箇所で使われています」 | 検出漏れがある | 「検出できた利用箇所 N 件」 |
| 「保存しました」（適用の意味で） | 下書き保存と混同 | 「コードに適用しました」 |
| 「元に戻しました」（適用の取り消しで、実際にはファイルを書いた） | Undo と区別できない | 「適用を取り消すための変更を、コードに適用しました」 |
| 「同期しました」（作業ツリーの外部変更を取り込んだとき） | 何が起きたか分からない | 「外部の変更を読み込みました（変更されたファイル N 件）」 |

### UX-E01. 既存ページの静的な文言・スタイルを編集する

> 編集トラックの基本フロー。**変更案の作成 → 適用前プレビューと差分の確認 → 明示的な適用 → 実際の再描画 → 検査結果の確認**（ED-11）を通しで示す。

#### 1. 目的と開始条件

| 項目 | 内容 |
| --- | --- |
| 目的 | 画面で見えている見出しの文言と余白を変え、通常のコードとして残す |
| 開始条件 | ①プロジェクトを IDE から起動している（実行中）②要素の識別子の注入が有効（無ければ EC-04 で止まる — EP-09）③作業ツリーと IDE の知っている版が一致（不一致なら UX-E09 から） |
| 入口 | ①モードタブの［編集］②探索モードの要素から（UX-E06 の逆向き） |

#### 2. 操作

| # | 操作 |
| --- | --- |
| ① | 編集モードに入る。左のページ一覧で対象ページを選ぶ（探索から来た場合は選択済み） |
| ② | アートボード上で見出しをクリックする |
| ③ | 右ドックの「内容」で文言を書き換え、確定する |
| ④ | 「スタイル」で内側の余白を変える（書き込み先の幅は 2.1 の既定のまま） |
| ⑤ | N0 の「未適用の変更 2 件」から S-14 を開く |
| ⑥ | 適用前プレビューと差分を確かめ、［コードに適用］を押す |
| ⑦ | 再描画と検査の結果を確かめる |

#### 3. システムの応答と状態変化

| 操作 | 応答 | 状態（`02e` 6章） |
| --- | --- | --- |
| ① | アートボードを並べる（既定の幅は UX-E04）。各見出しに「現在のコード」 | G: 実描画 |
| ② | 主選択の枠。右ドックに見出し（`h1` ／ `Hero.tsx:12`）、**編集可否「編集できます」**、パンくず。文言の由来「このテキストはコードに直接書かれています（Hero.tsx:12）」 | E: 編集可能 |
| ③ 入力中 | 適用前プレビューがあれば、アートボードの見出しが「適用前プレビュー」に変わり、文言が変わって見える | A: 編集中 |
| ③ 確定 | 変更案に1件入る。N0「未適用の変更 1 件 ・ 下書きに保存しました」。右ドックの値の横に「変更前: …」 | A: 変更案あり |
| ④ | 余白の行に**書き込み先**（`Hero.tsx:12` の `p-4`）と**影響**（「すべての幅に効きます。md 以上は md:p-8 が優先されます」）。確定で2件目 | A: 変更案あり |
| ⑤ | S-14: 変更案の一覧（利用者の下書き 1 件・操作 2 件・1 ファイル）。差分（`Hero.tsx`）。**適用前プレビュー**と「現在のコード」を切り替えて見られる。検査は「適用後に行います」 | — |
| ⑥ | 適用の直前に、基準の版と作業ツリーを比べる（一致）。書き込み → 新しい版。N0「コードに適用しました（未コミット）・再描画を待っています」。アートボードの見出し「更新を待っています」 | A: 適用中 → 適用済み、G: 更新待ち |
| 再描画 | 開発サーバーが新しい版を描く。見出し「現在のコード」に戻る。検査を開始 | G: 実描画、C: 検査中 |
| ⑦ | 検査結果: 「検査に通りました（実行した検査: 再描画・対象要素の文言と余白）」。型検査を実行しなかった場合はそれを書く | C: 検査に通過 / 一部のみ |

#### 4. 選択対象と変更範囲

| 層（`02e` 3.9） | この例 |
| --- | --- |
| ① 選択 | Desktop アートボードの `h1` の描画 |
| ② ソース上の対象 | `Hero.tsx:12` の `<h1>` |
| ③ プロパティ | 文言 ／ 内側の余白 |
| ④ 書き込み先 | `Hero.tsx:12` の JSX テキスト ／ 同じ要素の className の `p-4` |
| 影響範囲 | 確認できた範囲: この `h1` の全描画（1 回）。`Hero` の検出できた利用箇所 1 件。確認できない範囲: なし |

**探索モードの選択への影響**: 適用で `Hero.tsx` の行・列がずれた場合、選択を探し直す（UX-E09-3）。

#### 5. 完了条件

| 判定 | 条件 |
| --- | --- |
| 完了 | ①コードに適用された（新しい版）②再描画された ③検査の結果が示された（通過・問題・一部のみのいずれでも「示された」こと）④利用者が「適用」「検査」を別々に読み取れる |
| 完了ではない | 適用前プレビューで期待どおりに見えただけ／適用しただけで再描画を確かめていない |

#### 6. 失敗時・キャンセル時・復帰時

| 事象 | 扱い |
| --- | --- |
| 選んだ要素が動的な値 | 入力欄を出さない。EC-01 → UX-E06 |
| 書き込み先を特定できない | EC-02（定義元を特定できない）。候補があれば示す |
| 書き込み先が初期範囲外の種類（CSS Modules 等） | EC-03。定義元のファイル・行を示す。編集はしない |
| 混在する文言（`No.{id}`） | 固定の部分だけ入力欄を出し、式の部分は由来を示す（条件付き） |
| 入力をやめる | Esc は選択を戻すだけ（IX-E04）。入力を確定前に取り消すには入力欄の中での取り消し（UI） |
| 下書きをやめる | S-14 で［下書きを破棄］（UX-E08） |
| 適用の直前に外部変更が見つかった | 適用しない。EC-06（競合）または EC-07（重ならない外部変更）→ UX-E09 |
| 書き込みに失敗（権限・ディスク） | 何も書かない（全ファイルか無か）。EC-17「コードに適用できませんでした」。下書きは残る |
| 再描画が来ない（ビルドエラー等） | アートボードは「更新を待っています」のまま一定時間 → EC-10「再描画を確認できません」＋実行モードのログへの導線。適用は済んでいることを明記 |
| 検査で問題 | EC-09。［適用を取り消す］（UX-E08）と［問題の箇所を見る］ |
| 復帰（IDE を閉じて開き直す） | 下書きが残っている。基準の版と作業ツリーを比べ、一致なら下書きを復元、違えば UX-E09 |

#### 7. 未検証の技術と縮退

| 依存（EP） | 縮退したときの UX |
| --- | --- |
| EP-02 整形を壊さない書き換え | 差分に整形の変化を区別して示す。無理なら文言だけ編集可能にし、スタイルは EC-03 と同じ扱い。さらに無理なら編集モードを「準備中」に戻す |
| EP-12 適用前プレビュー | 方式 B → A → 無し。**無しのとき**: ③ でアートボードは変わらず、右ドックに「変更前 → 変更後」の値だけ。S-14 は差分だけ。適用後の実描画で確かめる |
| EP-05 外部変更の検出 | 常時の検出が無ければ、N0 の「コードの状態」を出さず、⑥ の直前の比較だけで競合を出す |
| EP-07 再描画と一致の確認 | 検査は「未検査」のまま。「アートボードで変更を確かめてください」と書き、通過とは言わない |

### UX-E08. Undo / Redo、未適用案の破棄、適用済み変更の取り消し

#### 1. 目的と開始条件

| 項目 | 内容 |
| --- | --- |
| 目的 | ①直前の操作を戻す・やり直す ②下書きをまとめて捨てる ③適用してしまった変更を取り消す |
| 開始条件 | 編集モード |

#### 2. 操作と 3. 応答

| 操作 | 何が変わるか | 応答 | 確認 |
| --- | --- | --- | --- |
| **Undo**（未適用の操作） | 下書きの最後の操作を外す。**ファイルは変わらない** | 右ドックの値・適用前プレビューが戻る。1行通知「余白の変更を戻しました（下書き）」 | なし |
| **Redo** | 外した操作を戻す | 同上 | なし |
| Undo（AI の提案を受け入れた直後） | 提案の変更案を**1単位で**外す（利用者の操作の列に混ぜない） | 「AI の提案を下書きから外しました」 | なし |
| **下書きを破棄** | 変更案ごと捨てる | S-14 で［下書きを破棄］。破棄した下書きは**このセッションの間は［破棄を取り消す］で戻せる** | なし（取り消せるため — UXR-25） |
| 下書きから1つの操作を外す | 独立した操作だけ（2.2） | 外せない場合は理由 | なし |
| **適用の取り消し** | 適用で書いた内容を元に戻す**新しい変更案**を作る（逆の差分） | S-14 の履歴で［適用を取り消す］→ 逆の差分を**下書きとして**開く → 利用者がそのまま適用 | なし（差分を見ることが確認 — UXR-E01） |
| Undo（直前に適用した直後） | **Undo では適用を取り消さない**。Undo の対象は下書きの中の操作だけ | Undo を押すと「適用した変更は Undo では戻りません。［適用を取り消す］を使ってください」（1行） | — |

> **Undo と適用の取り消しを見分ける**: Undo は「ファイルが変わらない」、適用の取り消しは「ファイルが変わる（新しい適用）」。語（3.3「元に戻しました」の禁止）と場所（Undo は編集の操作群、適用の取り消しは S-14）で分ける。

#### 4. 選択対象と変更範囲

| 操作 | 選択 |
| --- | --- |
| Undo / Redo | 選択は変えない。戻した操作の対象が選択と違えば、その対象を副次枠で一瞬示す（UI） |
| 破棄 | 選択は変えない |
| 適用の取り消し | 適用後の再描画で選択を探し直す（UX-E09-3） |

#### 5. 完了条件

①Undo / Redo でファイルが変わらないことが分かる ②破棄が取り消せる ③適用の取り消しが差分付きで行われ、再描画・検査まで通る。

#### 6. 失敗時・キャンセル時・復帰時

| 事象 | 扱い |
| --- | --- |
| 適用した範囲が、その後に変わっている（外部変更・別の適用） | 逆の差分を作れない部分を示す。EC-14「この適用は取り消せません（その後に同じ箇所が変更されています）」。わからないこと: 「どちらの変更を残すべきかは IDE では判断しません」。次の操作: ［変更された箇所を見る］。**IDE は上書きしない**。Git での戻し方を案内 |
| 外部変更が下書きの対象ファイルに入った | その対象ファイルについて、それより前の Undo を止める。「外部の変更より前には戻せません」（`02e` 6.9） |
| 過去のセッションの適用 | Undo の列には無い。S-14 の履歴から［適用を取り消す］ |
| IDE を閉じた後の Undo | 下書きの操作列は残る（下書き保存）。Redo の列は残さない（推奨。理由: 閉じた時点での「やり直し」の意図は失われている） |

#### 7. 未検証の技術と縮退

| 依存 | 縮退 |
| --- | --- |
| EP-06 無関係な変更を壊さない取り消し | 適用の取り消しは、適用した内容がそのまま残るファイルだけ。他は Git へ案内 |
| EP-06 原子性 | 変更案を1ファイルずつに制限 |

#### 8. 対応する IA・画面・要件

`EditIntent`、`ChangeSet`（状態）、`AuditEntry`、`CodeRevision(ide-revert)`。S-11、S-14。FR-16、FR-16b（CP-05）、NFR-16、NFR-28、UXR-25。

### UX-E09. 外部変更・競合・選択対象の消失に対応する

> 3つの事象を1つのフローにまとめる。どれも「背景で変わった事実」であり、**通知して、利用者の操作で切り替える**（UXR-29）。

#### 1. 目的と開始条件

| 項目 | 内容 |
| --- | --- |
| 目的 | 外部エディタ・AI・`next dev` によるコードの変更に気づき、下書きを失わず、外部の変更も上書きせずに作業を続ける |
| 開始条件 | 編集モード（他のモードでも N0 には出る） |

#### 2. 操作 / 3. 応答と状態変化

**E09-1 外部変更（下書きと重ならない）**

| 段階 | 応答 | 状態 |
| --- | --- | --- |
| 検出 | N0「コードが IDE の外で変更されました（N ファイル）」。バナー（自動で消えない）: ［変更を読み込む］ | D: 外部変更あり |
| 影響の提示 | ①観測: 変わったファイルに関わる経路は「変更前のコードで観測した経路」（F: 古い）②アートボード: 開発サーバーが再描画すれば実描画が新しい版になる。再描画前は「更新を待っています」③下書き: 重ならないので保持 | F: 古い、G: 更新待ち |
| ［変更を読み込む］ | ソース上の対象（`JsxSite`・定義元）を読み直し、選択を探し直す（E09-3）。下書きの基準の版を新しい版へ進める | D: 同期 |
| 誰が変えたか | `next dev` 自身の書き込み（`next-env.d.ts` 等）は「開発サーバーが書き換えました」と区別する（既存の検知と同じ）。AI の直接書き込みは「AI が…」（UX-E07）。それ以外は「IDE の外で」（エディタの特定はしない） | — |

**E09-2 競合（下書きと重なる）**

| 段階 | 応答 | 状態 |
| --- | --- | --- |
| 検出 | N0「競合: 下書きと外部の変更が同じファイルに重なっています」。バナー［競合を確かめる］。下書きの該当の変更案は**適用できない** | A: 競合、D: 競合あり |
| S-14 | 重なっているファイルについて、下書きの差分と外部の変更の差分を並べる | — |
| 選べる道（最大2つ — UXR-17） | ①［新しいコードの上で下書きを作り直す］（下書きの操作を新しい版に当て直す。当て直せない操作は理由つきで外れる）②［この下書きを破棄］。**外部の変更を上書きする道は用意しない**（UXR-E13） | A: 変更案あり / 破棄 |
| 適用の直前に見つかった場合 | 適用しない。同じ S-14 の表示へ | — |

**E09-3 選択対象の消失**

| 事象 | 応答 |
| --- | --- |
| 行・列がずれた | 「コードが変わったため、選択を探し直しています」→ 見つかれば移し「選択を新しい位置（Hero.tsx:14）に移しました」（**同じ要素だと断定する語を使わない**）→ 見つからなければ EC-08 |
| 要素が無くなった | EC-08「選んでいた要素は、いまのコードで見つかりません」。保持: 最後の位置・要素名・文言の先頭・版。次の操作: ［親の要素を選ぶ］［変更内容を見る］ |
| この幅で描画されなくなった | 選択は保つ。「この幅では描画されていません」 |
| 再描画の前 | 古い描画の上で編集させない（`revision-mismatch`）。「更新を待っています」 |

#### 4. 選択対象と変更範囲

選択は**無言で解除しない**（UXR-E11）。下書きの書き込み先（④）は、新しい版で当て直せたものだけ残る。当て直せないものは理由つきで一覧にする。

#### 5. 完了条件

①外部の変更が上書きされていない ②下書きが失われていない（または利用者が破棄を選んだ）③古い観測が古いと示された ④選択の行方（移した・見つからない）が示された。

#### 6. 失敗時・キャンセル時・復帰時

| 事象 | 扱い |
| --- | --- |
| バナーを無視して編集を続ける | 重ならない外部変更なら続けられる。適用時に改めて比較。競合中の変更案は適用できない |
| 外部変更が連続する | バナーを積み重ねず、件数を更新（IX-33） |
| 作業ツリーが大きく変わった（ブランチの切替） | 「多くのファイルが変更されました（N 件）」。下書きは全件を競合判定。観測はすべて「古い」 |
| IDE を開き直したら基準の版と違う | 起動時に同じ判定（重ならなければ基準を進めてよいか尋ねずに進め、1行通知。重なれば競合） |

#### 7. 未検証の技術と縮退

| 依存 | 縮退 |
| --- | --- |
| EP-05 外部変更の検出 | 常時の検出が無ければ E09-1 のバナーを出さない。**適用の直前と、編集モードに入る時**の比較だけ。N0 の「コードの状態」は「確かめていません（適用時に確かめます）」 |

#### 8. 対応する IA・画面・要件

`CodeRevision(cause)`、`ChangeSet(競合)`、`SelectionTarget`（最後に確認できた選択）、`LineagePath.observedRevision`。N0、バナー、S-14。FR-04、NFR-16、NFR-52、UC-03 代替A3、UXR-29、ST-03、ST-14。

> **範囲（0.2・`04e` R-04）: 本章の「ダイアログなし」は通常の編集フローの方針である。** 既存の危険操作の要件 — NFR-23（本番への書き込み・データ削除・`DROP`/`TRUNCATE`・外部への送信は AI が自律実行できず、ユーザー操作でも二段階の確認を要する）、`03` UXR-25（C群の削除・デプロイで二段階確認を導入）、FR-74（危険な操作の区別）、FR-54（任意 SQL の書き込みは明示的な許可） — は、そのまま有効である。編集トラックの操作がこれらに当たる場合は、本章ではなく既存の要件に従う。下表の「AI への依頼の送信」が NFR-23 の「外部への送信」に当たるかは要件定義の判断とする（`02f` C-14）。

| 操作 | 取り消せるか | ダイアログ | 判断を支えるもの |
| --- | --- | --- | --- |
| 値の編集（下書き） | Undo | なし | 右ドックの書き込み先・影響範囲（UXR-E02・E03） |
| 下書きの破棄 | セッション中は［破棄を取り消す］ | なし | S-14 の一覧（何を捨てるか見えている） |
| **コードへの適用** | 適用の取り消し（条件付き） | **なし** | **S-14 の中でだけ押せる**（差分と適用前プレビューを見る画面が確認を兼ねる — UXR-E01）。直前の比較で競合があれば押せない |
| 適用の取り消し | もう一度の取り消し | なし | 逆の差分を下書きとして開き、同じ S-14 で適用する |
| 取り消しに条件が付く操作（外部変更の後の取り消し） | 一部できない | なし | **押す前に**、取り消せない部分と理由をインラインで示す（EC-14） |
| アートボードを閉じる | 開き直せる | なし | 「表示を閉じる」であることを語で示す（UXR-E05） |
| ページの削除【後続予定】 | 適用前は Undo、適用後は適用の取り消し | なし | 削除は変更案の操作。S-14 の差分に「ファイルを削除」と出る |
| 新規プロジェクトの作成【後続予定】 | 作成先が空のフォルダなので、フォルダを消せば戻る | なし | 生成内容の一覧（④）。**空でない場所は選べない**（確認ではなく拒否） |
| AI への依頼の送信【後続予定】 | 送信は取り消せない（外部へ送る） | **なし（インラインの明示操作）** | 送信の前に渡す文脈の一覧を見せる（SG-09・NFR-22。`03` UXR-24 と同じ「インラインの1操作」） |
| 外部の変更の上書き | — | — | **操作自体を用意しない**（UXR-E13） |

## 7. 状態カード（EC-01〜）

`03d` 1.1節の4要素（①事実 ②理由 ③わからないこと ④次にできること 0〜2個）で書く。ER-01〜09 をそのまま適用する。

| ID | ① 何が起きたか | ② なぜか | ③ この結果わからないこと／できないこと | ④ 次にできること |
| --- | --- | --- | --- | --- |
| **EC-01** | この値はここでは編集できません | この値はデータ（または props）から来ています（推定） | 値を変えるには、データか、値を渡しているコードを変える必要があります。どちらかは出所を見ないと判断できません | ［出所を探索］ |
| **EC-02** | この性質の指定がどこにあるか特定できません | コードの指定と、実際に効いている値が合いません（または候補が複数あります） | どこを書けばこの見た目が変わるかが分かりません | ［候補を見る］（候補があるとき） |
| **EC-03** | この性質は、ここでは編集できません | 指定は `card.module.css:12` にあります。この種類の指定の編集にはまだ対応していません | — | ［指定の場所を見る］（コードピーク） |
| **EC-04** | このプロジェクトでは編集モードを使えません | 画面の要素とコードを結ぶための設定がありません（要素の識別子の注入） | 選んだ要素がどのコードかを確かめられないため、書き込み先を決められません | ［対応範囲を見る］ |
| **EC-05** | この要素は編集できません | ライブラリの中で描かれた要素です | — | ［親の要素を選ぶ］ |
| **EC-06** | 下書きと外部の変更が同じファイルに重なっています | 下書きを作った後に、IDE の外で `Hero.tsx` が変更されました | この下書きはいまのコードに適用できません | ［新しいコードの上で作り直す］［下書きを破棄］ |
| **EC-07** | コードが IDE の外で変更されました（N ファイル） | 理由を特定できません（または: 開発サーバー／AI が書き換えました） | 変わったファイルに関わる経路は、変更前のコードの観測です | ［変更を読み込む］ |
| **EC-08** | 選んでいた要素が、いまのコードで見つかりません | コードが変わり、要素の位置または要素そのものが変わりました | 最後に確認した位置: Hero.tsx:12 の h1 | ［親の要素を選ぶ］［変更内容を見る］ |
| **EC-09** | 検査で問題が見つかりました | 例: 対象要素の余白が変わっていません（md 以上の指定が優先されています） | 適用したコードは作業ツリーにあります | ［問題の箇所を見る］［適用を取り消す］ |
| **EC-10** | 再描画を確認できません | 開発サーバーから新しい描画が届きません（ビルドエラーの可能性は、ログを見ないと判断できません） | 適用は済んでいます。表示がコードと一致しているかは確かめていません | ［実行のログを見る］ |
| **EC-11** | AI の提案を作れませんでした | AI の応答（そのまま表示）／時間切れ／対象外のファイルへの変更を含みました | 何も変更していません | ［指示を直して依頼し直す］ |
| **EC-12** | 変更前のコードで観測した経路です | 観測の後に、この経路に関わるファイルが変わりました | いまのコードで同じ経路を通るかは確かめていません | ［再読み込みして観測し直す］ |
| **EC-13** | この観測がいまのコードに対応するか確かめられません | 観測にコードの版の記録がありません（記録済みのデータ・外部で起動したサーバー） | — | ［IDE から起動して観測する］（該当するとき） |
| **EC-14** | この適用は一部取り消せません | 適用の後に、同じ箇所が変更されています | どちらの変更を残すべきかは IDE では判断しません | ［変更された箇所を見る］ |
| **EC-15** | この幅では描画されていません | （例）`hidden md:block` により、768px 未満では表示されません | — | ［描画されている幅のアートボードを選ぶ］ |
| **EC-16** | 1件だけの見た目の変更には対応していません | この要素は同じコードから 10 回描画されています | どの描画がどのデータかは同定していません | ［全件の見た目を変える］［出所を探索］ |
| **EC-17** | コードに適用できませんでした | ファイルに書き込めません（権限・空き容量など、システムの応答をそのまま） | 何も書き込んでいません。下書きは残っています（**この文は EP-06 で「全ファイルか無か」が成立した場合だけ使う** — 0.2） | ［もう一度適用する］ |
| **EC-18**（候補・0.2） | 一部のファイルだけ書き込まれた可能性があります | 適用の途中で書き込みに失敗し、書き戻しを確かめられませんでした | ファイルごとの状態（書いた／書いていない／書き戻した／書き戻せなかった）。書き戻せなかったファイルの内容がどちらの版かは IDE では断定しません | ［ファイルごとの状態を見る］（S-14）。Git での確かめ方を案内 |

### 11.2 UI で崩してはならないこと

1. 適用は S-14 の中でだけ押せる（UXR-E01）。右ドックやアートボードに［適用］を置かない。
2. 書き込み先と影響範囲を、値の入力より前に読める位置に置く（UXR-E02）。
3. 利用箇所と描画回数を同じ見た目・同じ位置の数字にしない（UXR-E04）。
4. 適用前プレビューを、実描画と同じ見出し・同じ枠で描かない（UXR-E06）。
5. 「提案があります」「適用しました」「検査に通りました」を1つのチェック記号にまとめない（UXR-E08）。
6. 動的な値に無効化した入力欄を置かない（UXR-E10）。
7. 探索モードの面・情報量を変えない（UXR-E14）。
8. 既存のダーク・低彩度の符号（実線＝実測、破線＝推定）を、編集の状態（下書き・適用前プレビュー）の表現に転用しない。
