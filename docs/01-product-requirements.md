## 0. この文書の読み方

### 0.1 記法

| 記法 | 意味 |
| --- | --- |
| `FR-xx` | 機能要件 (Functional Requirement) |
| `NFR-xx` | 非機能要件 (Non-Functional Requirement) |
| `UC-xx` | ユースケース |
| `R-xx` | 技術的リスク |
| `Q-xx` | 未決定事項 / 検証が必要な問い |
| `P0 / P1 / P2` | 優先度。P0 = MVP必須、P1 = MVP直後、P2 = 将来 |
| `L0〜L3` | 観測性レベル。[第5章](#5-観測性モデル実測できる情報と推測する情報)で定義 |

### 0.2 本文書が特に重視した論点

本要件定義では、次の3点を他より厚く扱っている。

1. **「実測できる情報」と「推測する情報」の峻別**（第5章）。本プロダクトの最大の価値は「内部で何が起きているかを正しく理解させること」であり、最大の失敗は「正しそうに見える誤った図を見せること」である。したがって観測可能性の限界をプロダクトの中心的な設計制約として先に定義した。
2. **参考画像の情報階層の分析**（第6章・付録A）。見た目の模写ではなく、情報の重複を避けるための構造（番号バッジによる3ビュー同期、実線/破線の意味付け）を抽出した。
3. **優先順位と依存関係の明示**（第7章・第9章）。機能は削除せず、段階化して全て保持している。MVP外の機能は「不採用」ではなく「後続フェーズ」である。

## 1. プロダクトビジョン

### 1.1 ビジョン・ステートメント

> **アプリケーションの内部で起きていることを、見える状態にする開発環境。**
>
> コードを書く人にも、書かない人にも、「いま画面に出ているこの値が、どこから、どう流れてきたのか」が同じ一枚の図の上で分かる。

### 1.2 プロダクトの位置づけ

本プロダクトは **ノーコードツールではない**。コードを隠蔽するのではなく、コードとその実行結果の対応関係を可視化する。生成物は常に通常のソースコードであり、本IDEを使わなくなってもプロジェクトは動き続ける（ロックインしない）。

既存カテゴリとの関係は次の通り。

| 既存カテゴリ | 代表例 | 本プロダクトとの差分 |
| --- | --- | --- |
| ビジュアルIDE | Onlook, Webflow系 | ビジュアル編集に加え、**画面の裏側（API/DB/インフラ）まで同一画面で辿れる** |
| ノーコード/ローコード | Bubble, Retool | コードを生成・隠蔽するのではなく、**既存コードを読み解いて見せる**。理解を目的とする |
| APM / 可観測性 | Datadog, Sentry, OpenTelemetry系 | 運用者向けの事後分析ではなく、**開発中のローカル環境での理解**が主戦場。非エンジニアも読める表現 |
| ブラウザ開発者ツール | Chrome DevTools | ブラウザ内で閉じず、**サーバー・DB・クラウドまで1本の線で繋ぐ** |
| DBクライアント | TablePlus, pgAdmin | テーブル単体ではなく、**画面上の表示との対応関係**を持つ |

### 1.3 プロダクト原則

本プロダクトの意思決定における優先順位。上位が常に優先される。

| # | 原則 | 意味 |
| --- | --- | --- |
| 1 | **誠実さが第一** | 推測を実測のように見せない。分からないことは「分からない」と表示する。網羅できない範囲は明示する |
| 2 | **理解を与える** | 操作の自動化より、何が起きたかの説明を優先する |
| 3 | **可視化が主、編集が従** | 判断に迷ったら可視化の品質を優先する。編集機能のために可視化を犠牲にしない (Phase 1.5 で確定) |
| 4 | **コードが正** | 可視化はコードの従属物。IDE独自のメタデータにロジックを持たせない |
| 5 | **既存プロジェクトに寄生する** | 新規プロジェクト専用にしない。既存コードベースを壊さず読み取る |
| 6 | **安全側に倒す** | 破壊的操作・本番環境への書き込み・秘密情報の露出は、既定で不可 |
| 7 | **一目で概要、必要なときだけ詳細** | 常時表示する情報量を最小化する |

### 1.4 モード構成の方針 (Phase 1.5 で確定)

本プロダクトは、**可視化（理解する）** と **編集（作る）** という目的の異なる2つの活動を扱う。Phase 1 では両者の同居の妥当性が未決定だった (H-07)。Phase 1.5 で以下のように確定した。

| 決定 | 内容 |
| --- | --- |
| 同一プロダクトに配置する | 「画面を編集し、その変更がどこに波及するか見る」という連続した体験に価値があるため、分離しない |
| **独立したモードとして設計する** | 可視化モードと編集モードを明確に分け、画面構成・選択モデル・右パネルの内容をモードごとに最適化する。両者を1つの画面に混在させない |
| **可視化を中核、編集を副次とする** | 機能の優先順位、実装順序、品質基準のいずれも可視化を優先する |
| モード間の遷移を設計する | 「この要素を編集する」「この要素の出所を見る」を相互に行き来できること。遷移時に選択状態を引き継ぐこと |

**この決定の実務的な帰結**:

- ビジュアル編集 (FR-13〜FR-16) は、中核価値の実証には不要であるため **B群**（中核価値の実証後）に配置する (`01c` 2.1節)。
- 技術検証で編集機能の成立が困難と判明した場合 (Q-03 代替3)、**編集機能をMVPから外してもプロダクトの中核価値は失われない**。この縮退可能性が、本方針の実利である。
- Phase 2 のIA設計では、モード切替をナビゲーション構造の第一階層として扱う。

### 1.5 成功の定義（暫定指標）

Phase 1 時点の仮説的な指標。Q-18 で検証する。

- **理解速度**: 「この画面上の値はどのテーブルのどのカラムから来ているか」をエンジニアが特定するまでの時間が、従来手段（エディタ+DevTools+DBクライアント往復）比で 1/3 以下。
- **非エンジニアの到達度**: 非エンジニアのプロダクトオーナーが、支援なしで「エラーが起きている層（画面/API/DB/外部サービス）」を正しく言い当てられる。
- **誤誘導のなさ**: ユーザーが「IDEの図を信じて誤った結論に至った」事例が発生しない（第5章の表示規約で担保）。

## 2. 対象ユーザー

### 2.1 ペルソナ

> **Phase 1.5 での確定事項**: **MVP の主要ユーザーは P1（フルスタックエンジニア）とする。**
> P3（非エンジニア）向けの理解支援は、**将来の重要機能として維持する**（削除しない）。ただしMVPの設計判断（情報密度、用語選択、既定の表示粒度）が競合した場合は、**P1 を優先する**。
> 根拠: ①中核価値（順方向トレース）の精度と限界を正しく評価できるのは P1 である ②P3 向けの表現は、P1 向けに成立した可視化の上に段階的開示 (6.4節) として重ねられる ③逆順（P3 先行）では、精度不足を検証できないまま表現だけが先行するリスクがある。

#### P1. 個人開発者 / 小規模チームのフルスタックエンジニア — **主要ユーザー（MVP確定）**

| 項目 | 内容 |
| --- | --- |
| 状況 | Next.js + PostgreSQL(Supabase) + Vercel のような構成で、1〜5人規模でプロダクトを作っている |
| スキル | コードは書ける。インフラ・ネットワークは「動いているが完全には理解していない」領域がある |
| 痛み | 不具合の切り分けに、エディタ・ターミナル・ブラウザDevTools・DBクライアント・各クラウドのコンソールを往復する時間が長い |
| 本プロダクトへの期待 | 1画面で追える。環境の状態が一望できる |
| 成功条件 | 既存プロジェクトをそのまま開ける。IDE独自の作法を強要されない |

#### P2. フロントエンド中心のエンジニア

| 項目 | 内容 |
| --- | --- |
| 状況 | React/UIは得意。API・SQL・Docker・デプロイは他人任せか、見よう見まね |
| 痛み | 「データが出ない」ときに、自分の責任範囲かどうかの判断がつかない。バックエンド担当への質問の仕方が分からない |
| 期待 | 画面要素から裏側を辿れること。SQLや通信が読めなくても図で意味が分かること |
| 成功条件 | 専門用語に説明が添えられている。段階的に詳細を開ける |

#### P3. 非エンジニアのプロダクトオーナー / ディレクター — **差別化の鍵**

| 項目 | 内容 |
| --- | --- |
| 状況 | 仕様を決め、優先順位を付け、進捗を確認する。コードは読まない |
| 痛み | 「なぜこれは簡単で、あれは大変なのか」が分からない。見積もりの妥当性を判断できない。障害時に状況を把握できない |
| 期待 | アプリの構造を図で理解する。文言の修正程度は自分で行う |
| 成功条件 | 読み取り専用で安全に閲覧できる。壊す心配がない。日本語で説明される |
| 注意 | このペルソナが「編集できてしまう」ことはリスクでもある。権限設計が必要 (FR-62) |

#### P4. 学習者 / 新人エンジニア

| 項目 | 内容 |
| --- | --- |
| 状況 | Webアプリの全体像を学んでいる。断片的な知識はあるが繋がっていない |
| 痛み | 教科書の図と実際のコードの対応が取れない |
| 期待 | 自分のアプリが教材になる。実際の値と構造を見ながら学べる |
| 成功条件 | 用語解説と「いま何が起きたか」の自然言語説明 |

### 2.2 非対象ユーザー（現時点）

明示的にスコープ外とする。将来の検討対象ではあるが、要件を歪めないため今は外す。

- **大規模エンタープライズの運用チーム** — 既存APMの代替は目指さない。SLO管理、アラート運用、オンコールは対象外。
- **モバイルネイティブアプリ開発者** — Web（SSR/CSR）を前提とする。
- **データエンジニア / 分析者** — ETLパイプラインやDWHの可視化は対象外。
- **コードを一切持たないユーザー** — ゼロからのアプリ生成は本プロダクトの目的ではない。

### 2.3 想定プロジェクト（MVPの前提）

MVPが対象とする技術構成。これは **プロダクトの技術選定ではなく、解析対象の前提**である。

| レイヤー | MVP対象 | 後続で拡張 |
| --- | --- | --- |
| フロントエンド | React (Next.js App Router / Pages Router) | Vue, Svelte, Remix, Astro |
| サーバー | Next.js API Routes / Route Handlers, Node.js | Hono, Express, Fastify, Edge Runtime, Python/Go |
| DB | PostgreSQL (Supabase含む) | MySQL, SQLite, MongoDB |
| DBアクセス | Prisma, Drizzle, Supabase Client, 素のpg | TypeORM, Sequelize, Kysely |
| スタイル | Tailwind CSS | CSS Modules, styled-components, vanilla-extract |
| ローカル実行 | npm/pnpm/yarn スクリプト, Docker Compose | Kubernetes, devcontainer |
| クラウド | （MVP外） | Vercel, Supabase, GitHub, Resend, Cloudflare |

## 3. 解決する課題

### 3.1 課題の構造

本プロダクトが狙う根本課題は **「実行時の事実」と「ソースコードの記述」と「頭の中のモデル」の3つが一致しないこと** である。この不一致から、以下の具体的な課題が派生する。

### 3.2 個別の課題

#### C-01. コンテキストスイッチ税 — **最大の課題**

1つの疑問（「この値はどこから来た？」）を解くために、平均5〜7個のツールを往復する。

```
エディタ → コンポーネントを探す
  → DevTools Network → APIレスポンスを見る
    → エディタ → APIルートを探す
      → ターミナル → サーバーログを見る
        → DBクライアント → テーブルを見る
          → クラウドコンソール → 環境変数を確認
```

各ツールは単体では優秀だが、**それらの間の「対応関係」を保持しているのは人間の短期記憶だけ** である。この翻訳作業が認知負荷と時間の大半を占める。

- **影響**: 熟練者でも数分〜数十分。非熟練者は辿り着けない。
- **本プロダクトの解**: 対応関係そのものをデータとして保持し、図として表示する (FR-20〜FR-29)。

#### C-02. 障害の切り分けができない

「データが表示されない」の原因候補は、画面のレンダリング条件、APIの呼び出し失敗、認証、SQLのWHERE句、DBのデータ不在、環境変数、CORS、ポート競合、Dockerコンテナ停止など十数通りある。層をまたぐ切り分けには各層の観測手段を知っている必要がある。

- **本プロダクトの解**: 各層の状態を同時に1画面に並べ、フロー上のどこで止まったかを示す (FR-40〜FR-45)。

#### C-03. 非エンジニアが構造を理解できない

結果として、見積もりの妥当性判断ができず、仕様変更の影響範囲が分からず、障害時に「いつ直るのか」しか聞けない。エンジニア側も説明コストを払い続ける。

- **本プロダクトの解**: アイコンと線による表現、専門用語への説明の付与、読み取り専用モード (FR-60〜FR-64)。

#### C-04. ローカル環境の状態が不透明

「ポートが使われている」「コンテナが落ちている」「ビルドキャッシュが壊れている」「別のNode.jsバージョンが使われている」といった、アプリケーションコードの外側の問題。ターミナルの履歴を遡らないと分からない。

- **本プロダクトの解**: ローカル環境の状態を常時表示する (FR-30〜FR-37)。

#### C-05. ノーコードツールは理解を与えない

ブラックボックスを増やし、限界に達したときに脱出できない。学習にもならない。

- **本プロダクトの解**: 生成物を通常のコードに保ち、変更が「コードのどこに反映されたか」を常に示す (FR-13)。

#### C-06. 既存の可観測性ツールは開発中の理解に向かない

APMは本番運用の事後分析用で、セットアップが重く、表示が運用者向けであり、ローカル開発では使われない。

- **本プロダクトの解**: ローカル優先、ゼロ設定に近い導入、非専門家向けの表示 (NFR-11)。

#### C-07. DBから画面への逆引きができない

「このカラムの型を変えたら、どの画面が壊れるか」「このテーブルはまだ使われているか」は、現状は全文検索と勘に頼る。

- **本プロダクトの解**: 逆方向トレース (FR-26)。ただし精度に本質的な限界がある（第5章 / R-01）。

### 3.3 課題と機能の対応（概観）

| 課題 | 主担当機能群 | MVP |
| --- | --- | --- |
| C-01 コンテキストスイッチ | データフロー可視化 (FR-20〜29) | ◎ |
| C-02 切り分け不能 | 実行トレース・エラー解析 (FR-40〜45) | ○ |
| C-03 非エンジニア | 表示設計・読み取り専用 (FR-60〜64) | △（表示設計のみ） |
| C-04 ローカル不透明 | ローカル環境可視化 (FR-30〜37) | ○ |
| C-05 ブラックボックス | ビジュアル編集のコード反映 (FR-10〜16) | ◎ |
| C-06 APMが重い | 非機能要件 (NFR-11) | ◎ |
| C-07 逆引き | 逆方向トレース (FR-26) | △（限定版） |

### 4.2 主要ユースケース詳細

#### UC-01. 画面要素からデータの出所を辿る（順方向トレース）— **中核UC**

> 参考画像: `03-element-data-tracing.png`, `08-simplified-flow-layout.png`, `09-user-journey-overview.png` (手順3)

| 項目 | 内容 |
| --- | --- |
| アクター | フルスタックエンジニア / フロントエンドエンジニア / 非エンジニア |
| 事前条件 | プロジェクトが解析済み。開発サーバーが起動し、対象ページが表示されている |
| トリガー | ユーザーがプレビュー上の要素（例: カード内の「千葉県」というテキスト）をクリックする |

**基本フロー**

1. ユーザーがプレビュー内の要素をクリックする。
2. システムが、その要素に対応するDOMノード → Reactコンポーネント → ソースコード上の位置 を特定する。
3. システムが、その要素に表示されている値の供給経路を次の粒度で提示する。
   1. フロントエンド: どのコンポーネントの、どのpropsまたはstateか (`PropertyCard / props.area`)
   2. APIリクエスト: どのエンドポイントの、レスポンスのどのパスか (`GET /api/properties` → `properties[0].area`)
   3. サーバー処理: どのハンドラ・どのクエリビルダ呼び出しか
   4. データベース: どのテーブルの、どのカラムか (`public.properties.area (text)`)
   5. 実際の値: 取得された生の値
4. 中央キャンバスに、1〜5をノードと線で結んだ経路を描画する。
5. 右パネルに、各ステップの詳細を番号付きの縦リストで表示する。
6. 各ステップについて、**その情報が実測によるものか推測によるものかを明示する**（第5章）。

**代替フロー**

- A1: 値が静的なリテラル（コードに直書き）の場合 → 「このテキストはコードに直接書かれています」と表示し、該当行を示す。
- A2: 値が複数の経路から来る可能性がある場合（条件分岐・複数のデータソース）→ 候補を複数提示し、実行トレースがあれば実際に通った経路を強調する。
- A3: 開発サーバーが起動していない場合 → 静的解析のみに基づく経路を、推測である旨を明示して表示する（実際の値は表示しない）。
- A4: 経路の特定に失敗した場合 → **推測で埋めない**。「ここから先は追跡できませんでした」と、その理由（動的なクエリ生成、未サポートのORM、等）を表示する。

**事後条件**: ユーザーが値の出所を特定でき、該当するコード位置・SQL・テーブルへ1クリックで遷移できる。

#### UC-02. DBカラムから表示箇所を探す（逆方向トレース）

> 参考画像: `09-user-journey-overview.png` (手順4,5)

| 項目 | 内容 |
| --- | --- |
| アクター | フルスタックエンジニア |
| トリガー | スキーマビューでテーブルのカラムを選択し、「利用箇所を表示」を実行 |

**基本フロー**

1. ユーザーが `public.properties.area` を選択する。
2. システムが、そのカラムを参照する可能性のあるコード位置を列挙する（SQL文字列、ORMのselect句、型定義経由の参照）。

**重要な制約**: 逆方向トレースは静的解析に依存するため、**網羅性を保証できない**。`SELECT *`、動的なカラム名、ビュー経由のアクセス、生SQL文字列の組み立てでは検出漏れが起きる。UIは「検出できた N 件」であり「全 N 件」ではないことを明示しなければならない (FR-26, R-01)。

## 5. 観測性モデル：実測できる情報と推測する情報

> **本章は本プロダクトの最重要の設計制約である。**
> 参考画像は概念イメージであり、描かれている全てのノードが実際に観測可能なわけではない。実装可能性と誠実さを担保するため、全ての表示情報を観測性レベルで分類し、UI上で区別することを要件とする。

### 5.1 観測性レベルの定義

| レベル | 名称 | 定義 | UI表現（規約） |
| --- | --- | --- | --- |
| **L0** | 実測 (Measured) | 実行時に直接取得した事実。ログ、プロトコルのレスポンス、プロセスの状態など、証跡が残るもの | 実線 / 通常の彩度 / 値をそのまま表示 |
| **L1** | 計装による実測 (Instrumented) | 本IDEがアプリに計装を注入することで取得できる事実。計装が有効な場合のみL0と同等 | 実線 / 計装アイコンを付与 |
| **L2** | 静的解析による推論 (Inferred) | コードの解析から導いた「そうである可能性が高い」関係。実行していない | **破線** / 確度ラベル付き / 「推定」バッジ |
| **L3** | 図式的表現 (Schematic) | 観測手段が存在せず、一般的な構成知識から描いている説明用の要素 | 破線 + 低彩度 / 「説明用」注記 / 詳細パネルで値を出さない |

> **UI規約**: 参考画像では既に実線と破線が使い分けられている（`02-full-request-flow.png` の Docker / Static Assets / External API への破線、`08` の Storage への破線）。この視覚言語を **観測性レベルの正式な符号化**として採用する。これにより追加のUI要素なしに誠実さを表現できる。

### 5.2 レイヤー別の観測性マトリクス

#### 5.2.1 フロントエンド / ブラウザ

| 対象 | レベル | 取得手段（概念） | 限界・注意 |
| --- | --- | --- | --- |
| DOMツリー、要素の位置・スタイル | L0 | ブラウザ自動化プロトコル | — |
| ネットワークリクエスト（URL, ヘッダ, ボディ, ステータス, 時間） | L0 | ブラウザのネットワーク計測 | HTTPSの中身は自ブラウザ内なので取得可。他プロセスの通信は不可 |
| コンソールログ、JSエラー、スタックトレース | L0 | — | — |
| 描画タイミング、再レンダリング回数 | L1 | Reactの開発用フック | 本番ビルドでは取得不可 |
| DOM要素 → Reactコンポーネント の対応 | L1 | React内部ツリーの参照 | 開発ビルド前提。本番ビルドでは成立しない |
| コンポーネント → ソースコード行 の対応 | L1〜L2 | ビルド時の位置情報注入 / ソースマップ | 注入可能ならL1、ソースマップ推定ならL2 |
| 要素に表示される値 → props/state の対応 | L2 | AST解析 + 実行時の値照合 | 計算式・条件分岐・配列mapでは特定が困難 |

#### 5.2.2 サーバー / Node.js

| 対象 | レベル | 取得手段（概念） | 限界・注意 |
| --- | --- | --- | --- |
| プロセスの起動・終了・終了コード | L0 | 自IDEが起動した子プロセスとして管理 | **IDEが起動していないプロセス**は、外部からの観測に限られる |
| 標準出力・標準エラー | L0 | — | IDEが起動していない場合は取得不可 |
| 待ち受けポートとPID | L0〜L2 | OSのソケット一覧 | 権限により他ユーザーのプロセスは不可。macOS/Windowsで挙動が異なる |
| CPU/メモリ使用量 | L0 | OSのプロセス情報 | — |
| 受信したHTTPリクエストの詳細 | L1 | HTTPサーバーへの計装注入 | 計装なしでは不可。ブラウザ側からの観測で代替可能だがサーバー内部の情報は得られない |
| 外部へのHTTPリクエスト（外部API呼び出し） | L1 | HTTPクライアントへの計装注入 | ライブラリごとに対応が必要 |
| 発行されたSQLと実行時間 | L1 | ORM/ドライバへの計装注入 | 対応ORMごとの実装が必要。未対応ORMではL2に落ちる |
| **サーバー処理内の内訳**（認証12ms / 検証8ms / 整形10ms 等） | **L1（要個別計装）** | 明示的な計測点の挿入 | **参考画像 `06-data-flow-tab.png` の「サーバー処理」内訳は、自動では取得できない。** 自動計装が届く境界（ミドルウェア、ハンドラ、DB呼び出し）のみが現実的。それ以外は表示しないか、粒度を落とす |
| 環境変数の値 | L0 | プロセス環境 | **秘密情報を含むため既定でマスク必須** (NFR-20) |

#### 5.2.3 データベース

| 対象 | レベル | 取得手段（概念） | 限界・注意 |
| --- | --- | --- | --- |
| スキーマ（テーブル、カラム、型、制約、索引） | L0 | DBへの直接接続（情報スキーマ照会） | 接続情報と権限が必要 |
| 実データのプレビュー | L0 | 直接照会 | **PIIを含みうる。既定でマスク/件数制限** (NFR-20) |
| 実行された実際のSQL | L1 | ORM計装 または DBのログ設定 | DBログの有効化は利用者の権限と設定に依存 |
| 実行計画 | L0 | `EXPLAIN` の明示実行 | 本番DBでの実行は負荷の懸念があり、既定で無効 |
| クエリの実行時間 | L1 | 計装 または DB統計 | 計装の方が正確（ネットワーク往復を含むか否かの定義が必要） |
| コード上のクエリ → 実テーブル の対応 | L2 | 静的解析 | 動的なテーブル名・生SQL連結では不能 |
| 画面要素 → カラム の対応 | L2 | 静的解析 + 実行時の値照合 | **`09-user-journey-overview.png` 手順5「このカラムの利用箇所 4件」は L2。網羅保証不可** |

#### 5.2.4 ローカルOS / ネットワーク — **誤解が生じやすい領域**

| 対象 | レベル | 現実的に取得できること | **取得できないこと** |
| --- | --- | --- | --- |
| Dockerコンテナ | L0 | 一覧、状態、イメージ、ポートマッピング、ログ、リソース統計（Docker Engine API） | Docker未起動時は何も取得できない。「停止中」と「未接続」は区別して表示すること |
| プロセスとポート | L0〜L2 | 自身が起動したプロセスは完全に把握。他プロセスはOSのソケット一覧の範囲 | 権限外のプロセス詳細。OS間差異あり |
| HTTP通信 | L0/L1 | ブラウザ側とサーバー計装側の両端で取得 | **両端に計装がない通信は見えない**。パケットキャプチャは行わない（権限・プライバシー・実装コストの観点で非採用） |
| **ファイアウォール** | **L2/L3** | 設定の読み取り（OSの設定照会）。接続の成否という**結果** | **「このリクエストがファイアウォールを通過した/ブロックされた」という個別イベントは取得できない。** 参考画像 `03` `04` の「ファイアウォール → 許可」バッジは、実際には「接続が成功した＝経路上で遮断されなかった」という**推論**である。この表現を採用する場合、L2として破線・推定表示にするか、ノード自体を「ネットワーク到達性」に改める必要がある |
| **プロキシ** | **L2/L3** | 環境変数（HTTP_PROXY等）やシステム設定の読み取り | 経由の事実。レスポンスヘッダからの間接的な推定に留まる |
| **ロードバランサ** | **L3** | — | **ローカル環境には通常存在しない。** 参考画像 `02-full-request-flow.png` のロードバランサノードは、ローカル構成では描くべきではない。構成に実在する場合のみ表示する |
| DNS解決 | L0 | 名前解決の結果（明示的に実行した場合） | 自動的な解決履歴は取得困難 |

#### 5.2.5 クラウド

| 対象 | レベル | 取得できること | 取得できないこと |
| --- | --- | --- | --- |
| Vercel | L0 | デプロイ一覧・状態・ログ・プロジェクト設定・ドメイン（公式API） | 内部のルーティング詳細、エッジノードの選択理由。ランタイムログは保持期間・プラン依存 |
| GitHub | L0 | リポジトリ、ブランチ、コミット、PR、Actions実行結果 | — |
| Supabase | L0 | プロジェクト設定、DB接続、Storage使用量、Authユーザー数（Management API + 直接接続） | 内部インフラ構成。APIのレート制限あり |
| 外部API（地図、決済等） | L1 | **自アプリから呼び出した事実**（計装による） | 相手側の内部。呼び出し以外の経路 |
| **メール送信** | **L0〜L2** | 送信APIの呼び出しと応答（例: 202 Accepted）。Webhookを設定すれば配信/バウンス/開封イベント | **「ユーザーのメールボックスに届いた」ことは観測できない。** 参考画像 `12-cloud-email-flow.png` の「⑥メール受信（ユーザー）」ノードは L3（図式的表現）。送信成功を受信成功と誤認させない表示が必須 |
| CDN | L0〜L2 | レスポンスヘッダからのキャッシュ状態の推定（`x-vercel-cache` 等） | 内部のキャッシュ戦略、オリジンへのフェッチ |
| コスト・使用量 | L0 | 各サービスのAPIが返す範囲 | リアルタイム性はサービス依存（集計遅延あり） |

### 5.3 表示規約（要件）

この分類を踏まえ、以下をUIの必須要件とする。

| ID | 要件 |
| --- | --- |
| **OBS-01** | 全てのノード・エッジ・詳細項目は、内部的に観測性レベル (L0/L1/L2/L3) を保持する |
| **OBS-02** | L2/L3 の要素は、視覚的に L0/L1 と区別される（破線・低彩度・推定バッジ） |
| **OBS-03** | L2 の推論には確度（高/中/低）とその根拠（どの解析によるか）を詳細パネルで示す |
| **OBS-04** | L3 の要素には実測値を表示しない。「説明用の図示であり、実際の計測ではない」旨を明示する |
| **OBS-05** | 情報が取得できなかった場合、推測で補完せず「取得できませんでした」と理由を表示する |
| **OBS-06** | 「データなし」「未接続」「権限不足」「サービス停止」を明確に区別して表示する |
| **OBS-07** | 逆方向トレースなど網羅性を保証できない機能は、「検出できた件数」であることを明示し、「全件」と表現しない |
| **OBS-08** | ユーザーが任意のノードについて「この情報はどうやって取得されたか」を確認できる（情報源の開示） |

#### 5.3.1 観測性レベルの粒度規約 (Phase 1.5 で追加)

> Phase 1 の OBS-01〜08 は、**レベルをどの単位で判定するか**を定めていなかった。その結果、「実測されたAPI通信」と「静的解析で推測したDBカラムの関係」を、同じ1本のトレースに属するという理由でまとめて「実測」と扱ってしまう余地が残っていた。以下はその穴を塞ぐ規約である。

| ID | 要件 | 優先度 |
| --- | --- | --- |
| **OBS-09** | 観測性レベルは、**トレースや経路の単位ではなく、ノード・エッジ・属性の個別の単位で判定・保持する**。1本の経路の中でレベルが変化することを前提とする | A |
| **OBS-10** | **最弱環の原則**: 経路全体としての主張の確度は、その経路を構成する要素のうち最も低いレベルに等しい。5つのホップが L0/L1 でも、1つが L2 なら経路の主張は L2 である | A |
| **OBS-11** | 経路を表示する際、**その経路で最も確度が低い箇所を名指しで提示する**（例:「この経路で最も確度が低いのは、props とAPIレスポンスの対応付けです」） | A |
| **OBS-12** | 1本の接続線の中でも、**区間ごとに線種（実線/破線）を切り替える**。経路全体を単一の線種で描かない | B |
| **OBS-13** | L2 の確度算出において、**何が根拠として一致したか**（実SQLの構文解析 / ORMスキーマのマッピング / 構造の照合 / 値の一致 など）を開示する | B |

#### 5.3.2 禁止事項

| 禁止 | 理由 |
| --- | --- |
| 経路全体に単一の観測性ラベルを付けること | OBS-09 違反。確度の高い区間が低い区間を覆い隠す |
| 値が一致したことをもって対応付けを「実測」と表示すること | **値の一致は必要条件であって十分条件ではない**。同じ値が複数カラムに存在しうる |
| 「実行されたSQL」（L1）と「そのSQLと画面要素の対応付け」（L2）を同じ確度で表示すること | ユーザー指示による明示的な禁止事項 |
| 確度ラベルを、実際の正解率と較正せずに表示すること | NFR-17 違反。確度表示が信用できなければ観測性モデル全体が無意味になる |

### 5.4 正準トレースの観測性分解 (Phase 1.5 で追加)

OBS-09/OBS-10 を具体化するため、中核機能 (FR-22) の正準的な経路を分解して示す。**Phase 2 のIA設計は、この表を表現できる視覚言語を設計しなければならない。**

題材: 「PropertyCard に表示されている『千葉県』は、`properties` テーブルの `area` カラムから来ている」という主張。

| # | 対象 | 種別 | レベル | 根拠 | 弱点 |
| --- | --- | --- | --- | --- | --- |
| 1 | DOM要素とそのテキスト `"千葉県"` | ノード | **L0** | DOMの直接読み取り | — |
| 1→2 | DOM要素 → ソース位置識別子 → JSX位置 | エッジ | **L1** | ビルド時の識別子注入 | 注入対象がユーザーのソースに限定される |
| 2 | コンポーネント `PropertyCard` とソース位置 | ノード | **L1** | 同上 | 開発ビルド限定 |
| 2→3 | `props.area` → レスポンスJSONの `properties[0].area` | エッジ | **L2** | 静的解析 + 値照合 | **値の一致は必要条件に過ぎない。加工・条件分岐で破綻** |
| 3 | HTTPリクエスト（URL・ヘッダ・ステータス・時間） | ノード | **L0** | ブラウザ側の計測 | — |
| 3→4 | ブラウザのリクエスト ↔ サーバーの受信 | エッジ | **L1** | トレースコンテキストの伝播 | 失敗時は L2（時間窓推定）に降格 |
| 4 | サーバーハンドラの実行（開始・終了・時間） | ノード | **L1** | 自動計装 | 計装が前提 |
| 4→5 | ハンドラ → 発行SQL | エッジ | **L1** | 同一トレース内の親子関係 | 計装方式により L2 に降格しうる |
| 5 | 実行されたSQL文・実行時間・取得件数 | ノード | **L1** | ORM計装 | 計装が前提 |
| 5→6 | SQL → テーブル `properties` | エッジ | **L1相当** | **実測されたSQL文の決定的な構文解析** | 動的に組まれたSQLでも実測文なら解析可能 |
| 6 | テーブル定義（カラム・型・制約） | ノード | **L0** | DBへの直接照会 | — |
| 5→7 | SQL → カラム `area` | エッジ | **L1相当 または L2** | SELECT句に列挙されていれば L1相当。**`SELECT *` なら L2** | クエリの書き方に依存 |
| 7 | カラム `area`（型・制約） | ノード | **L1相当** | テーブル定義の照会 + 実測SQLの解析 | `SELECT *` の場合はノード自体が L2 |
| 7→3 | カラム `area` → レスポンスJSONのキー `area` | エッジ | **L2** | ORMのマッピング推定 | **ORMの内部変換は観測の外。別名・加工があると不能** |
| **経路** | **主張全体「この表示は `properties.area` 由来」** | **経路** | **L2** | **最弱環 = #2→3 と #7→3** | — |

> **この表が示す最重要の事実**: 14の構成要素（ノード7 + エッジ7）のうち **12 が L0/L1/L1相当（実測）であっても、2つの「値の結びつき」(#2→3 と #7→3) が L2 であるため、経路全体の主張は L2 である。**
> **件数は導出値である。** 経路の構成が変われば件数も変わる。本表の 14 / 12 / 2 は、この正準トレースに限った値であり、固定値として実装に埋め込んではならない (OBS-10)。
> 本プロダクトの中核機能は、**構造的に推論であり、実測ではない**。これは欠陥ではなく、正しく表示すべき事実である。「ほぼ実測だから実測扱いでよい」という妥協は、OBS-10 により禁止される。

| ID | 要件 | 優先度 |
| --- | --- | --- |
| INS-01 | 計装は **ユーザーが書いたアプリケーションコードを変更せずに** 実現されること（**Phase 1.5 で定義を修正**。詳細は下記） | P0 |
| INS-02 | 計装は開発環境でのみ既定で有効。本番環境への適用は明示的なオプトインを要する | P0 |

| INS-04 | 計装によるアプリケーションの性能劣化が開発体験を損なわない範囲であること（目標: 起動時間増 +20%以内、リクエスト遅延 +10ms以内） | P0 |

| **INS-08** | **(新規)** 計装は、**IDEがアプリケーションプロセスを起動した場合にのみ適用される**。既に外部で起動済みのプロセスには適用できないことを、UI上で明示すること | P0 |

#### 5.5.1 INS-01 の定義修正について (Phase 1.5)

技術レビュー (`01b` Q-01.0) により、「ソースコードを変更せずに」には区別すべき2つの意味があることが判明した。

| 解釈 | 内容 | 扱い |
| --- | --- | --- |
| **(a) 非改変** | ユーザーが書いた既存のアプリケーションコードを一切変更しない | **必須要件とする** |
| **(b) 非追加** | プロジェクトディレクトリに一切ファイルを追加しない | **望ましいが必須ではない**（成立しない可能性が高いため） |

**(b) を満たせない場合に IDE が追加できるファイルの条件**（全てを満たすこと）:

1. 一時的であること（IDE終了時に除去できる）
2. ユーザーに可視であること（何が追加されたか一覧できる — INS-07）
3. バージョン管理の対象外にできること（`.gitignore` への登録を提案する）
4. ユーザーのアプリケーションロジックを含まないこと（計装の初期化のみ）
5. IDEをアンインストールしてもプロジェクトが動作すること（NFR-53）

### 6.3 情報階層と3ビュー同期モデル — **最重要の構造的発見**

参考画像の全てで、同じ構造が繰り返されている。

```
┌──────────────────────────────────────────────────────────┐
│ L1: グローバルバー                                        │
│    プロジェクト / 環境(Local·Staging·Production) /        │
│    実行コマンド / 共有・デプロイ                          │
├──────────────────────────────────────────────────────────┤
│ L2: モードタブ                                            │
│    Visual · Code · Database · API · Infra · Deploy · Logs │
├────────┬────────────────────────────────┬────────────────┤
│ L3左   │ L3中央: キャンバス（最大面積）  │ L3右           │
│ 構造   │  プレビュー ｜ フロー図         │ 選択中の詳細   │
│ ナビ   │                                 │                │
├────────┴────────────────────────────────┴────────────────┤
│ L4: ドロワー                                              │
│    Timeline · Logs · Network · Database · Docker · Build  │
└──────────────────────────────────────────────────────────┘
```

この構造の核心は、**連番バッジ（①②③…）が3つのビューを横断する共通IDとして機能している** 点にある。

| ビュー | 役割 | 表示する情報 |
| --- | --- | --- |
| 中央フロー図 | **空間**（どこを通ったか） | ノード、接続、番号バッジ、最小限のラベル |
| 下部タイムライン | **時間**（いつ、どれだけかかったか） | 同じ番号、所要時間、並行関係 |
| 右詳細パネル | **内容**（何が送られ、返ったか） | 同じ番号、ヘッダ、SQL、JSON、値 |

3ビューは同じ事象を異なる軸で切り出しており、**情報の重複ではなく射影** である。これが UI-07（重複表示の禁止）を満たしながら高い情報量を扱える仕組みである。

| ID | 要件 |
| --- | --- |
| **UI-10** | フロー上の各ステップには一貫した連番IDを振り、フロー図・タイムライン・詳細パネルで同一の番号・同一の色を使用する |
| **UI-11** | いずれかのビューで項目を選択すると、他の2ビューが同期してハイライトする |
| **UI-12** | 中央キャンバスの「プレビュー」と「フロー図」の分割比率は可変とし、片方を最大化できる |
| **UI-13** | 右詳細パネルは選択がないとき格納され、キャンバスを広げる |
| **UI-14** | 下部ドロワーは折りたたみ可能で、既定は折りたたみ |
| **UI-15** | ノード上には種別アイコンと短いラベルのみを置く。属性値はホバー/選択時に詳細パネルへ出す |

| 段階 | 操作 | 表示 |

| ID | 要件 |
| --- | --- |
| **UI-20** | 段階0で表示する情報は、ノード種別アイコン・名称・状態（正常/警告/エラー/不明）に限る |

## 9. MVPの対象範囲

### 9.1 MVPの定義

> **MVPが証明すべき仮説**
> 「画面上の値をクリックすると、そのデータがDBのどのカラムから来たかまでを一本の図で辿れる」という体験が、開発者の問題解決を実際に速くするか。

この1点に集中する。他の機能は、この体験を成立させるために必要な最小限に絞る。

> **Phase 1.5 での更新**: MVP要件の詳細な優先順位（A / B / C 分類、実装順序、M2 の達成条件）は **`docs/01c-mvp-priorities.md` に委譲した。** 本章は前提条件とマイルストーンのみを示す。
>
> 最大の変更点は、**ビジュアル編集 (FR-13〜FR-16) を「中核価値の実証に必要なもの」から外した**こと。方針「可視化が中核、編集は副次」(1.4節) に従い、B群（実証後に着手）へ移した。これにより仮説検証までに必要な要件が約4割減っている。

## 11. 技術的リスク

> 影響度 × 発生確度 で評価。**高**リスクは Phase 2 以前に技術検証（PoC）すべきもの。

### R-01. データリネージの静的解析精度 — **影響: 高 / 確度: 高**

**内容**: コードからデータの流れを追う解析は、本質的に不完全である。

- `SELECT *` ではカラム単位の特定ができない
- 動的に組み立てられるSQL・テーブル名・カラム名は追跡不能
- ORMの多様性（Prisma / Drizzle / Supabase Client / 素のドライバ）ごとに解析実装が必要
- ビュー、ストアドプロシージャ、トリガー経由のアクセスは見えない
- 配列の `map` 内、条件分岐、スプレッド構文、高階コンポーネントで値の対応が曖昧になる
- TypeScriptの型情報があっても、実行時の値の経路とは一致しない

**影響**: 中核機能 (FR-22, FR-26) の品質が直接左右される。

**緩和策**:
- 静的解析に加え、**実行時トレース（L1）と突き合わせる**ことで確度を上げる。静的のみに依存しない
- 確度を明示する (OBS-03)。曖昧な場合は候補を複数提示する
- 追跡不能な箇所は「ここで追跡が途切れた」と理由付きで表示する (OBS-05)
- MVPは1つのORMに絞り、精度を優先する

### R-02. ランタイム計装の侵襲性と信頼性 — **影響: 高 / 確度: 高**

**内容**: サーバー側の情報（発行SQL、受信リクエスト）を取るには、ユーザーのアプリに計装を入れる必要がある。

- ユーザーのコードを書き換えずに計装する手段が、フレームワーク・ランタイムによって異なる
- バンドラ（Turbopack/webpack）やサーバーコンポーネントの実行形態により、計装が届かない領域がある
- Edge Runtime、Serverless環境では、従来のNode.js計装が機能しない
- 計装がアプリを壊す（起動失敗、挙動変化）リスクがある
- フレームワークのバージョンアップで計装が壊れる（継続的な保守コスト）

**緩和策**:
- INS-03（計装なしでも成立する設計）を厳守し、計装を「あれば精度が上がるもの」と位置づける
- 標準的な可観測性規格との互換を保ち、独自実装への依存を減らす (INS-06)
- 計装の有効/無効をユーザーが切り替えられる
- **Phase 2 以前に、対象フレームワークでの計装可否を PoC で確認すること (Q-02)**

### R-03. DOM要素 → ソースコード位置のマッピング — **影響: 高 / 確度: 中**

**内容**: ビジュアル編集と要素選択の前提となる、画面上の要素とコードの対応付け。

- ビルド時に位置情報を注入する方式はビルド設定への介入が必要
- サーバーコンポーネント、ストリーミングSSR、ポータル、Suspense境界で対応が崩れる
- UIライブラリ（shadcn/ui 等）を経由すると、ユーザーのコードではなくライブラリ内部を指してしまう
- 本番ビルドでは成立しない（開発ビルド限定の機能になる）

**緩和策**: 複数の手がかり（ビルド時注入 / React内部ツリー / ソースマップ / DOM構造の照合）を組み合わせ、確度を持って提示する。特定できない場合は編集を無効化する。

### R-04. ビジュアル編集のコード往復 — **影響: 高 / 確度: 高**

**内容**: 画面での編集をコードに戻す処理は、既知の難所である。

- Tailwindのクラス文字列の編集（任意値、条件付きクラス、`clsx`/`cva` の合成）
- CSS-in-JS、CSS Modules など複数のスタイル手段の混在
- 整形（Prettier設定）の尊重と、意図しない差分の抑制
- 同じコンポーネントが複数箇所で使われている場合、1箇所の見た目の編集が全箇所に波及する（**ユーザーの意図との乖離**）
- propsで渡されたスタイルの編集先が、コンポーネント定義か呼び出し元か判断できない
- 外部エディタでの同時編集との競合

**緩和策**:
- 編集前に「この変更が影響する箇所」を提示する
- 編集可能・不可能を明確に区別し、不可能な場合は理由を示す (FR-12)
- 変更差分を常に提示し、取り消せるようにする (FR-16)
- MVPはTailwind単一構成に絞る

### R-05. 観測不能な領域の誠実な表現 — **影響: 高 / 確度: 高** — **固有リスク**

**内容**: 第5章で整理した通り、参考画像には実際には観測できない要素が含まれている（ファイアウォールの通過判定、ロードバランサ、メールの受信）。これを「それらしく」描くと、**ユーザーが誤った確信を持つ**。本プロダクトの価値（正しい理解）を根本から毀損する。

**具体例**:
- 「ファイアウォール：許可」と表示されたが、実際には単に接続が成功しただけで、ファイアウォールは観測していない → ユーザーがファイアウォールの設定を誤って判断する
- 「メール送信 → メール受信」と表示されたが、実際は送信APIが受理しただけ → ユーザーが「届いている」と誤認し、実際の配信失敗を見逃す

**緩和策**: OBS-01〜08 を必須要件として強制する。デザインレビューで「この表示の観測性レベルは何か」を必ず問う。レベル不明の表示は実装しない。

### R-06. キャンバスの性能と情報過多 — **影響: 中 / 確度: 中**

**内容**: 実プロジェクトでは、ページ1枚でも数十〜数百のリクエストとノードが生じうる。参考画像のような美しく疎なグラフにはならない。

**緩和策**: 自動集約、フォーカスモード (UI-33)、スコープ切替 (UI-34)、ズームレベルに応じた詳細度変更 (UI-32)。**実プロジェクトでの見え方を早期に確認する (Q-10)**。

### R-07. クラウドAPIの制約 — **影響: 中 / 確度: 中**

**内容**: 各クラウドサービスのAPIには、レート制限、プラン依存の機能差、ログの保持期間、権限スコープの制約がある。認証方式も個別（OAuth / PAT / Service Role Key）。トークン管理はセキュリティリスクでもある。

**緩和策**: MVPから除外済み。Phase B で各サービスの制約を個別調査する (Q-13)。

### R-08. 実データとPIIの取り扱い — **影響: 高 / 確度: 中**

**内容**: 「実際の値を表示する」ことが価値である一方、個人情報・機密情報が画面に出る。スクリーンショット、画面共有、録画、AIへの送信を通じて漏洩しうる。顧客のDBに接続する受託開発では、契約・法令上の問題にもなる。

**緩和策**: NFR-20, NFR-25, NFR-26。PII候補の推定とマスクを既定にする。ただし **完全な検出は保証できない**ことを明示し、ユーザー側の責任範囲を示す。

### R-09. フレームワーク・エコシステムの多様性 — **影響: 中 / 確度: 高**

**内容**: Next.jsだけでも App Router / Pages Router / Turbopack / webpack / サーバーコンポーネント / Edge Runtime と組み合わせが多い。ORMも複数。対応拡大のコストが線形以上に増える。フレームワークのバージョンアップへの追随も継続コストになる。

**緩和策**: NFR-40（アダプタ分離）。MVPは単一構成に絞り、対応状況を明示する (FR-07)。

### R-10. AIによる操作実行の安全性 — **影響: 高 / 確度: 中**

**内容**: AIがプロセス起動、コード変更、SQL実行、デプロイを行える場合、誤操作・意図しない破壊が起きうる。自然言語の曖昧さが危険な操作に繋がる可能性がある。

**緩和策**: NFR-23, FR-74。危険操作の分類を先に定義し、AIの権限を構造的に制限する。MVPでは操作実行を含めない。

### R-11. 「IDE」としての完全性の期待 — **影響: 中 / 確度: 中**

**内容**: 「IDE」を名乗ると、コード編集・補完・デバッグ・Git操作など、既存IDEと同等の機能が期待される。これを満たすのは非現実的であり、中核価値の開発を圧迫する。

**緩和策**: プロダクトの位置づけを「既存エディタの置き換え」ではなく「理解のための環境」として明確に伝える。既存エディタとの共存 (NFR-52) を前提とする。**名称と訴求の決定が必要 (Q-16)**。

### R-12. 配布形態と権限 — **影響: 中 / 確度: 中**

**内容**: ローカルのプロセス・ポート・Docker・ファイルシステムにアクセスするため、ブラウザ内で完結しない。デスクトップアプリ、ローカルサーバー+ブラウザ、エディタ拡張のいずれかになるが、それぞれ配布・権限・更新の制約が異なる。macOSの署名・公証、各OSのセキュリティ機構への対応も必要。

**緩和策**: Phase 3（技術選定）で判断する。**現段階では確定しない**（本要件定義の制約）。

### 12.4 明示的な仮説（検証されていない前提）

本要件定義は以下を仮定している。**いずれも未検証であり、覆る可能性がある。**

| ID | 仮説 | 覆った場合の影響 |
| --- | --- | --- |
| H-01 | 開発者は「値の出所を辿る」ことに十分な時間を費やしており、短縮に価値を感じる | プロダクトの前提が崩れる。課題の再定義が必要 |
| H-02 | 非エンジニアは、図で示されればアプリの内部構造を理解できる | P3ペルソナ向け機能の価値が失われる。P1特化へ転換 |
| H-03 | 静的解析と実行時トレースの組み合わせで、実用的な精度のリネージが作れる | 中核機能が成立しない。手動のアノテーションを併用する設計へ |
| H-04 | ユーザーは自分のプロジェクトに計装が注入されることを許容する | L1情報が取れない。L0+L2のみで成立する設計へ |
| H-05 | 1つのスタック（Next.js + PostgreSQL）に絞っても、十分な対象ユーザーがいる | 対応拡大を前倒しする必要がある |
| H-06 | 可視化の価値は、エラー発生時だけでなく日常的な開発でも発揮される | 利用頻度が低く、ツールとして定着しない。エラー対応特化へ |
| ~~H-07~~ | ~~ビジュアル編集と可視化は、同一プロダクトに同居させる価値がある~~ → **【Phase 1.5 で決定】同一プロダクトに配置するが、独立したモードとして設計する**（1.4節） | — |

> **H-07 の決着 (Phase 1.5)**: ビジュアル編集（作る）と可視化（理解する）は、ユーザーの目的も使用タイミングも異なる。この差異を認めた上で、**同一プロダクト内の独立したモードとして配置する**ことを決定した（1.4節）。混在させないことで、それぞれの画面構成を目的に最適化できる。
>
> なお、H-01 / H-03 / H-04 は依然として未検証である。特に **H-03（実用的な精度のリネージが作れる）は、技術レビュー (`01b` Q-04) により「原理的に推論にしかならない」ことが構造的に判明した。** 仮説の内容を「完全な精度」から「**誤答率を基準内に抑えた上で、確度を較正して提示できる**」へ修正して検証すべきである。

**Phase 1 の確定事項（継続）**

1. プロダクトの目的は **「理解を与えること」** であり、自動化・コード生成ではない。
2. **観測性レベル (L0〜L3) のモデルを採用**し、全ての表示情報を分類する。推測を実測として見せない。
3. 中核機能は **順方向トレース（画面要素 → DBカラム）** であり、MVPはこの1点の検証に集中する。

5. ローカルファーストであり、クラウド接続を必須としない。
6. MVPの対象スタックは Next.js + PostgreSQL + Tailwind の単一構成とする。
7. 情報設計は **3ビュー同期モデル**（フロー図=空間 / タイムライン=時間 / 詳細パネル=内容）を採用する。
8. 秘密情報・PIIの自動マスクは必須要件であり、オプションではない。
9. MVPに含まれない機能は **削除ではなく後続フェーズへの配置** である。

### A.4 参考画像から抽出した最も重要な設計示唆

1. **連番バッジによる3ビュー同期**（A.2 の `08` が最も明快）— 情報を重複させずに多面的に見せる構造。本プロダクトの情報設計の核。
2. **実線と破線の使い分け** — 既に視覚言語として存在している。これを観測性レベルの正式な符号化に昇格させることで、追加のUI負荷なく誠実さを表現できる。
3. **吹き出しによる値の近接表示**（`08`）— ノードの横に実際の値・SQL・テーブル定義を置くことで、詳細パネルを開かずに要点が掴める。段階的開示の中間段階として有効。
4. **グループ矩形によるサービス境界の表現**（`11`）— 所属（ローカル/Vercel/Supabase/外部）を視覚的に区切る。ノード数が増えたときの整理手段として有効 (UI-33 の補完)。
5. **サムネイル列による「各段階で何が起きたか」の提示**（`02` 下部）— 抽象的なノードに具象的な画像を添えることで、非エンジニアの理解を助ける。

## 付録B. 用語の暫定定義

| 用語 | 定義 |
| --- | --- |
| プロジェクトグラフ | 本IDEが保持する、プロジェクトの構成要素（ページ、コンポーネント、API、テーブル、プロセス、サービス）とその関係の内部モデル |
| ノード | 可視化上の1つの構成要素。グラフの頂点 |
| エッジ / 接続線 | ノード間の関係。データの流れ、呼び出し、依存 |
| トレース | 1つのユーザー操作（またはリクエスト）に起因する、一連の処理の記録 |
| スパン | トレースを構成する個々の処理区間 |
| リネージ | ある値が、どのデータ源から、どの経路を通って現在の表示に至ったかの系譜 |
| 順方向トレース | 画面要素 → データ源 の方向の追跡 |
| 逆方向トレース | データ源 → 画面要素 の方向の追跡 |
| 計装 | 実行時の情報を取得するために、アプリケーションの実行に組み込む観測機構 |
| 観測性レベル | 表示情報の確からしさの分類 (L0〜L3)。第5章で定義 |
