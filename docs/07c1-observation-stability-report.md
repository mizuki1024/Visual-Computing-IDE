## 1. 事前に整理したこと（基準コミット `aeac823`）

### 1.1 データの流れ

```
ブラウザ（iframe）──▶ 中継（previewGateway.ts）──▶ 開発サーバー（計装つき）
                         │ record(run, rec, {relayId, docToken})          │ スパン・呼び出し位置を
                         ▼                                                ▼ .ide-runtime/spans/<runId>.jsonl に追記
                 ObservationStore（observations.ts）◀── collect() で差分を読む
                         │ 起動ごとのセッション（run キー）
                         ▼
   /api/runtime/observations（1.5 秒ごと）──▶ 画面（LivePreview.tsx）: 一覧・キャンバス
   /api/runtime/lineage（選択のたび）    ──▶ bindDocument → evaluateLineage → 画面
```

### 1.2 基準コミットの保持方式と、そこから起きていたこと

| もの | 基準コミットの方式 | 起きていたこと |
| --- | --- | --- |
| 通信（`exchanges`） | 配列に追加。**200 件に達したら新しい通信を捨て**、数だけ `overflow` に足す | 201 件目以降の文書は記録されず、選択は `token-not-in-session`（理由の文も「別の起動・停止の前」で原因を示さない）＝ **P0-1** |
| 通し番号 `seq` | `exchanges.length + overflow + 1`（記録しない通信も番号を消費） | 単調増加・起動内で一意ではあった |
| スパン | 起動の全体で 60,000 本まで。超えたら**新しいスパンを捨てる**（`truncated`） | 通信が上限に達した後も、スパンは読み続けて溜める。1 要求 約 28 本なので約 2,100 要求で同じ問題がスパンでも起きる |
| 呼び出し位置の記録・照合の結果 | 起動の全体で持つ（照合の結果は spanId ごとに使い回す） | 際限なく増える |
| 観測 API | 毎回、保持しているすべての通信・そのトレースのスパン・SQL の解析・照合の結果を返す。SQL の解析も毎回やり直す | 200 件で 2.63 MB、以後一定。1.5 秒ごとに約 1.75 MB/秒 |
| 収集ファイル | 起動ごとに `<プロジェクト名>-<時刻>.jsonl`。消さない | 起動のたびに残る（7C-0 の終わりで 9 ファイル・74 MB） |

### 1.3 通し番号と Trace・SQL の関係（変えていない）

* 通信 → サーバー処理（`handles`）: 中継が要求ごとに作った識別子（`relayId`）を受け取った受付スパンがちょうど 1 本で、応答の `x-vcide-trace` とも食い違わないときだけ（7B-3B-1）。無い記録は応答のトレース識別子＋パスの照合（7B-3A）
* SQL（`executes` / `queries`）: その受付スパンと**同じトレース**の SQL スパン。呼び出し位置は spanId と PID の一致（7B-3B-1）
* 文書（`supplies` の前提）: iframe の文書が知らせた文書の識別子（`docToken`）を持つ通信がちょうど 1 件（7B-3B-2）

どれも**識別子の完全一致**で結ぶ。通し番号では結ばない。したがって「古い通信を外す」ことで変わるのは、照合の相手が見つからなくなる（＝結ばない）ことだけで、別の通信に付け替わる経路は無い。これを第5節の試験で確かめた。

## 2. 新しい保持方式（P0-1）

### 2.1 方式

`src/server/observations.ts`。**古い通信を外し、新しい通信は必ず記録する。** 持つのは次の和集合だけ。

| 持つもの | 数 | 理由 |
| --- | --- | --- |
| 直近の通信（種類を問わない） | 200 件（`WINDOW`） | 7C-0 までの上限と同じ大きさ。一覧と、表示中の通信の文脈 |
| 文書の識別子を持つ直近の文書（HTML の応答） | さらに 50 件（`DOC_RESERVE`） | API・RSC・HMR の取得が続いても、**表示中の文書**を押し出さないため。iframe に出ているのはふつう直近の文書 |
| 画面が保持を頼んだ通信 | 最大 8 件（`PIN_LIMIT`）・期限 30 秒（`PIN_LEASE_MS`） | **表示中・同定済みの通信を不意に失わない**ため。画面は 1.5 秒ごとの取得で頼み直す。由来の API は同定した通信を自分で頼む |

* **通し番号**: セッションの `lastSeq` を 1 ずつ増やす。外した通信の番号は使い回さない（起動の中で一意・単調増加）。起動が変われば新しいセッションで 1 から（従来どおり。起動の鍵が違えば観測を返さない）
* **スパン・呼び出し位置・照合・SQL の解析**: トレースの単位（`TraceBucket`）で持ち、**持っている通信のトレースの分だけ**残す。通信を外すとき、残す通信が参照していなければそのトレースの記録を一緒に消す
* **どの通信にも属さないトレース**（IDE 自身の生存確認など）: 120 秒（`ORPHAN_GRACE_MS`）の後に消す（応答を送り終える前に書かれるスパンがあるので、すぐには消さない）。消した受付スパンは「中継を通らない処理」の数に足す
* **外した後に読んだスパン**（通信を外した後に収集ファイルを読んだ場合）: 外した通信のトレース識別子・中継の識別子を覚えておき、猶予を待たずに消す（「中継を通らない処理」に数えない）
* **安全弁**: 持つスパンが 60,000 本（`SPAN_BUDGET`）を超えたら、古い通信から外す（保持を頼まれた通信と最新の 1 件は外さない）。それでも超えるときだけ、猶予の内のトレースも古い順に消し `truncated` を立てる
* 収集ファイルは 1 回の取得で 8 MB ずつ最大 8 回読み、読むたびに整理する（長く取得が無かった後に一度に溜めない）
* SQL の構文解析の結果をスパンごとに使い回す（7C-0 までは毎回解析し直していた）

**`MAX_EXCHANGES` を大きくする修正ではない。** 200 件という大きさは変えず、捨てる側を逆にし、証拠も同じ範囲に揃えた。

### 2.2 採用理由

| 候補 | 判断 |
| --- | --- |
| 上限を大きくする | 不採用（指示どおり）。到達が遅れるだけで、到達後は同じ。メモリと転送量も比例して増える |
| 文書の通信だけを上限の外に別に持つ | 単独では不採用。文書の後の RSC の再取得（`refetched-after-document` の判定）を見落とす。本方式では「文書の保持（50 件）」として取り込み、外した RSC は下の「保持対象外の記録」で判定に使う |
| **直近 N 件＋直近の文書＋期限つきの保持の依頼（採用）** | 新しい文書は必ず記録される。持つ量は通信の数・スパンの数の両方で上限がある。画面が見ている通信は外れない。選ばれない古い通信は理由つきで「保持対象外」になる |

### 2.3 誤接続を起こさないための点検

| 起こりうること | 対策 |
| --- | --- |
| 外した通信のスパンが、残った通信に結ばれる | 結び方は識別子の完全一致だけ（第1.3節）。外した通信のトレースは消すので、照合の候補にも残らない。単体試験 8 と soak で確認 |
| 番号の使い回しで、古い番号が新しい通信を指す | 番号は使い回さない（`lastSeq`）。画面の保持の依頼も、いま持っている番号にしか効かない（外した通信を生き返らせない） |
| 文書は保持しているが、その後の RSC の再取得を外していた | 外した通信の記録（種類・パス・時刻）も `bindDocument` の再取得の判定に使う。記録まで整理した範囲がその文書より後にかかるときは `history-evicted` で断る |
| 停止・再起動をまたいで混ざる | セッション・収集ファイルの読み取り状態・照合と解析の使い回し・保持の依頼・外した記録を、`begin` / `end` で全部捨てる |

## 3. 保持対象外の通信の扱い

* 外した通信は、番号・種類・パス・開始時刻・文書の識別子・外した理由（`window` / `span-budget`）だけを **サーバーの中に** 4,000 件（`HISTORY_LIMIT`）まで残す（`EvictedExchange`。画面へは返さない）。超えた古い記録は番号の範囲（`historyLostThroughSeq`）だけを残す
* 文書の同定（`bindDocument`）に新しい理由を 2 つ足した

| 理由 | 起きるとき | 画面の文 |
| --- | --- | --- |
| `exchange-evicted` | 選んだ要素の文書の通信を、保持範囲から外していた | 「この文書の通信は、観測の保持範囲から外れています（保持対象外）。古い通信の証拠（トレース・SQL）はもう持っていません。プレビューを読み込み直してから選んでください — 通信 #1506（/lin-a）は、直近 200 件の保持範囲より古くなったため外しました」（soak の実際の表示） |
| `history-evicted` | 文書の通信は保持しているが、それより後の通信の記録まで整理済みで、再取得が無かったことを確かめられない | 「…同じパスの再取得（RSC）が無かったことを確かめられません（保持対象外）…」 |

* `token-not-in-session` は従来どおり「いまの起動の通信に無い」とき。外した記録まで整理済みの範囲があれば、詳細にその範囲を書く（古すぎる文書か別の起動の文書かを区別できないため）
* 表示中の通信は保持を頼むので外れない。頼む前に外れた場合（画面の取得が止まっていたなど）だけ、プレビューのパネルに「表示中の通信 #n は、観測の保持範囲から外れました（保持対象外）」と出す
* 一覧の見出しに「（直近 200 件と最近の文書を保持。古い n 件は保持対象外）」と出す（7C-0 の「上限を超えた n 件は記録していません」の置き換え）
* **方針の限界**: iframe に表示しているが選んでいない文書は、保持の依頼の対象ではない（画面は表示中の文書の識別子を選ぶまで知らない）。文書の保持（直近 50 件）で守るので、その後に 50 件を超える文書と 200 件を超える通信があれば外れ、選ぶと `exchange-evicted` になる。読み込み直せば結べる（soak で確認）

## 4. 観測 API の転送量（P1-8）

### 4.1 方式の比較

| 候補 | 判断 |
| --- | --- |
| 一覧には軽量な要約だけを返す | **採用。** 画面の一覧が使うのは通信ごとの「サーバー処理に結べたか・SQL の本数・呼び出し位置を特定した本数」だけ。判定はサーバーが**全件の証拠で**行う（画面が使っていた `liveExchangeLinks` と同じ関数を、その通信のトレースの証拠だけで呼ぶ。単体試験で全件の判定と一致を確認） |
| 選んだ通信の詳細を必要時に取得する | **採用。** スパン・SQL の解析・照合は、画面が求めた通信（表示中・表示待ち・同定した文書・利用者が一覧で選んだもの。最大 4 件）の分だけ返す。由来の API は同定した通信の分を返す |
| 変更分だけを取得する | **一部採用。** 中身の指紋（`etag`）が画面の持っているものと同じなら `{ unchanged: true }` だけを返す（50 バイト）。通信単位の差分の結合は採用しなかった — 要約の形で応答の大きさは保持範囲（最大 258 件）で上限が決まり、差分の結合・外した通信の同期を画面に持たせる複雑さに見合わない |

* 証拠（Trace ID・Span ID・文書の識別子・中継の識別子・SQL・照合）は**サーバーに残る**。由来の評価はサーバーで全件の証拠と外した記録を使う。返す一覧の通信からは、中継の識別子・文書の識別子を外す（画面は使わない）
* 画面は、証拠を受け取っていない通信を変換しない（`hasDetail`。`fromLiveRun` も `detailSeqs` に無い通信を拒む）。［表示］を押した通信の証拠がまだ無ければ、待たずに取り直してから描く
* 画面の既定の選択（最新の SQL のある通信）の証拠は求めない。通信が続く間は毎回変わり、取得が増えるため（最初の試行ではこれで取得の回数が増えうることに気づき、直した）
* `detail: 'all'` を付けると 7C-0 までと同じ全件の形を返す（試験・診断用。画面は使わない）。試験（observe-e2e・queries-e2e・lineage-e2e）は証拠を直接確かめるので、これを明示して求めるように変えた

| 期間 | 回数 | 受け取った量 | 1 回あたり |
| --- | --- | --- | --- |
| 修正後: 1,500 要求の間（330 秒・1 秒 5 要求） | 212 回 | 13.8 MB | 平均 65 KB（約 42 KB/秒） |

* 1 秒 5 要求（直列）。パスは `/lin-a`・`/rsc-db`・`/api/listings`・`/lin-c`・`/rsc-parallel` の繰り返し（すべて HTML を求めるので、どれも文書の識別子を持つ）

原因の候補は 2 つあり、どちらも直した（画面が由来の評価を誤ったのではなく、試験が別の要求の応答を読んだ）。

1. 試験の道具が、由来の API の応答を**届いた順**で要求に結んでいた（`linCalls.filter((x) => !x.res).at(0)`）。応答が前後すると取り違える → **要求そのもの**（Playwright の `request`）で結ぶように直した。検査の内容・期待値は変えていない
2. 画面の由来の評価は、一時的な未観測のときに 1 秒後に取り直すが、取り直しを待つ間に**別の要素を選んでも要求を出していた**（結果は捨てていた）。古い選択の要求が新しい選択の後に届きうる → 要求を出す前に、選択が変わっていれば出さないように直した（`LivePreview.tsx` の `evaluate` に 2 行。不要な要求も減る）
