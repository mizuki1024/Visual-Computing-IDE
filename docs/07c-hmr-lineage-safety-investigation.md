## 1. 調査の結論

1. **誤対応は起きる。** Server Component の中に SQL が2つあり、その生成物の行の差が「生成物の中でのモジュールの開始位置のずれ（K 行）」と一致するとき、サーバー側 HMR の後に実行された **SQL b を、別の呼び出し a の位置に帰属させる**。製品の照合（`resolveDataAccess` の A〜D と PoC-02 の4段）はすべて通り、`evaluateLineage` は `linked` を返し、右ドックに「この値の出所 poc.regions . name」、根拠に「静的解析が見た取得の呼び出し位置と、実測した呼び出し位置（src/app/hmr-m/page.tsx:7:24）が列まで一致」と表示した【実測。第4節】。
2. **原因は、スタックの行・列の「座標系」が変わったことを IDE が知らないこと。** Next.js 16 の server fast refresh（既定で有効）は、変更されたモジュールをディスクから読み直さず、Turbopack の実行時がプロセスの中で `eval` する。そのとき `//# sourceURL=<生成物のファイル>?<moduleId>` が付き、スタックの行・列は**そのモジュール単体の中の位置**になる。計装は URL の `?<moduleId>` を捨てて生成物のファイル名だけを記録し、IDE は**ディスク上の、全モジュールを連結した生成物のソースマップ**で戻す。結果、K 行前の位置に戻る【実測＋静的。第3・4節】。
3. **既存の照合は、この誤りを構造的に止められない。** 生成物・ソースマップ・ソースの更新時刻はすべて SQL の実行より前（照合 D は通る）、ソースの内容も対応表もいまのソースと一致（F-01・コンポーネントの2情報源の一致は通る）、ずれた先の行には本当に `pool.query(` がある（行の読み直しは通る）。止まったのは「ずれた先がたまたまデータ取得の行ではなかった」場合だけで、前回の報告の「安全側（未観測）に倒れた」は**偶然**だった【実測。既存の題材の全 21 か所の呼び出しを机上で当てはめると、21 件とも偶然に未特定。誤対応になる配置が題材に無かったので、既存の試験では見つけられなかった（第4.3節）】。
4. **第2の機構も見つけた（in-flight）。** 要求の処理中にソースが変わると、実行中の古いコードの位置を、新しいソース（または新しい生成物）で解釈する。`--no-server-fast-refresh` でも起きる。このときは由来（`evaluateLineage`）は「文書の取得の後にソースが変わった」で切れるが、**観測の表示（キャンバス・詳細の「実行した呼び出し位置」）は誤った呼び出し位置を出す**【実測（製品の関数の出力）＋静的（画面がその出力をそのまま描く）。第4.4節】。
5. **MVP の推奨: 案A（実行コードの世代を確かめられない記録は、呼び出し位置の照合の段で未観測にする）。** 計装が「HMR で eval されたコードのフレーム」を印付けして渡し、IDE は (A1) その印のあるスタック、(A2) 要求の処理中に生成物・ソースが変わった SQL、(A3) ソースマップの `sourcesContent` がいまのソースと一致しない場合を、`DataAccessSite` を作る前に拒む。加えて、再起動せずに由来を取り戻す手段として `next dev --no-server-fast-refresh` での起動を**判断事項**として挙げる（実測で変更後の再要求 35/35 が正しく結んだ）。将来は案B（実行時に Node が持つソースマップで戻し、内容のハッシュで世代を結ぶ）・案C（ビルド時に呼び出し位置の識別子を埋め込む）へ進む（第6・7節）。
6. **ユーザーテストへは、A1〜A3 を入れ、この題材（/hmr-m 型）での回帰試験が通るまで進めない**ことを推奨する（第10節）。

## 3. HMR 前後の実測比較（呼び出し位置が戻せない／ずれる仕組み）

### 3.1 Next.js 16 の server fast refresh（静的）

- `next dev` は既定でサーバー側の HMR（server fast refresh）を有効にする。CLI の `--no-server-fast-refresh` か `experimental.turbopackServerFastRefresh: false` で無効になる（`poc/fixture-app/node_modules/next/dist/server/lib/router-server.js:212-222`、`next/dist/bin/next:207`）。IDE は `next dev -p <port> -H 127.0.0.1` で起動しており、既定のまま（`src/server/devServer.ts:418`）。
- App Router・Node.js ランタイムのエントリは HMR に参加し（`next/dist/server/dev/hot-reloader-turbopack.js:517-519`）、更新は `__turbopack_server_hmr_apply__` でプロセスの中に適用される（`:170-252`）。この場合 `require` キャッシュは消さない（`:576-583`）。
- Turbopack の実行時（`.next/dev/server/chunks/ssr/[turbopack]_runtime.js`、題材のコピーで生成されたもの）は、更新されたモジュールの関数を `(0, eval)(\`(require) => ${code}\`)` で作り（`:1859`）、`code` の末尾に `//# sourceURL=file:///…/<生成物>.js?<moduleId>` とインラインのソースマップを付ける（`inlineSourcemaps`、`:1790-1801`）。

## 4. 誤対応の再現結果

### 4.1 題材（一時的。使い捨てのコピーにだけ置いた）

```tsx
export default async function HmrM() {
  const a = await pool.query('SELECT id, region FROM poc.listings ORDER BY id DESC LIMIT 1');   // 7 行目
  const n1 = a.rows.length;  …  const n6 = n5 + 1;                                              // 8〜13 行目（1文1行）
```

手順3の前提（選択の位置はいまのソースの `<p>`＝F-01 は通る、文書は新しい要求に `identified`）はすべて通過（前提の確認 10/0）。画面: `hmr-misattr-3-after-hmr.png`（右ドックの「この値の出所 poc.regions . name 推定」）、比較 `hmr-misattr-1-fresh.png`・`hmr-misattr-4-after-restart.png`【実測】。

### 4.3 どのくらい起きうるか（`hmr-offset-sim.txt`。予測）

既存の題材の全ページ（21 枚）をコンパイルし、生成物の中のすべてのデータ取得の呼び出し（題材のソースに戻る 21 か所）について、「HMR の後に実行されたら、行が K 行ずれる」を製品の照合器（`rscattr.mjs`）に当てはめた。

- 予測の妥当性: `/hmr-m` の予測（a → `no-app-frame`、b → `7:24` で誤）は第3.3節の実測と一致【実測との突き合わせ】。
- 既存の題材 21 か所: **誤 0**、`no-app-frame` 10、`source-line-mismatch` 11（そのうち2か所は**別のファイル**に戻った: `ListingCount.tsx:6` → `rsc-dup/page.tsx:7`、`LinFChild.tsx:9` → `lin-f/page.tsx:10`）【予測】。
- K は生成物の中のモジュールの位置で決まる（観測した値: 2・7・69・72）。生成物の先頭のモジュールでは、同じコンポーネントの K 行前、後ろのモジュールでは**前にある別のモジュール（別のファイル）**の位置に戻る。
- 誤対応の条件: ずれた先の行が、いまのソースでデータ取得の呼び出しで、同じ囲むコンポーネント名が両方の情報源で一致し、静的解析の取得の位置と列まで一致し、その SQL の SELECT 句に参照の鍵があること。題材のように意図して置かなくても、**1つのコンポーネントに取得が複数ある実在のコード**では起こりうる【推定】。発生頻度は実在のプロジェクトでは測っていない【未観測】。
- 既存の試験（lineage-e2e・lineage-revision-e2e）は、このずれが偶然安全側に倒れる題材だけで構成されていた。**HMR の後に「未観測」になったことは、安全性の証拠ではなかった。**

### 4.4 第2の機構: 要求の処理中の変更（in-flight。`hmr-race-probe*.txt`）

`/hmr-r`: SQL a → 5 秒待つ → SQL b。要求の開始の 1.5 秒後に、a より前へ 7 文を足す。

| 条件 | SQL a | SQL b（開始 +5.0 秒） | 由来 |
| --- | --- | --- | --- |
| 既定・生成物は書き直されない（`hmr-race-probe.txt`） | `source-changed-after-call`（安全） | **`page.tsx:14:24`＝いまのソースでは a の行（誤）**。古いマップで古い位置 14 行へ戻し、新しいソースの 14 行（a）を読み直して通った | r-a・r-b とも `source-changed-after-run` で切れる（安全） |
| 同 `--no-server-fast-refresh`（`…-nsfr.txt`） | 同上 | **同上（誤）** | 同上（安全） |
| 既定・書き換えの直後に2本目の要求（生成物を +2.0 秒で書き直す。`…-kick.txt`） | `build-changed-after-call`（安全） | **`page.tsx:14:24`（誤）**。生成物の更新（+2.0 秒）は b の開始より前なので照合 D を通る | 切れる（安全） |
| 同 `--no-server-fast-refresh`（`…-nsfr-kick.txt`） | 同上 | **同上（誤）** | 切れる（安全） |

- 由来（`evaluateLineage`）は、文書の取得の開始の後にソースが変わったので切れる（`liveLineage.ts:98-101`）。**誤ったカラムは出さない**【実測】。
- しかし観測の表示（キャンバスのコンポーネントのノード・詳細の「実行した呼び出し位置」、`adapter.ts:2132-2246`）は `dataAccess` の `site` をそのまま描くので、**SQL b を a の呼び出し位置で実行したと表示する**【製品の関数の出力は実測、画面への反映は静的。画面では撮っていない】。
- Node の `findSourceMap` は、実行中の古いコードの位置を**古いソースの 14 行**（＝実行したコードとしては正しい位置）に戻した。ただし IDE がそれを**いまのソース**の 14 行として読むと誤る。案B には「どの版のソースの座標か」の照合が要る（第6節）【実測】。

## 6. 対策案の比較

### 6.1 案の内容

**案A — 実行コードの世代を確かめられない記録は未観測（MVP 推奨）**

- A1（HMR で eval されたコードの検出）: 計装の `classifyFile` で、生の URL に `?` があるもの・`eval at` の形のフレームを `build-output` にせず、新しい種別（例 `evaluated`）として記録する。IDE は、注入範囲のフレームを探す途中でこの種別が現れたら **`hmr-evaluated-code`** で拒む（そのフレームを飛ばして呼び出し元のフレームを採ることもしない）。
- A2（要求の処理中の変更）: 照合 D の基準を「SQL の開始」から「**その要求（トレースの受付スパン）の開始**」に変える。生成物・ソースマップ・戻した先のソースのどれかが要求の開始より後に書かれていれば拒む（`changed-during-request`）。
- A3（ソースマップとソースの版の一致）: 戻すのに使ったソースマップの区画の `sourcesContent` が、いまのソース（ローダの変換を同じ規則で当てたもの、または埋め込まれた `data-vcide-rev` といまの版）と一致しなければ拒む（`map-source-mismatch`）。
- 範囲: 拒むのは**その SQL の呼び出し位置だけ**。同じ要求の他の SQL、無関係なファイル、文書の同定、静的解析は止めない。
- 再び由来を出せる条件: その SQL の記録に eval のフレームが無く、要求の間に変更が無く、マップとソースが一致すること。既定の起動では、**変更したファイル（のモジュール）は開発サーバーの再起動まで**未観測になる。無関係なファイルは影響を受けない（S1・S2 の実測）。
- 不要な無効化: ファイル単位・SQL 単位なので、起動全体を無効にするより狭い。

**案A′ — 起動オプション `--no-server-fast-refresh`（案A に足す使い勝手の対策。判断事項）**

- IDE が起動する `next dev` に付ける。HMR の後も、変更されたモジュールはディスクから読み直されるので、変更後の再要求でそのまま正しく結ぶ（35/35）。
- 安全の保証ではない（in-flight は起きる）。案A と組み合わせる前提。
- 利用者の開発サーバーの振る舞いを変える（サーバー側のモジュールの状態が変更のたびに作り直される＝Next 15 までと同じ振る舞いと考える【推定】）。対応していない Next の版ではフラグが不明なオプションとして起動に失敗しうるので、版で切り替える必要がある【推定】。

**案B — 実行中のコードの世代を識別する**

- 計装が呼び出しの瞬間に `module.findSourceMap(<生の URL>)` で元の位置へ戻し、使ったマップの `sourcesContent` のハッシュ（またはその中の `data-vcide-rev`）を記録に付ける。IDE はディスクの生成物を読まず、記録の位置とハッシュを、いまのソースのハッシュと照合する。
- 世代 ID は「実行したコードが作られたソースの内容ハッシュ」になる。HMR の前後・in-flight・保存から適用までの間のすべてで、実行したコードのソースの版を指す【推定。位置は 43/43 本で正しいことを実測、ハッシュの照合は未実装】。
- 費用: SQL の呼び出しごとにマップの検索（Node が解析済みのマップを持つ）とハッシュ（マップごとに1回計算して使い回せる）。メモリ・時間は【未測定】。
- 依存: Node の `--enable-source-maps`（Next が既定で付ける。利用者が `--disable-source-maps` を使うと使えない → 未観測に倒す）、Turbopack が eval のコードにインラインのマップを付けること。
- 残る点: 同じ URL のマップが上書きされたときの in-flight（A2 と併用で止める）。

**案C — 呼び出し位置の取得方式を変える（ビルド時の計装）**

- 既存の要素識別子のローダ（`poc/anchor/loader.cjs`。Turbopack・webpack 共用）を広げ、データ取得の呼び出しに「ファイル:行:列＋ソースの版」の識別子を埋め込む（例: 呼び出しの前に非同期の文脈へ識別子を置く）。SQL のスパンはその識別子を直接持つ。スタックもソースマップも使わない。
- 世代は**実行されたコードそのものに入っている**ので、HMR・in-flight の影響を構造的に受けない。
- 課題: 利用者のコードの実行時の形を変える（`this` の束縛・タグ付きテンプレート・ORM ごとの呼び出しの形）。データ取得の API を構文で知る必要がある（静的解析 PoC-04 の取得の判定と揃えられるのは利点）。`.ts` のファイル（取得関数）もローダの対象にする必要がある（いまは `*.tsx` だけ、`poc/fixture-app/next.config.mjs` の `turbopack.rules`）。動的 SQL は問題にならない（識別子は SQL 文ではなく呼び出し位置）。実装・保守の費用が最も大きい。

**案D（参考）— 起動全体を、最初のサーバー側の変更で無効化**

- いちばん単純だが、無関係な変更でもすべての由来が消える（S1・S2 の実測からは過剰）。案A の A1 が使えない（計装を変えられない）場合の退避策。

### 6.3 推奨

- **MVP: 案A（A1＋A2＋A3）を採用する。** 安全性を最優先し、実測した失敗（HMR の eval・in-flight の2種）をすべて止める。照合の段の追加だけで、既存の規則（推測で補わない）と同じ形。
- **案A′ は判断事項として推奨する（ユーザーテストで有効にするか）。** 有効にすると、変更→再読み込み→由来の確認、という IDE の主な使い方で再起動が要らない。無効のままなら試用の手引きに「サーバー側のコードを変えたファイルの由来は、開発サーバーを再起動するまで未観測になる」と書く。
- **将来: 案B を次の段階で、案C を長期の候補として扱う。** 案B は保存〜適用の間の残りのリスクを閉じる。案C は根本的だが費用が大きい。
- 採用しない: 案D（過剰）、案A′ 単独（安全の保証にならない）。

## 7. MVP 向け推奨設計

### 7.1 未観測に切り替える場所

**`DataAccessSite` を作る段（`src/server/dataAccess.ts` の `resolveDataAccess`）で切る。** 理由:

- 由来（`liveLineage.ts` の `hits`）と観測の表示（`adapter.ts` の「実行した呼び出し位置」・コンポーネントのノード）が、同じ `dataAccess` の結果を使う。ここで切れば両方が止まる。由来の段で切ると、観測の表示に誤った呼び出し位置が残る（第4.4節）。
- 画面の段で隠すのは、誤った根拠を API が返し続けるので不可。
- 計装の段では「切る」ことはせず、**証拠（eval のフレームの印）を捨てずに渡す**ことだけを足す。現状は IDE がこの証拠を後から復元できない（`otel.cjs:104` で消えている）。

### 7.2 照合の追加（擬似的な流れ）

```
for each SQL span:
  …既存の A（記録が1件）・B（トレース・PID）
  frames = 記録のフレーム（上から）
  if frames の中で、注入範囲へ戻せる最初の build-output より上に 'evaluated' がある → 未観測 hmr-evaluated-code   (A1)
  …既存の PoC-02 の4段（rscattr.mjs）・C（src/ の中）
  t0 = その SQL のトレースの受付スパンの開始（無ければ未観測）
  if 生成物・マップ・戻した先のソースの更新時刻 > t0 → 未観測 changed-during-request                     (A2。既存の D を包含)
  if 使ったマップの区画の sourcesContent ≠ いまのソース（同じ規則で正規化） → 未観測 map-source-mismatch    (A3)
```

- `evaluated` のフレームを `parseCallsiteRecord`（`dataAccess.ts:54-79`）が**黙って捨てない**ようにすること。いまは未知の `scope` を捨てる（`:73`）ので、そのままだと呼び出し元のフレームが選ばれ、別の誤りの元になる。
- A3 の正規化は、ローダ（`poc/anchor/transform.cjs`、挿入だけで行を変えない）を同じ選択肢でいまのソースに当てて比べるのが第一案。決定的であることの確認が要る【未確認】。代案は `sourcesContent` に入っている `data-vcide-rev` といまの版の比較（JSX を持つファイルだけ）と、`.ts` は内容の一致。
- 失敗の理由は画面の文言（「サーバー側のコードが同じ起動の中で差し替わったため、実行したコードの位置を確かめられません。開発サーバーを起動し直すと確かめられます」など）を持つ。

### 7.3 MVP で保証すること・しないこと

| 保証する | 保証しない（未観測として扱う・残るリスク） |

## 10. ユーザーテストへの影響

- 現状のままでは、試用者が「コードを少し直して、読み込み直して、由来を見る」と、**誤ったカラムを確信のある根拠付きで見せる**可能性がある（第4.2節）。由来の表示は「推定」だが、根拠に「実測と列まで一致」と書くので、試用者はそれを信じる。誤対応が起きる配置は限られる（第4.3節）が、起きたかどうかを試用者も観察者も見分けられない。
- **最低条件（推奨）**:
  1. 案A（A1〜A3）の実装と T1〜T7 の通過、T8 の回帰の通過。
  2. 案A′ を使うかの決定。使わない場合は、試用の手引きと画面の理由に「サーバー側のコードを変えたファイルの由来は、開発サーバーを再起動するまで出ない」を書く。
  3. 試用の観察記録で、由来が未観測になった理由（`hmr-evaluated-code` 等）を区別して記録できること。
- 上の条件の前に試用する場合の暫定の運用（推奨しない）: 「サーバー側のコードを変えたら、由来を見る前に必ず開発サーバーを再起動する」を手引きに入れ、観察者が守らせる。これは安全の保証ではない（in-flight の観測の表示は残る）。
