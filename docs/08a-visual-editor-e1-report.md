## 1. 実装した機能

### 1.1 モジュール（`src/server/edit/`）

| ファイル | 責務（指示の 1〜8） | 書き込み |
| --- | --- | --- |
| `config.ts` | 既定で無効の判定（`VCIDE_EDIT_E1_WRITE` が `"1"` のときだけ）・範囲（`src/`・`.tsx`/`.jsx`）・必須の幅（1440・375）・検証の古さの上限・ジャーナルの保存期間 | しない |
| `target.ts` | **1. 編集対象の特定**: (行:列) の JSX 要素を探索とは別に構文解析して見つけ、className のリテラルを調べ、**内容の指紋**（タグ・囲むコンポーネント・属性の並び・className・子の構造・要素のソース全体）を作る | しない |
| `revision.ts` | **2. 版**: 同じバイト列から内容の sha256（外部変更の検出）と探索と同じソースの版（sha1 の先頭16桁 = `data-vcide-rev`）を作る。UTF-8 で往復しない内容は扱わない | しない |
| `scope.ts` | 書き込み範囲の検査（F-02）。パスの形・根から葉までの各区間の `lstat`（リンクを拒否）・`realpath(root/src)`・通常のファイル・リンク数 1・大きさ | しない |
| `validation.ts` | **3. 変更内容の検証**: `{kind:'class-token', from, to}` の形・Tailwind の token の形・同じ variant・token が1つだけある・変更後の token が無い | しない |
| `patch.ts` | **4. 差分の生成**: 範囲の1 token だけを差し替え、範囲の外が1文字も変わらないことを確かめる。表示用の unified diff と、確認した差分の同定（diffHash） | しない |
| `fsio.ts` | **5. 安全なファイル書き込み（唯一の入口）**: 対象のソースの置き換え（一時ファイル＋fsync＋rename・書く直前の再検査・書いた後の確かめ）、一時ファイルの削除、IDE 側の記録の原子的な書き込み、排他の鍵 | **する（ここだけ）** |
| `journal.ts` | **6. ジャーナル管理**: 記録の形・状態の遷移（`prepared → applying → committed / failed`）・**7. 復旧**の判断（純粋な規則 `planRecovery`）・読み出し | しない |
| `verification.ts` | **8. 適用結果の検証**: 検証の報告の形と、受け入れる条件（F-05）。純粋な関数 | しない |
| `engine.ts` | 流れの組み立て（`resolveTarget`・`reresolveTarget`・`createDraft`・`apply`・`revert`・`recover`・`submitVerification`・`outcome`） | しない（fsio を呼ぶ） |

### 1.2 コード変更の流れ

```
DOM の選択（ElementSelection: 識別子・data-vcide-rev。製品の parseSelection を通す）
   │
   ▼ resolveTarget ……………… 第1段の照合
   │   探索の7段（anchors.resolveSelection: DOM の版＝対応表の版＝いまのファイルの版・タグ・コンポーネント）
   │   ＋ 書き込み範囲（scope）＋ 自分で読み直した内容の版 ＋ 内容の指紋
   │   → 対象（id・ファイル・行:列・版・内容の sha256・指紋）をエンジンが保持
   ▼ createDraft(対象, いまの DOM の選択, {from,to}) …… 第2段の照合（同じ照合をいまの内容でやり直す）
   │   変更の検証 → token の範囲 → 差し替え → 変更後も同じ位置に同じ構造の要素があり、変わったのは token 1つだけ
   │   → 下書き（差分・diffHash・適用後の版）。ファイルには触れない
   ▼ apply({changes:[{draftId, reviewedDiffHash, selection}]}) …… 第3段の照合
   │   既定で無効なら拒否 → 変更は1件だけ（複数ファイル・複数の変更は拒否）→ 確認した差分のハッシュ
   │   → 同じ照合をもう一度 → 内容が下書きの基準と同じ → 排他の鍵
   │   → ジャーナル prepared → applying（一時ファイルの名前を先に記録）
   │   → fsio.replaceSourceFile（範囲・内容の再検査 → 一時ファイル → 最後の照合 → rename → 書いた後の確かめ）
   │   → committed（読み直した内容 = 書いた内容）／failed（書いていない・確かめられない）
   ▼ submitVerification(報告) …… プレビュー（E2 以降）が送る実測を、サーバーが自分で確かめる
   │   success = committed かつ verified（それまでは「適用済み・未検証」で、成功扱いにしない）
   ▼ revert(txId) …… いまの内容が適用直後の内容とバイト一致するときだけ戻す（それ自体も1件の適用として記録）
   ▼ recover() …… 持ち主のいない prepared・applying だけを仕様どおりに片付ける（committed・failed は対象にしない）
```

拒否の結果は `ok:false`（または `written:false`）と、理由（`reason`）・文言（`detail`）・選び直しを求めるか（`reselect`）を必ず持つ。
書き込みの結果は3つに分ける: **committed**（書いて確かめた）／**refused・conflict**（書いていない）／**failed**（書いていないことを確かめた、または書いたが確かめられない＝`written: 'unknown'` か `true`・要確認）。

## 3. F-01〜F-05 への対応

### 3.1 F-01 古い要素への誤編集（重要度 高）

| 項目 | 内容 |
| --- | --- |
| 照合するもの | DOM の版（選択の `anchorRev` = 要素の `data-vcide-rev`）・対応表の版・いまのファイルの版（ここまで探索の `resolveSelection` が3つの一致を確かめる）、**＋** エンジン自身が読み直した内容の sha256 と版、**＋** その位置の要素の**内容の指紋** |
| いつ | **第1段** 解決（`resolveTarget`・`reresolveTarget`）／**第2段** 下書きの作成（`createDraft`）／**第3段** 適用の直前（`apply`）。第2・3段は、呼び出し側が渡す**いまの DOM の選択**で探索の7段を通し直し、対象を選んだ時点の版・内容・指紋と比べる |
| 合わないとき | 書かずに `reselect: true`。理由は `target-unresolved`（探索の照合で止まった。`anchorReason` に `source-changed`・`manifest-stale` など）／`target-moved`（同じ要素が別の行・列へ動いた — 付け替えない）／`element-mismatch`（同じ位置に**別の要素**がある）／`source-changed`（同じ要素だが内容が変わった — E1 は引き継がない） |
| 再現試験 | RV07・RV08 相当（`edit-engine-unit` T3）: 1つ目の `<div>` を選んだ後に外部の編集で2つ目が同じ (行:列)・同じタグ・同じコンポーネント・同じ識別子になる → 古い DOM は `source-changed` で特定しない、新しい DOM での再解決・下書き・適用はすべて `element-mismatch` で書かない、2つ目の `p-4` は書き換わらない。兄弟の `<dd>` の入れ替え（同じ大きさ・同じ行数）も `element-mismatch`。**正しく対応付ける**: いまの DOM で選び直すと2つ目が別の指紋の対象になり、2つ目だけが書き換わる。実際の HMR の上でも同じ（`edit-e2e` 第5節） |
| 探索の F-01 | 弱めていない。`anchors.ts` は読むだけで変更していない（`git diff 2e5c0a2 -- src/server/anchors.ts` が空）。探索の版の試験（`select-revision-*`・`lineage-revision-e2e`）は全件の中で通る（第6節） |

### 3.2 F-02 許可範囲外への書き込み（重要度 中）

| 対策 | 実装 |
| --- | --- |
| パスの正規化・形 | `src/` で始まる相対パス。`..`・`.`・空・`node_modules`・隠し区間・NUL・制御文字・`\`・絶対パスを拒否 |
| 拡張子 | `.tsx`・`.jsx` だけ（小文字）。`.ts`・`.css`・`.env`・`next.config.mjs` は拒否 |
| シンボリックリンクの拒否 | 根の実体から葉まで**1区間ずつ `lstat`**。葉・途中のディレクトリ・`src` そのもの、どれがリンクでも拒否（リンク先が src/ の中でも外でも） |
| `realpath` | 実体のパスが `realpath(root/src)` の中で、かつ字面のパスと一致すること |
| その他 | 通常のファイル・リンク数 1（ハードリンクを拒否）・大きさの上限 |
| 書き込み直前の再検証 | `fsio.replaceSourceFile` の入口で検査し直し、検査した時点の同一性（dev・inode・親ディレクトリの dev・inode）と同じかを確かめる。一時ファイルを書いた後の**最後の照合**でもう一度。Linux では `/proc/self/fd` で一時ファイルの実体の場所を確かめ、rename の後に書いた実体が書き込み先の名前にあることを確かめる |
| 一時ファイル（F-06） | `O_CREAT|O_EXCL|O_NOFOLLOW` で作る。途中で失敗したら消す（開いている fd の実体を使うので、ディレクトリが移されても消せる）。プロセスが止まった場合は、ジャーナルに先に記録した名前を復旧で消す |
| 再現試験 | RV01・RV02 相当（`edit-scope-unit`）: src/ の中のリンクがプロジェクトの中・src/ の外（探索の照合は通る）を指しても `outside-scope`、リンク先は不変。下書きの後に**同じ内容**のリンクへ差し替えても書かない。段ごとの差し替え（ディレクトリ6段・ファイル5段）で src/ の外の中身は不変・一時ファイルを残さない。ジャーナルの `file` を `next.config.mjs` 等に書き換えても書かない |

**検査だけで防げない競合**は第5節（安全とは断言しない）。

### 3.3 F-03 外部変更との競合（重要度 中）

| 対策 | 実装 |
| --- | --- |
| 編集開始時の内容ハッシュ | 対象の解決の時点の内容の sha256 を対象に、下書きの時点の sha256 を下書きの基準（`baseContentHash`）にする。確認した差分のハッシュ（`diffHash`）は基準・適用後の内容・差分の本文に結び付く |
| 適用直前の再確認 | 第3段の照合（内容の sha256 が対象・下書きの基準と同じ）→ `fsio` の入口でもう一度 → 一時ファイルを書いた後の最後の照合（内容の sha256 ＋ 読む前と後の `lstat` の inode・大きさ・更新時刻・変更時刻）。違えば `conflict`・`written: false`・ジャーナル `failed` |
| 複数ファイル | 拒否（`multi-file-unsupported`）。同じファイルの2つの変更も拒否（`multi-change-unsupported`）。拒否した要求はジャーナルを作らない |
| 成功と失敗の区別 | 成功は「読み直した内容 = 書いた内容」のときの `committed` だけ。書いた直後に別の書き込みが入ったら `failed`・`written: true`・`fileState: 'other'`・要確認（成功扱いにしない・取り消しの対象にしない — F-11） |
| 自動の強制上書き | しない（その手段が無い） |
| 再現試験 | `edit-engine-unit` T5: 下書きの後・`applying`・`temp-written`・`before-final-check`・`before-last-stat` の各段の外部変更で書かない（外部変更は残る・一時ファイルを残さない・ジャーナル failed）、`renamed` の直後の外部変更は成功扱いにしない。RV04 相当（T6）。RV03（最後の照合〜rename の窓）は**既知の限界として再現を記録**（第5節） |

### 3.4 F-04 復旧処理の誤動作（重要度 中）

ジャーナルは1つの適用（または取り消し）につき1つ。IDE 側（既定 `.ide-runtime/edit-journal/<プロジェクトの鍵>/`。**対象プロジェクトの中には置けない** — 置こうとすると例外）。ソースの本文は写さない（ハッシュ・範囲・token・指紋のハッシュだけ）。

| 状態 | 意味 | 次 |
| --- | --- | --- |
| `prepared` | 照合をすべて通した。対象にも一時ファイルにも何もしていない | `applying`／`failed` |
| `applying` | これから一時ファイルを作り rename する（**この記録を書いてから**一時ファイルを作る）。対象は適用前か適用後のどちらか | `committed`／`failed` |
| `committed` | rename の後、読み直した内容が書いた内容と一致した | **終わり** |
| `failed` | 書いていない／書いたが確かめられない／復旧で戻した（`failure`・`recovery`・`needsAttention` に記録） | **終わり** |

**復旧の仕様**（`journal.planRecovery`。純粋な規則）

| 状態 | 対象の内容 | 持ち主 | 復旧 |
| --- | --- | --- | --- |
| `committed`・`failed` | 何でも | — | **何もしない**（ファイルがどんな内容でも。利用者が戻した内容にも触れない） |
| `prepared`・`applying` | 何でも | 生きている（または別の機械） | 何もしない |
| `prepared` | — | いない | `failed` にするだけ（書かない） |
| `applying` | 適用前 | いない | 一時ファイルを消して `failed` |
| `applying` | 適用後 | いない | **確定していない適用は残さない**: 適用前へ戻して `failed`（`restored-before`）。戻す前に戻すことと一時ファイルの名前を記録する（復旧の途中で止まっても次の復旧で片付く） |
| `applying` | それ以外・無い・範囲の外 | いない | **書かない**。`failed`・要確認 |

* 「適用後」で止まった適用を戻す（前へ進めて `committed` にしない）理由: 成功は `committed` を記録した後にだけ報告するので、止まった適用は利用者に成功と伝えていない。戻すのは、いまの内容が**書いた内容とバイト一致する**ときだけで、外部の変更を失わない。
* 書き込みが無効の起動では、復旧は判断を見せるだけ（`dry-run`）で、ファイル・ジャーナル・一時ファイルを変えない。
* 排他: 適用・取り消し・復旧はプロジェクトごとの鍵（`apply.lock`。持ち主の pid）を取ってから行う。持ち主が死んだ鍵だけを取り除く。鍵が取れない復旧は `busy` で何もしない。
* 保存期間: 終わった（`committed`・`failed`）ジャーナルを 30 日で消す。終わっていないものは期間に関係なく消さない。
* 再現試験（`edit-journal-unit`）: RV05 相当（T7）・子プロセスを `prepared`・`applying`・`temp-created`・`temp-written`・`before-rename`・`renamed`・`committed` で SIGKILL し、止まった時点の状態と復旧の後の状態が上の表どおり（T8）。復旧の途中の停止（3段）・停止の後の外部変更・同時に走る適用（別のプロセスが rename の後で止まっている間の復旧は何もしない → そのプロセスは `committed` まで進む）。

### 3.5 F-05 検証結果の信頼性（重要度 中）

E1 には利用者向けのプレビューが無いので、**検証の報告を受け取る契約**と、それを**サーバーが自分で**確かめる判定を実装した（`verification.ts`・`engine.submitVerification`）。UI の手順に頼らない。

| 確かめるもの（指示の項目） | 条件（1つでも外れれば `not-verified`） |
| --- | --- |
| 必須の viewport 幅 | 1440・375 がすべて、ちょうど1回ずつ（欠け・重複・置き換えを拒否） |
| 検証対象のファイル | 報告のファイル = 適用したファイル。各幅の文書が描いた対象のファイルの版 = 適用後の版 |
| ソース revision | 報告の版・測った要素の版 = 適用後の版。**受け取った時点で**サーバーがファイルを読み直した版 = 適用後の版（RS04）。文書が描いた他のファイルも、いまの版と一致 |
| 検証した文書 | 文書の識別子（32桁の16進）・パス・描いたファイルと版の組。**中継の実際の応答との結び付けは E2** |
| 実測か予測か | 各幅の `mode` が `measured`、かつ描画の中の予測の印（`data-vcide-predict`）が 0 個。言わない報告は形の不備として拒否 |
| 検証時刻 | 確定の後・未来でない（2秒の時計のずれまで）・古すぎない（10分） |
| 適用対象との対応 | txId が `committed` の適用（または取り消し）・要素の識別子が一致・測った要素がある・すべてに変更後の token があり変更前の token が無い・（サーバー側のコードが適用時に与えたときだけ）期待する計算済みスタイル |

* 結果は IDE 側に記録し（`<txId>.verification.json`）、`outcome(txId).success` は「committed かつ記録に verified がある」ときだけ真。予測の報告の後に正しい実測を送れば verified になる（予測は成功の根拠にしない）。verified の後にファイルが変わったら `staleSinceVerification: true`。
* 再現試験（`edit-verify-unit`）: RS02（Mobile だけ）・RS04（適用後の変更・無関係なファイルの変更）・予測・予測の印・版・時刻・対応・期待値の各条件。`edit-e2e` では実際の HMR の後に2幅で測り、Mobile だけ・予測を含む報告は verified にならず、2幅の実測は verified。

## 4. 安全性の保証範囲

### 4.1 保証できること（試験で確かめた条件で）

1. **既定で書かない。** `VCIDE_EDIT_E1_WRITE=1` を明示しない起動では、適用・取り消し・復旧・書き込みの入口のどれもファイルに書かない。通常の IDE の起動に書き込みの API は無い。
2. **選んだ要素以外へ書かない。** 第1〜3段のどこかで、版（DOM・対応表・ファイル）・内容のハッシュ・内容の指紋のどれかが選んだ時点と違えば書かない。同じ (行:列)・同じタグ・同じコンポーネント・同じ識別子の別の要素へは書かない。推測で付け替えない。
3. **1 token だけを変える。** 書き換えるのは構文解析で特定した静的な className のリテラルの中の1 token だけで、範囲の外は1文字も変えない（差分・バイト一致で確認）。変更後も同じ位置に同じ構造の要素があることを確かめる。
4. **src/ の外・リンク先・許可しない拡張子へ書かない**（静的なリンク・ハードリンク・パスの抜け道・段の間の差し替え・ジャーナルの書き換え）。
5. **段の間・書き込みの途中の外部変更を上書きしない**（下書きの後〜最後の照合まで。第5節の窓を除く）。
6. **確定した変更を復旧で取り消さない。** 確定していない適用は、書いた内容のままのときだけ戻す。外部の変更が混ざっていれば書かない。
7. **成功を過大に報告しない。** 成功は「書いて読み直して確かめた（committed）」かつ「サーバーが確かめた実測の検証（verified）」のときだけ。書いたが確かめられないものは `failed`・要確認で、取り消し・検証の対象にしない。
8. **途中で止まっても、対象は「適用前」か「適用後」のどちらか**（rename の原子性。途中で切れた内容にならない）で、一時ファイルは復旧で消える。

### 4.2 保証できないこと

1. **最後の照合から rename までの窓**（F-08・RV03）: この間（数十マイクロ秒）に IDE の外のエディタ・AI が同じファイルへ書くと、その変更は失われ、エンジンは `committed` と報告する。ファイルのロックが無い通常のファイルシステムでは 0 にできない。**「外部変更を上書きしない」を、この窓を含めて保証の語として使わない。** 再現は `edit-engine-unit` の［既知の限界］。
2. **同じ権限で src/ を書き換え続ける敵対的なプロセス**: 検査と open・rename の間にディレクトリを何度も差し替えられると、0 にはできない（Node に `openat`・`renameat` が無い）。Linux では `/proc/self/fd` で事後に検出して要確認とするが、他の OS ではその事後の確かめが無い。実測（`edit-scope-unit` 第5節）では、open の直前にディレクトリを差し替えると**自分の一時ファイルが一瞬 src/ の外に作られ、検出して消す**（src/ の外の既存のファイルは置き換えない）。
3. **rename の直後〜読み直しの間の外部変更**: 検出して成功扱いにしない（`failed`・要確認）が、書いた事実は戻せない。
4. **別の機械（ホスト名が違う）の記録**: 持ち主を確かめられないので復旧しない（安全側）。コンテナを作り直してホスト名が変わった場合、止まった適用のジャーナルは自動では片付かない（要確認として残る）。
5. **pid の再利用**: 持ち主の pid が別のプロセスに再利用されていると「生きている」と見なし、復旧しない（安全側）。
6. **検証の報告の真正さ**: E1 は報告の**中身**（版・幅・実測/予測・時刻・対応）を確かめるが、報告が実際のプレビューの中継から来たこと（文書の識別子と中継の応答・接続の結び付け）は E2 で結ぶ。プレビューのスクリプトはアプリと同じ JavaScript の世界で動くので、悪意のあるアプリが偽った計測を送ることは防げない（探索の `SelectionDocument` と同じ前提）。
7. **Tailwind 以外のスタイル・CSS の優先順位**: E1 は token の差し替えと描画の token の有無・（与えたときの）計算済みスタイルの一致だけを確かめる。変更の見た目の正しさの予測（幅の帯・上書き）は E4/E6。
8. Windows・macOS・ネットワークファイルシステム・webpack は試していない（Linux・ローカルの ext4 系・Turbopack）。

## 8. 次の E2「プレビューと編集対象の同期」への引き継ぎ

### 8.1 E2 が E1 から使うもの

* 書き込みはすべて `EditEngine`（`src/server/edit/engine.ts`）を通す。E2 以降で `fs` に書く処理を足さない（`edit-disabled` が検索で止める）。
* 第2・3段の照合は**いまの DOM の選択**を受け取る。E2 はプレビューの選択（v3 の `ElementSelection`）をそのまま渡せばよい。
* 検証の報告の形は `verification.ts` の `VerificationReport`。E2 はプレビューのスクリプトに「識別子・版・class の token・計算済みスタイル・予測の印の数」を測らせ、**サーバー側で**対応表から `document.sourceRevs`（ファイル → 版）を作る（`edit-e2e` の `docRevs` がその手順の見本）。
* 適用後の要素の指紋（`journal.target.afterFingerprint.hash`・`structureHash`）は、07d 3.3 の「自分が書いた変更の後の選択の引き継ぎ」に使える（HMR の後の DOM の版が `afterRev` と一致し、その位置の要素の指紋が `afterFingerprint` と一致するときだけ引き継ぐ）。

### 8.2 E2 で決めること・直すこと（優先順）

1. **選択の引き継ぎの規則（07d 3.3）**: E1 は版が変われば必ず再選択を求める。E2 で「自分が書いた変更だけが違う」ことの照合（`afterRev`・`afterFingerprint`）を設計し、外部変更が混ざったら無効にする。探索モードの照合（7段）は変えない。
2. **検証の報告と中継の結び付け**: 文書の識別子を previewGateway の文書の識別子（`SelectionDocument.token`・`DOC_TOKEN_RE`）と、接続（nonce・起動インスタンス）に結ぶ。E1 は形を確かめるだけ（第4.2節 6）。
3. **プロトコルへの編集の知らせの追加**: `previewProtocol.ts` は探索の持ち物。足すときは**探索側で先に変えて**全件を回す（07d 4.2 規則2）。知らないキーを捨てる検査を同じ強さで。
4. **起動時の復旧の呼び出し場所**: E1 の `recover()` は呼ばれない（入口が無い）。E2 で編集モードを有効にするときに、起動時に1回呼ぶ（書き込みが有効なときだけ）。別のホストの記録（第4.2節 4）の扱いを画面で見せる。
5. **ジャーナル・検証の記録の画面への出し方**（要確認の記録・`staleSinceVerification`）。

### 8.3 E2 へ進めない理由になるもの

無い。第4.2節・第5節の残るリスクは、いずれも E2（画面に出さない同期の層）を進める妨げにならない。ただし**利用者に書き込みを使わせる E4 の前に**、C-1（窓）を利用者への表示でどう伝えるか（「上書きしない」を保証の語にしない）を決める。
