## 1. 実装した経路

```
ブラウザ（プレビューの iframe）
   │ GET /rsc-db
   ▼
プレビュー中継（IDE） ── 要求ごとに乱数 R を作り、x-vcide-relay: R を開発サーバーへの要求に載せる（ブラウザの同名ヘッダは通さない）
   │                     記録: 方法・パス・状態・時刻・応答の x-vcide-trace（7B-3A）＋ R
   ▼
next dev（NODE_OPTIONS=--require boot.cjs, POC02_CALLSITE=1, POC07_RELAY_ID=1）
   ├ 受付スパン（attrs: vcide.relay.id = R）
   │   └ 描画スパン AppRender.getBodyResult（ルート単位）
   │        └ pg.query スパン ←── 呼び出しの入口（Pool.query）で取ったスタック（同じ spanId / traceId / pid の記録）
   └→ .ide-runtime/spans/<この起動>.jsonl
                     │
IDE ─ observations.collect ─ 受付スパンの索引（R → スパン）・呼び出し位置の記録（spanId → 記録）
                     └ dataAccess.ts ─ PoC-02 の rscattr.mjs（4段）＋ 7B-3B-1 の照合（第3節）
                                        → LiveDataAccess（site か、理由）
     ─ adapter.fromLiveRun ─ ③通信 ─handles→ ④処理 ─executes→ ⑤SQL ←queries─ ②''呼び出し位置
                              （選択していれば ①値 ─renders→ ② を並べる。②・① と ⑤・②'' の間に線は無い）
```

## 3. `queries` の作成条件と失敗条件

### 3.1 作る条件（すべて満たしたときだけ。`src/server/dataAccess.ts`）

| # | 条件 | 由来 |
| --- | --- | --- |
| A | その SQL のスパン ID の呼び出し位置の記録が、**いまの起動の収集ファイルにちょうど1件** | 7B-3B-1 |
| B | 記録のトレース ID・書いたプロセス（`proc.pid`）・種類（`sql`）が SQL のスパンと同じ | 7B-3B-1 |
| 1 | 記録は呼び出しの入口で取ったスタック（スパン開始時のスタックでは代用しない） | PoC-02（`rscattr.mjs`） |
| 2 | 上から順に、`src/` のソースへソースマップで戻せる最初のフレーム | PoC-02（`srvmap.mjs`） |
| 3 | 戻した行を**読み直し**、データ取得の呼び出しが書かれている | PoC-02（`srcverify.mjs`） |
| 4 | 囲むコンポーネントが、ソースの読み直しとビルド時の対応表で一致 | PoC-02 |
| C | 戻した位置が対象プロジェクトの `src/` の中（`..`・シンボリックリンクで外へ出ない） | 7B-3B-1 |
| D | SQL の実行の**後に**、生成物・ソースマップ・ソースファイルのどれも書き換わっていない | 7B-3B-1 |

ホップは `queries`（`server-call-stack`・L1相当）。`endpoints.from` は `DataAccessSite`（ファイル・行・**列**・`inComponent`）。
同じ SQL に `executes`（サーバー処理 → SQL・`trace-span`）も入り、2本とも `convergence: 'shared-object'`（同じ SQL への別々の観測。合流ではない）。
同じ位置から2本の SQL が出たら、位置のノードは1つで線が2本（どの描画インスタンスかは同定しない — 決定 G）。

### 3.2 作らない条件（理由を返し、SQL の詳細に書く）

| 理由コード | いつ |
| --- | --- |
| `callsite-disabled` | 呼び出し位置の記録を指示していない起動（IDE 以外が起動した・計装なし） |
| `no-callsite-record` / `multiple-callsite-records` | 記録が 0 件 / **2 件以上（複数候補は断定しない）** |
| `callsite-mismatch` | 記録が別のトレース・別のプロセス・別の種類 |
| `no-entry-callsite` | 入口のスタックが無い（**スタックが無い**。Prisma など） |
| `no-app-frame` | `src/` へ戻せるフレームが無い |
| `source-line-mismatch` | 戻した行にデータ取得の呼び出しが無い（**ソース不一致**） |
| `component-not-agreed` / `manifest-unavailable` | 囲むコンポーネントが2情報源で一致しない / 対応表が無い |
| `outside-scope` | `src/` の外 |
| `build-changed-after-call` / `source-changed-after-call` | 実行の後に生成物 / ソースが書き換わった |
| `build-freshness-unverified` | webpack の仮想モジュール（書き換えの有無を確かめられない） |
| `resolver-unavailable` | 照合器を読めない（使い回さず、次の取得で再試行） |

**使っていないもの**: 時刻の近さ・SQL 文の一致・ページのパス・コンポーネントの名前の一致。

### 3.3 照合器の再利用（作り直していない）

PoC-02 の3ファイルに**対象アプリの場所を引数で渡せるようにした**だけである（既定は従来どおり PoC の題材なので、PoC のランナーは変わらない）。

| ファイル | 変更 |
| --- | --- |
| `poc/runner/lib/rscattr.mjs` | `resolveRscAttribution(callsite, comps, { root })`。結果に戻す前の生成物の位置（`generated`）を足した（条件 D のため） |

## 4. 既存の実測との接続 — 同じ起動・Trace ID / Span ID・同一パスの並行要求

### 4.1 同じ起動・同じトレース・親子

| 確認 | 方法 |
| --- | --- |
| 同じ起動 | 呼び出し位置の記録は**スパンと同じ収集ファイル**（起動ごとに別のファイル — 7A の runId）からだけ読む。照合結果は観測セッションごとに持ち、`begin` / `end` で捨てる。ソースマップの索引も起動が変われば捨てる |
| Trace ID / Span ID | 記録の `spanId` と SQL のスパンの `spanId`、記録の `traceId` と SQL のスパンの `traceId` が一致すること。変換でも、照合結果のトレースが SQL のスパンと違えば使わない |
| 親子 | SQL のスパンは、その通信の受付スパン → ルート単位の描画スパンの**子孫**であること（7B-3A の判定をそのまま使う） |

### 4.2 応答ヘッダの付け替えを検出できるか（評価）

**7B-3A の規則（応答の `x-vcide-trace` ＋ パスの照合）は、同じパスの別の要求への付け替えを検出できない。** 実データで確かめた:
`/rsc-dup` へ6本を同時に送った観測を複製し、通信 A の応答ヘッダだけを同じパスの通信 B のものに差し替えると、7B-3A の規則は **A を B の受付スパンに結んでしまう**（パスは同じなので照合が通る）。
模擬環境（代役の開発サーバーが2要求に互いのトレース識別子を返す）でも同じ結果だった。

### 4.3 比較した方式と採用

| 方式 | 誰が値を決めるか | 同じパスの付け替え | アプリへの影響 | 採否 |
| --- | --- | --- | --- | --- |
| (1) 応答の専用ヘッダ `x-vcide-trace`（7B-3A） | アプリのプロセス（計装） | **検出できない** | なし | 補強としてだけ残す |
| **(2) 中継が要求ごとに作る識別子 `x-vcide-relay` を、計装が受付スパンに記録** | **IDE（中継）** | **検出できる**（受付スパンの値と応答ヘッダが食い違う） | 専用ヘッダ1つが要求に増える。アプリの既存のヘッダは変えない | **採用** |
| (3) 中継が W3C `traceparent` を生成して注入（トレース ID を IDE が決める） | IDE（中継） | 検出できる | **ブラウザ・アプリ自身の `traceparent` を上書きする**（アプリの分散トレースを壊す）。受付スパンが親を持つようになり、7B-3A の「親の無い受付スパン」の数え方が変わる | 不採用（必要になれば、アプリが `traceparent` を送っていないときだけ使う形で再検討） |

**採用した規則（`liveExchangeLinks`）**: 中継の識別子を受け取った受付スパンが**ちょうど1本**あり、応答の専用ヘッダがある場合は**同じ受付スパンを指す**こと。パスの照合も維持。0本（未着）・2本以上・食い違いのどれでも**結ばない（切断を維持）**。
ブラウザ（ページのスクリプト）が `x-vcide-relay` を送っても中継は転送せず、自分の値に置き換える。値は 16 進 32 桁の乱数だけで、計装・マスクの両方が形を検査する。ブラウザへの応答には返さない。

> 残る限界: 計装と同じプロセスで動くアプリのコードが計装そのものを書き換えることは防げない（同じ JavaScript の世界）。
> 中継の識別子は「偶然の付け替え・応答の再利用」を見抜くためのものであり、悪意のあるアプリに対する保証ではない。

### 4.4 同一パスの並行要求の検証（実物）

`/rsc-dup` へプレビューの中から6本を同時に送った（中継の記録で、6本すべてが他の要求と区間が重なっていた）。

| 確認 | 結果 |
| --- | --- |
| 中継の識別子 | 6本とも別 |
| 通信 → 受付スパン | 6本とも `relay-id` で結び、受付スパン・トレースは6本とも別。各受付スパンはその通信の識別子を受け取っていた |
| SQL | 12本（各2本）。どの SQL も1つの通信にしか属さず、その通信のトレースの中だけ |
| 呼び出し位置 | 6本とも、2本の SQL が `page.tsx:13:24` と `ListingCount.tsx:6:24` へ。照合のトレースは SQL のトレースと同じ |
| `validateDataset()` | 6本とも通過 |

## 5. 選択した要素との関係 — 証明できたこと・できなかったこと

| | 内容 |
| --- | --- |
| **証明できた** | 選んだ `<li>` を描いた JSX の位置（`src/app/rsc-db/page.tsx:19:11` / `RscDb` — 7B-2 の6段の照合）。その通信の SQL を実行した呼び出し位置（`page.tsx:12:24` / `RscDb` — 第3節）。**どちらも実測（L1 / L1相当）** |
| **事実として書いたこと** | 2つの位置が**同じコンポーネント定義（`RscDb`）の中にある**こと。選択した要素のコンポーネントの詳細に「同じ定義の中にあることは根拠にしていません。この値がその SQL の結果から来たかは未確認です」 |
| **証明できなかった** | ① この値がこの SQL の結果から来たこと（`supplies` / `derives` / `maps`）。② **この要素を描いた文書の取得が、並べた通信かどうか**（同じパスのページであることだけで並べている。どの通信がこの DOM を描いたかを示す証拠は取っていない） |
| 画面での扱い | 2つのコンポーネントのノードは**別**で、間に線は無い。値に触れる関係は `renders` だけ、描いた位置に触れる関係も `renders` だけ、実行した位置に触れる関係は `queries` だけ（E2E で確認）。描いた位置から「この値の由来は未確認です」の切断。`supplies` を作ろうとすると `validateDataset()` が拒否する |

## 11. 未検証事項・残る制約

1. **題材は `poc/fixture-app` の素の `pg` だけ。** 計装が入口を包むのは `pg` の `Pool.query` / `Client.query` だけで、Prisma・他のドライバの SQL は `no-entry-callsite`（断定しない）
2. **webpack は断定しない**（`build-freshness-unverified`）。PoC-02 は webpack でも戻せたが、実行の後に書き換わっていないかを確かめる手段を作っていない
3. **コンポーネントでない関数の中の SQL**（`/rsc-helper`）は `DataAccessSite` を担うノードが無いため `queries` を作らない。M1 は端点をソース位置としているが、表示ノードが `ComponentDef` を担う契約（`ENDPOINT_CARRIER`）のため。参考の位置は出す
4. **キャンバスの配置**: コンポーネントは2つまで（選択と並べると、実行した位置は1つまで描く。残りは SQL の詳細に書く）。SQL は2本まで（7B-3A のまま）。浮かぶパネルがキャンバスを覆う（7B-2 から継続）。コンポーネントが2つあると、1つ目の札が2つ目の立体の横に来て読み違えやすい（自動配置の札の位置。番号付きリストと右ドックでは正しく対応する）。配置は変えていない
5. **選択した要素を描いた文書取得の同定はしていない**（第5節）。同じパスであることで並べるだけ
6. 中継の識別子は、計装を書き換えるアプリには効かない（第4.3節）
7. 呼び出し位置の照合は SQL ごとにセッションの中で使い回す。照合の時点で書き換わっていなければ成立とし、その後にソースが変わっても結果は変えない（「実行したときのコード」についての主張のため）
8. 計装の性能影響（入口でのスタック取得、最大 60 フレーム）は測っていない（PoC-02 第11章 #11 のまま）
9. 実物の Codespaces・Windows は未確認（7B-3A から継続）
